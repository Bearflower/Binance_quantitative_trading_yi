## 1. 问题概述

### 1.1 背景

MTPCS 策略在开仓时，会通过 `place_conditional_order()` 挂载止损条件单（STOP）和止盈条件单（TAKE_PROFIT）到交易所。当仓位平仓后，策略通过 `_cleanup_position_orders()` 方法取消这些条件单。然而，当条件单取消失败时，策略直接标记为"已取消"（设置 `order_id = None`），导致订单仍在交易所存活，成为"孤儿条件单"。

### 1.2 问题表现

| 问题 | 描述 | 影响 |
|------|------|------|
| **孤儿条件单触发** | 孤儿条件单在新周期开仓后触发，平掉新仓位 | 造成非预期亏损 |
| **成交未记录** | 孤儿条件单触发后的成交使用新订单ID | 未被记录到 `trade_records` 表 |
| **追踪断裂** | `_cleanup_residual_orders` 清理已平仓记录后，孤儿条件单彻底无人追踪 | 无法恢复 |

### 1.3 实际损失

| 交易对 | 亏损金额 | 触发原因 |
|--------|---------|---------|
| BTCUSDT | -39.69 USDT | 孤儿条件单触发平仓 |
| XRPUSDT | -30.28 USDT | 孤儿条件单触发平仓 |

### 1.4 数据差异

- 已发现 **123 笔** 未匹配成交记录（条件单触发后的成交使用新订单ID，未被记录到 `trade_records`）

## 2. 问题根因分析

### 2.1 条件单取消流程（当前实现）

```
平仓完成
  ↓
position.current_quantity <= 0
  ↓
position.cancel_pending = True
  ↓
asyncio.ensure_future(_cleanup_position_orders(symbol, position))
  ↓
对每个条件单分别调用 cancel_algo_order()
  ↓
┌─ 成功 → order_id = None（正常）
└─ 失败 → order_id = None（异常！← 问题根因）
```

### 2.2 根因一：取消失败后直接放弃追踪

在 `_cleanup_position_orders()` 方法中（[strategy.py:L3353](file:///Users/yl/vscode/Binance_quantitative_trading/strategies/btc_eth/strategy.py#L3353-L3528)），对每个条件单的取消操作有独立的 `try/except` 包裹：

```python
# 代码片段（strategy.py 约 L3368-L3396）
if position.stop_loss_order_id is not None:
    try:
        await self.binance.cancel_algo_order(symbol, position.stop_loss_order_id)
        position.stop_loss_order_id = None  # 成功时置空
    except BinanceAPIError as e:
        if e.code in silent_error_codes:
            position.stop_loss_order_id = None  # 静默错误码也置空
        else:
            # 仅记录日志，不置空？不不，也没有 retry 逻辑
            logger.warning(...)
    except Exception as e:
        logger.warning(...)  # 未知异常仅记录日志
```

**关键缺陷**：取消失败时，无论是否可重试，代码都没有重试机制。`silent_error_codes` 中的错误码（如订单已成交）被静默处理后置空，非静默错误码仅记录警告日志但**同样没有重试**。最终在方法末尾的检查中，只要所有 `order_id` 都为 `None`，就认为清理完成。

### 2.3 根因二：启动时无孤儿条件单检测

`cleanup_orphan_algo_orders()` 方法（[strategy.py:L3567](file:///Users/yl/vscode/Binance_quantitative_trading/strategies/btc_eth/strategy.py#L3567-L3578)）已废弃，因为条件单查询 API `/papi/v1/um/algo/openOrders` 已不再可用。策略启动时无法检测交易所上是否存在未关联的孤儿条件单。

### 2.4 根因三：条件单触发成交未记录

`place_conditional_order()` 方法（[shared/binance_api.py:L528](file:///Users/yl/vscode/Binance_quantitative_trading/shared/binance_api.py#L528-L696)）在条件单创建时调用 `trade_logger.log_order()` 记录一次。但条件单触发后的实际成交通过 `place_conditional_order()` 返回的响应中不包含成交明细，且条件单触发后的成交由交易所自动执行，策略不会收到成交回调，因此成交记录缺失。

### 2.5 问题传播路径

```
条件单取消失败（API异常）
  ↓
order_id 置为 None，失去追踪
  ↓
条件单仍在交易所存活
  ↓
该币种持仓已平仓，_cleanup_residual_orders 删除持仓记录
  ↓
新周期该币种重新开仓
  ↓
孤儿条件单触发，平掉新仓位
  ↓
触发后的成交未被记录到 trade_records
  ↓
外部 orphan_cleanup 脚本无法关联（algo_id 已不在本地记录中）
  ↓
问题永久性丢失追踪
```

## 3. 修复目标

### 3.1 核心目标

1. **条件单取消重试机制**：取消失败时，不能直接标记为"已取消"，应放入重试队列，确保最终一致性
2. **启动时孤儿条件单检测**：策略启动时，通过 `condition_orders` 表检测是否有未关联的孤儿条件单，并取消
3. **记录条件单触发成交**：条件单触发后的成交也应记录到 `trade_records`，确保账务完整
4. **条件单创建时机控制**：限价开仓单成交确认后，才创建止损/止盈条件单，防止限价单未成交时条件单成为孤儿单

### 3.2 非目标

- 不修改外部脚本 `orphan_cleanup.py` 的逻辑（该脚本作为兜底清理机制继续运行）
- 不修改 `condition_orders` 表结构
- 不引入新的外部依赖
- 不修改 `_close_position()` 以外的平仓逻辑

## 4. 功能需求

### 4.1 条件单取消重试机制

#### 4.1.1 需求描述

在 `_cleanup_position_orders()` 中，当条件单取消失败时，不再直接设置 `order_id = None`，而是将取消失败的条件单信息放入重试队列，后续周期持续重试，直到取消成功或确认条件单已触发执行。

#### 4.1.2 业务规则

| 规则 | 描述 |
|------|------|
| R1.1 | 取消失败时，保留 `order_id` 不变，不移除追踪 |
| R1.2 | 取消成功的条件单，立即设置 `order_id = None` |
| R1.3 | 条件单确认已触发执行（如返回 `-2021` 错误码），标记为已执行，设置 `order_id = None` |
| R1.4 | 重试间隔：每个周期（`main_loop` 循环）重试一次，不额外增加 API 调用频率 |
| R1.5 | 最大重试次数：配置化（默认 10 次），超过后触发告警通知 |
| R1.6 | 重试超时后（超过最大重试次数），不再重试，记录错误日志并发送飞书通知 |

#### 4.1.3 重试队列数据结构

在 `PositionState` 中增加重试相关字段：

```python
@dataclass
class PositionState:
    # ... 现有字段
    
    # 新增：条件单取消重试计数
    cancel_retry_count: Dict[str, int] = field(default_factory=dict)
    # key: 条件单类型（"stop_loss" / "tp1" / "tp2" / "trailing_stop"）
    # value: 已重试次数
```

#### 4.1.4 修改位置

| 文件 | 方法 | 修改内容 |
|------|------|---------|
| `strategies/btc_eth/strategy.py` | `PositionState` | 增加 `cancel_retry_count` 字段 |
| `strategies/btc_eth/strategy.py` | `_cleanup_position_orders()` | 取消失败时保留 order_id，递增重试计数 |
| `strategies/btc_eth/strategy.py` | `main_loop()` 或 `_cleanup_residual_orders()` | 每周期检查重试队列，执行重试 |
| `shared/condition_orders.py` | `record_condition_order()` | 补充 orderId 情况的记录逻辑 |

#### 4.1.5 异常处理

| 场景 | 处理方式 |
|------|---------|
| 取消 API 返回 `-2011`（订单不存在） | 视为取消成功，设置 `order_id = None` |
| 取消 API 返回 `-2021`（条件单已执行） | 视为已执行，设置 `order_id = None`，记录到 `trade_records` |
| 取消 API 返回其他错误码 | 递增重试计数，保留 order_id |
| 网络异常（如超时） | 递增重试计数，保留 order_id |
| 达到最大重试次数仍失败 | 发送飞书告警，不再重试，记录错误日志 |

#### 4.1.6 配置项

在 `config.yaml` 的 `risk_config` 中增加以下配置：

```yaml
risk_config:
  # 原有配置...
  
  # 新增：条件单取消重试配置
  cancel_retry:
    max_retries: 10          # 最大重试次数
    retry_interval_cycles: 1 # 重试间隔（主循环周期数）
    notify_on_timeout: true  # 超时后是否发送通知
    cleanup_timeout_seconds: 300    # 启动时孤儿单清理超时时间（秒）
    trade_lookup_window_minutes: 60 # 查询已执行条件单成交记录的时间窗口（分钟）
```

#### 4.1.7 流程图

```
_cleanup_position_orders 调用
  ↓
对每个条件单执行取消
  ↓
┌─ 取消成功 → order_id = None，清除重试计数
│
├─ 异常码 -2011（订单不存在）→ order_id = None，视为已取消
│
├─ 异常码 -2021（已执行）→ order_id = None，标记已执行，记录成交
│
├─ 其他异常码或网络异常
│   ↓
│   递增 cancel_retry_count[type] += 1
│   ↓
│   ┌─ 未达最大重试次数 → 保留 order_id，等待下次周期重试
│   └─ 已达最大重试次数 → 发送飞书告警，order_id = None（放弃）
│
└─ 所有条件单取消完成后
    ↓
    检查是否还有待重试的条件单
    ↓
    ┌─ 有 → position.cancel_pending = True（保持待处理状态）
    └─ 无 → position.cancel_pending = False
```

### 4.2 启动时孤儿条件单检测与清理

#### 4.2.1 需求描述

策略启动时（`__init__` 或 `main_loop` 首次执行前），通过 `condition_orders` 表查询该策略的 OPEN 状态条件单，与交易所当前持仓进行对比，对无对应持仓的孤儿条件单执行取消。

#### 4.2.2 业务规则

| 规则 | 描述 |
|------|------|
| R2.1 | 策略启动时，从 `condition_orders` 表查询 `strategy_name='btc_eth'` 且 `status='OPEN'` 的条件单 |
| R2.2 | 查询交易所当前持仓，获取有持仓的 symbol 集合 |
| R2.3 | 对于 `condition_orders` 表中的 OPEN 条件单，其 symbol 不在交易所持仓中的，视为孤儿条件单 |
| R2.4 | 对孤儿条件单执行取消操作，取消成功后更新 `condition_orders` 表状态为 `CANCELED` |
| R2.5 | 取消操作使用 `cancel_all_algo_orders` 批量取消（按 symbol 维度），比逐个取消更可靠 |
| R2.6 | 启动时孤儿条件单清理在策略主循环开始前完成，不影响后续交易 |
| R2.7 | 清理结果发送飞书通知（成功数量、失败数量、详情） |

#### 4.2.3 修改位置

| 文件 | 方法 | 修改内容 |
|------|------|---------|
| `strategies/btc_eth/strategy.py` | 新增 `_startup_orphan_cleanup()` | 实现启动时孤儿条件单检测与清理 |
| `strategies/btc_eth/strategy.py` | `__init__` 或 `main_loop` 首次执行前 | 调用 `_startup_orphan_cleanup()` |

#### 4.2.4 与现存机制的关系

| 现存机制 | 关系 |
|---------|------|
| `_ensure_position_protection()` | 已通过 `condition_orders` 表检查是否有 OPEN 条件单，但不会主动取消孤儿单。本功能补充了启动时清理能力 |
| `orphan_cleanup.py`（外部脚本） | 每 30 分钟执行一次，与本功能互为补充。本功能在启动时执行，外部脚本在运行时持续守护 |
| `_cleanup_position_orders()` | 处理平仓时的条件单清理，本功能处理启动时已存在的孤儿单 |

#### 4.2.5 流程图

```
策略启动
  ↓
查询 condition_orders 表（strategy='btc_eth', status='OPEN'）
  ↓
┌─ 无 OPEN 条件单 → 跳过清理
└─ 有 OPEN 条件单
    ↓
    查询交易所当前持仓
    ↓
    对比得出孤儿条件单集合（条件单 symbol 不在交易所持仓中）
    ↓
    ┌─ 无孤儿条件单 → 跳过清理
    └─ 有孤儿条件单
        ↓
        按 symbol 分组，对每个 symbol 调用 cancel_all_algo_orders
        ↓
        更新 condition_orders 表状态为 CANCELED
        ↓
        发送飞书通知（清理结果汇总）
```

### 4.3 条件单触发成交记录

#### 4.3.1 需求描述

条件单触发后，交易所自动执行的成交应被记录到 `trade_records` 表，确保账务完整。策略通过定时查询交易所的订单状态或利用 `condition_orders` 表的状态变更来捕获条件单触发后的成交信息。

#### 4.3.2 方案选择

| 方案 | 描述 | 优点 | 缺点 | 推荐 |
|------|------|------|------|------|
| **方案A：定时查询** | 定期查询 `condition_orders` 表中 OPEN 状态条件单对应的订单成交情况 | 实现简单，不依赖 WebSocket | 有延迟，增加 API 调用 | 推荐 |
| **方案B：WebSocket 监听** | 通过 WebSocket 监听条件单触发事件 | 实时性好 | 需要 WebSocket 连接，实现复杂 | 暂不推荐 |
| **方案C：取消时确认** | 取消条件单时，如果返回 `-2021`（已执行），立即查询成交记录 | 触发时机明确 | 仅覆盖取消时已执行的场景 | 作为补充 |

**推荐方案A + 方案C 组合**：

- 主方案：**方案A** — 每周期扫描 `condition_orders` 表中 OPEN 状态的条件单，查询交易所对应订单的状态
- 补充方案：**方案C** — 在 `_cleanup_position_orders()` 和 `_cleanup_residual_orders()` 中，当遇到 `-2021` 错误码时，立即查询成交记录

#### 4.3.3 业务规则

| 规则 | 描述 |
|------|------|
| R3.1 | 条件单触发后，通过 `condition_orders` 表中的 `algo_id` 无法直接查询成交（条件单 API 已废弃） |
| R3.2 | 采用间接方式：通过 `cancel_algo_order` 返回 `-2021` 确认条件单已执行，此时查询 `trade_records` 表确认是否有对应的成交记录 |
| R3.3 | 如果没有成交记录，记录一条警告日志，标记为"条件单已执行但无成交记录，需人工核查" |
| R3.4 | 已执行的条件单，更新 `condition_orders` 表状态为 `EXECUTED` |
| R3.5 | 对于已执行的条件单，从 `trade_records` 表关联的成交记录中提取盈亏数据 |

#### 4.3.4 修改位置

| 文件 | 方法 | 修改内容 |
|------|------|---------|
| `strategies/btc_eth/strategy.py` | `_cleanup_position_orders()` | 在 `-2021` 异常处理中，补充成交记录检查 |
| `strategies/btc_eth/strategy.py` | `_cleanup_residual_orders()` | 在清理已平仓记录时，检查条件单是否已执行 |
| `strategies/btc_eth/strategy.py` | 新增 `_check_executed_conditional_orders()` | 定时检查已执行的条件单并记录成交 |

#### 4.3.5 流程图

```
每周期执行
  ↓
查询 condition_orders 表（strategy='btc_eth', status='OPEN'）
  ↓
对每个 OPEN 条件单
  ↓
尝试取消（获取实际状态）
  ↓
┌─ 返回 -2011（订单不存在）→ 标记为 CANCELED
│
├─ 返回 -2021（已执行）
│   ↓
│   查询 trade_records 表（按 symbol 和时间范围）
│   ↓
│   ┌─ 有匹配记录 → 记录日志，确认已记录
│   └─ 无匹配记录 → 记录警告日志，标记需人工核查
│   ↓
│   更新 condition_orders 状态为 EXECUTED
│
├─ 取消成功 → 标记为 CANCELED
│
└─ 其他异常 → 保留 OPEN 状态，下次周期重试
```

### 4.4 条件单创建时机控制

#### 4.4.1 需求描述

MTPCS 策略在开仓时，先通过 `place_limit_order()` 挂限价开仓单，然后立即创建止损/止盈条件单。当限价开仓单未成交时，条件单已被创建，导致：

1. **孤儿单风险**：如果限价单最终未成交，这些条件单成为"孤儿单"（持仓不存在但条件单存在）
2. **异常执行风险**：后续价格波动触发条件单时，因无持仓而执行失败或产生异常行为

#### 4.4.2 解决方案

在 `strategy.py` 中新增 `_wait_for_order_fill` 方法，在限价开仓单挂单后轮询成交状态，确认成交后才创建止损/止盈条件单。

**核心逻辑：**

```
place_limit_order() 开仓限价单
  ↓
调用 _wait_for_order_fill() 轮询成交状态
  ↓
┌─ 成交确认 → 创建止损/止盈条件单（正常流程）
└─ 超时未成交 → 取消限价单，返回 False，不创建条件单
```

#### 4.4.3 配置项

在 `config.yaml` 的 `risk_config.position_sizing` 节中新增配置项：

```yaml
risk_config:
  position_sizing:
    entry_order_timeout_seconds: 60  # 限价单入场超时等待秒数，超时后取消限价单，不创建条件单
```

#### 4.4.4 验收标准

| 编号 | 验收项 | 验收条件 |
|------|--------|---------|
| AC-T1 | 限价单成交后创建条件单 | 限价单成交确认后，止损/止盈条件单被创建 |
| AC-T2 | 限价单超时未成交不创建条件单 | 超时后取消限价单，不创建条件单，日志记录超时信息 |
| AC-T3 | 限价单被取消/过期/拒绝不创建条件单 | 限价单非成交状态结束时，条件单不被创建 |
| AC-T4 | 超时时间从配置读取 | `entry_order_timeout_seconds` 配置项生效，无硬编码 |

#### 4.4.5 边界条件

| 边界条件 | 处理方式 |
|---------|---------|
| 限价单立即成交（轮询前已成交） | 首次查询即检测到成交，直接进入条件单创建流程 |
| 轮询期间网络异常 | 记录警告日志，继续轮询直到超时 |
| 超时后取消限价单失败 | 记录错误日志，不再重试（下次策略周期处理） |
| 策略重启时存在未成交限价单 | 重启后策略状态恢复，未成交限价单在交易所仍存在，策略重新开始监控 |

## 7. 风险说明

### 7.1 技术风险

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|---------|
| 条件单批量取消 API 不稳定 | 低 | 中等 | 作为兜底手段，不依赖单次调用成功；失败时回退到逐个取消 |
| 启动时孤儿单检测延迟策略启动 | 低 | 低 | 设置超时时间（30秒），超时后跳过清理，不影响启动 |
| 重试队列与主循环耦合导致性能问题 | 低 | 低 | 重试逻辑异步执行，不阻塞主循环 |
| condition_orders 表数据过大 | 低 | 低 | 保留历史数据，查询时只过滤 `status='OPEN'` |

### 7.2 业务风险

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|---------|
| 重试期间孤儿条件单触发 | 中 | 高 | 重试间隔短（一个周期约 1-2 分钟），降低窗口期 |
| 启动时误取消正常条件单 | 低 | 高 | 严格对比交易所持仓，仅取消无对应持仓的条件单 |
| 重试次数耗尽后仍有孤儿条件单 | 低 | 中 | 依赖外部 `orphan_cleanup.py` 兜底清理 |

### 7.3 依赖关系

| 依赖 | 说明 | 风险 |
|------|------|------|
| `condition_orders` 表 | 启动时检测依赖该表数据的完整性 | 如果历史数据不完整，检测效果打折扣 |
| `cancel_all_algo_orders` API | 批量取消条件单 | 该 API 需要统一账户模式支持 |
| `cancel_algo_order` API | 逐个取消条件单，返回状态码 | 依赖 API 返回正确的状态码 |

### 7.4 回滚方案

如果修复上线后出现异常，可以通过以下方式快速回滚：

1. **配置回滚**：将 `cancel_retry.max_retries` 设为 0，关闭重试机制
2. **代码回滚**：恢复 `strategy.py` 到上一个版本
3. **数据库回滚**：`condition_orders` 表结构不变，无需回滚
