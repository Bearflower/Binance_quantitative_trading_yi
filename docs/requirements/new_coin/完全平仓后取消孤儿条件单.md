## 1. 需求概述

### 1.1 背景

新币做空策略使用分批止盈止损机制，每笔做空开仓时会同时创建以下条件单（algo orders）：

| 序号 | 条件单类型 | 触发方向 | 平仓比例 | 订单特点 |
|------|-----------|---------|---------|---------|
| 1 | `STOP` | 价格上涨触发止损 | 100%（`closePosition=True`） | 止损单，限价偏移量 0.1% |
| 2 | `TAKE_PROFIT` | 价格下跌触发止盈 | 30% | 第一目标止盈，限价偏移量 0.1% |
| 3 | `TAKE_PROFIT` | 价格下跌触发止盈 | 40% | 第二目标止盈，限价偏移量 0.1% |

剩余 30% 仓位由策略代码中的移动止盈逻辑监控（`_check_trailing_stop`），不通过条件单管理。

### 1.2 核心问题

当止盈单或止损单触发导致该合约**完全平仓**后，该合约上尚未触发的其他条件单**不会被自动取消**，成为"孤儿订单"（orphan orders）。

**孤儿订单的危害：**

- **资金风险**：如果价格后续反向波动触及孤儿条件单的触发价，可能执行**非预期的开仓**或**报错**（因为实际持仓已为 0，部分平仓单可能因数量不匹配而失败，但 `closePosition=True` 的止损单可能产生不可预期的行为）
- **资源浪费**：孤儿条件单持续占用交易所的条件单数量配额（币安限制每个合约最多 10 个条件单）
- **状态混乱**：策略内部 `self.positions` 已清除，但交易所仍有该合约的条件单，导致策略状态与交易所状态不一致

### 1.3 需求描述

> 合约进行止盈或止损后，该合约处于完全平仓时，未触发的止盈订单与止损订单，应该同步取消。这个可以在每小时系统启动检测的时候进行处理。

### 1.4 业务目标

- 确保策略内部状态与交易所实际状态保持一致
- 消除孤儿条件单带来的资金风险
- 不增加额外的 API 调用负担（复用现有的每小时 `_monitor_positions()` 检测周期）

## 2. 问题场景分析

### 2.1 场景一：止损先触发，完全平仓

```
开仓 → 设置 3 个条件单（止损、止盈30%、止盈40%）
  ↓
价格反向暴涨 → 止损单触发（closePosition=True，平仓100%）
  ↓
交易所状态：持仓 = 0，但止盈30%和止盈40%两个条件单仍然存在
策略状态：self.positions 中该 symbol 被移除
  ↓
【问题】两个止盈条件单成为孤儿订单
```

### 2.2 场景二：两个止盈目标先后触发，完全平仓

```
开仓 → 设置 3 个条件单（止损、止盈30%、止盈40%）
  ↓
价格下跌 → 第一目标止盈触发（平仓30%），剩余70%
  ↓
价格继续下跌 → 第二目标止盈触发（平仓40%），剩余30%
  ↓
移动止盈触发 → 平仓剩余30%
  ↓
交易所状态：持仓 = 0，但止损单仍然存在
策略状态：self.positions 中该 symbol 被移除
  ↓
【问题】止损单成为孤儿订单
```

### 2.3 场景三：止盈触发后止损触发

```
开仓 → 设置 3 个条件单（止损、止盈30%、止盈40%）
  ↓
价格下跌 → 第一目标止盈触发（平仓30%），剩余70%
  ↓
价格反向暴涨 → 止损单触发（closePosition=True，平仓剩余70%）
  ↓
交易所状态：持仓 = 0，但第二目标止盈（40%）条件单仍然存在
策略状态：self.positions 中该 symbol 被移除
  ↓
【问题】第二目标止盈单成为孤儿订单
```

### 2.4 场景四：时间止损触发，完全平仓

```
开仓 → 设置 3 个条件单
  ↓
持仓超过 72 小时 → 时间止损触发（_close_position 平仓100%）
  ↓
交易所状态：持仓 = 0，但 3 个条件单全部存在
策略状态：self.positions 中该 symbol 被移除
  ↓
【问题】全部 3 个条件单成为孤儿订单
```

## 5. 实现方案

### 5.1 方案概述

在 `TradingExecutor` 中新增 `cancel_all_algo_orders(symbol)` 方法，该方法：
1. 从 `position_tracking[symbol]['algo_ids']` 获取本地存储的 algoId 列表
2. 遍历列表，对每个条件单调用 `binance_api.cancel_algo_order(symbol, algo_id)` 逐个取消
3. 单个取消失败不阻塞后续取消，仅记录警告日志
4. 返回取消结果统计（总数、成功数、失败数）

在 `strategy._monitor_positions()` 中，检测到完全平仓后（`positionAmt == 0`），在删除 `self.positions` 记录**之前**，调用 `trading_executor.cancel_all_algo_orders(symbol)` 取消孤儿条件单。

### 5.2 模块一：TradingExecutor 新增方法

**文件：** `strategies/new_coin/executor.py`

**新增方法：** `cancel_all_algo_orders(symbol: str) -> Dict[str, int]`

**方法签名：**

```python
async def cancel_all_algo_orders(self, symbol: str) -> Dict[str, int]:
    """
    取消指定合约上所有未触发的条件单（止盈止损单）

    在完全平仓后调用，清理孤儿条件单，防止后续价格波动触发非预期交易。

    Args:
        symbol: 交易对名称

    Returns:
        取消结果统计字典：
        - total: 查询到的条件单总数
        - cancelled: 成功取消的数量
        - failed: 取消失败的数量
        - algo_ids: 已取消的条件单ID列表
    """
```

**伪代码逻辑：**

```
1. 从 self.position_tracking[symbol]['algo_ids'] 获取本地存储的 algoId 列表
2. 如果列表为空，记录日志，返回 {total: 0, cancelled: 0, failed: 0, algo_ids: []}
3. 遍历列表，对每个 algoId：
   a. 调用 binance_api.cancel_algo_order(symbol, algo_id)
   b. 成功：cancelled += 1，记录日志
   c. 失败：failed += 1，记录警告日志（含错误信息），继续下一个
4. 记录总结日志：共 N 个条件单，取消成功 M 个，失败 K 个
5. 返回统计结果
```

### 5.3 模块二：strategy._monitor_positions() 修改

**文件：** `strategies/new_coin/strategy.py`  
**修改位置：** `_monitor_positions()` 方法，约第 675 行

**修改内容：** 在检测到完全平仓后（`positionAmt == 0`），在删除 `self.positions` 之前，插入取消孤儿条件单的调用。

**修改后的流程：**

```
检测到完全平仓 (positionAmt == 0)
  ↓
【新增】调用 trading_executor.cancel_all_algo_orders(symbol)
  ↓
【新增】清理 trading_executor.position_tracking 中对应记录
  ↓
计算盈亏（原有逻辑）
  ↓
更新连续亏损计数（原有逻辑）
  ↓
删除 self.positions 记录（原有逻辑）
  ↓
保存状态（原有逻辑）
```

**关键设计决策：**

1. **取消操作放在盈亏计算之前**：如果取消操作抛出异常（不应影响盈亏计算），盈亏计算仍可继续；但实际上取消操作的异常应被内部捕获，确保不抛出
2. **取消操作放在删除 self.positions 之前**：确保即使取消操作失败，`self.positions` 记录仍保留，下次周期可以重试
3. **取消操作失败不阻塞后续流程**：取消失败只记录警告，不影响盈亏计算和状态更新

### 5.4 数据结构

**position_tracking 中存储的 algo_ids 字段：**

| 字段 | 类型 | 说明 |
|------|------|------|
| `algo_ids` | List[int] | 条件单ID列表，开仓时从创建条件单返回值中提取并存储，用于取消操作 |

**说明：** 不再依赖 `get_open_algo_orders()` 查询条件单列表，而是在开仓创建条件单时，将返回的 `algoId` 存入 `position_tracking` 的 `algo_ids` 字段中。完全平仓时直接从本地存储读取并取消。

### 5.5 API 调用频率考虑

- `get_open_algo_orders(symbol)` 已废弃，不再调用
- `cancel_algo_order(symbol, algo_id)`：每次完全平仓时调用 N 次（N = 剩余条件单数，通常 1~3 个），从本地 `position_tracking[symbol]['algo_ids']` 获取 algoId
- 币安 API 权重：取消条件单 `1` 权重
- 总计每次完全平仓消耗约 1~3 权重，远低于限频，无需额外频率控制

### 5.6 条件单创建时机控制

#### 5.6.1 问题描述

new_coin 策略在开仓时，`_place_short_order()` 挂限价开仓单后，立即调用 `_set_stop_loss_take_profit()` 创建止损/止盈条件单。当限价开仓单未成交时，条件单已被创建，导致：

1. **孤儿单风险**：如果限价单最终未成交，这些条件单成为"孤儿单"（持仓不存在但条件单存在）
2. **异常执行风险**：后续价格波动触发条件单时，因无持仓而执行失败或产生异常行为

#### 5.6.2 解决方案

在 `executor.py` 中新增 `_wait_for_order_fill` 方法，在 `_place_short_order()` 挂限价开仓单后轮询成交状态，确认成交后才创建止损/止盈条件单。

**核心逻辑：**

```
_place_short_order() 挂限价开仓单
  ↓
调用 _wait_for_order_fill() 轮询成交状态
  ↓
┌─ 成交确认 → 创建止损/止盈条件单（正常流程）
└─ 超时未成交 → 取消限价单，返回 None，不创建条件单
```

#### 5.6.3 配置项

在 `config.yaml` 的 `trading` 节中新增配置项：

```yaml
trading:
  entry_order_timeout_seconds: 60  # 限价单入场超时等待秒数，超时后取消限价单，不创建条件单
```

#### 5.6.4 验收标准

| 编号 | 验收项 | 验收条件 |
|------|--------|---------|
| AC-T1 | 限价单成交后创建条件单 | 限价单成交确认后，止损/止盈条件单被创建 |
| AC-T2 | 限价单超时未成交不创建条件单 | 超时后取消限价单，不创建条件单，日志记录超时信息 |
| AC-T3 | 限价单被取消/过期/拒绝不创建条件单 | 限价单非成交状态结束时，条件单不被创建 |
| AC-T4 | 超时时间从配置读取 | `entry_order_timeout_seconds` 配置项生效，无硬编码 |

#### 5.6.5 边界条件

| 边界条件 | 处理方式 |
|---------|---------|
| 限价单立即成交（轮询前已成交） | 首次查询即检测到成交，直接进入条件单创建流程 |
| 轮询期间网络异常 | 记录警告日志，继续轮询直到超时 |
| 超时后取消限价单失败 | 记录错误日志，不再重试（下次策略周期处理） |
| 策略重启时存在未成交限价单 | 重启后策略状态恢复，未成交限价单在交易所仍存在，策略重新开始监控 |

## 6. 边界条件和异常处理

### 6.1 边界条件

| 边界条件 | 处理方式 | 说明 |
|---------|---------|------|
| 该合约无未触发条件单 | `position_tracking[symbol]['algo_ids']` 为空列表，直接返回成功 | 可能已被手动取消或全部触发 |
| 条件单已被触发但尚未从列表移除 | `cancel_algo_order` 可能返回错误，容错处理 | 币安条件单触发后可能有短暂延迟才从列表移除 |
| 同时多个合约完全平仓 | 逐个处理，互不影响 | 遍历 `self.positions` 的循环本身就是逐个处理 |
| 策略重启后恢复状态 | 恢复的 `self.positions` 中可能包含已平仓的持仓 | 下次 `_monitor_positions()` 检测到完全平仓时会触发取消 |
| 网络超时 | `cancel_algo_order` 内部有重试机制（`@retry_on_failure`） | API 层已有重试，单次失败记录警告继续 |
| 非统一账户模式 | `get_open_algo_orders` 和 `cancel_algo_order` 仅支持统一账户 | 当前生产环境使用统一账户，无需额外处理 |

### 6.2 异常处理策略

| 异常类型 | 处理策略 | 恢复方式 |
|---------|---------|---------|
| 读取 `position_tracking[symbol]['algo_ids']` 时 key 不存在 | 记录警告日志，视为空列表，不阻塞后续流程 | 开仓时未正确存储 algoId 导致，需检查开仓逻辑 |
| `position_tracking[symbol]['algo_ids']` 为空列表 | 记录日志，直接返回成功 | 所有条件单已被取消或触发 |
| `cancel_algo_order` 单个取消失败 | 记录警告日志（含 algo_id 和错误信息），继续取消下一个 | 已取消的生效，失败的留待下次 |
| `cancel_algo_order` 全部取消失败 | 记录错误日志，不阻塞后续流程 | 下次周期重试 |
| `cancel_algo_order` 参数错误（如 algo_id 无效） | 记录错误日志，跳过该条 | 不太可能发生，防御性处理 |

### 6.3 幂等性

- `position_tracking[symbol]['algo_ids']`：本地存储读取，天然幂等
- `cancel_algo_order`：如果条件单已被取消，币安 API 返回错误 `-2011`（Order was not found），需捕获此错误码并视为成功（已被取消）
- 如果同一 symbol 在短时间内被两次检测到完全平仓（极端情况），第二次读取 `position_tracking[symbol]['algo_ids']` 应为空（已清理），不会重复取消

## 7. 验收标准

### 7.1 功能验收

| 编号 | 验收项 | 验收条件 | 验证方式 |
|------|--------|---------|---------|
| AC-1 | 止损触发后取消止盈单 | 止损触发完全平仓后，该合约上所有未触发止盈单被取消 | 日志检查 + API 查询确认 |
| AC-2 | 止盈触发后取消止损单 | 两个止盈目标全部触发后完全平仓，止损单被取消 | 日志检查 + API 查询确认 |
| AC-3 | 时间止损后取消所有条件单 | 时间止损触发完全平仓后，所有 3 个条件单被取消 | 日志检查 + API 查询确认 |
| AC-4 | 部分平仓不触发取消 | 仅第一目标止盈触发（30%），持仓未完全平仓，不取消任何条件单 | 日志确认无取消操作 |
| AC-5 | 取消失败不阻塞流程 | 单个条件单取消失败时，不影响其他条件单取消和后续盈亏计算 | 日志确认流程继续 |
| AC-6 | 无条件单时正常返回 | 该合约无未触发条件单时，取消操作正常返回，不报错 | 日志确认正常返回 |
| AC-7 | position_tracking 清理 | 完全平仓后，`trading_executor.position_tracking` 中该 symbol 记录被清除 | 代码检查 |
| AC-8 | 限价单成交后创建条件单 | 限价单成交确认后，止损/止盈条件单被创建 | 日志检查 + 代码审查 |
| AC-9 | 限价单超时未成交不创建条件单 | 超时后取消限价单，不创建条件单，日志记录超时信息 | 日志检查 |
| AC-10 | 限价单被取消/过期/拒绝不创建条件单 | 限价单非成交状态结束时，条件单不被创建 | 日志检查 |
| AC-11 | 超时时间从配置读取 | `entry_order_timeout_seconds` 配置项生效，无硬编码 | 代码审查 |

## 9. 附录：术语说明

| 术语 | 说明 |
|------|------|
| 条件单（Algo Order） | 币安统一账户中的算法订单，包括止损单（STOP_MARKET）和止盈单（TAKE_PROFIT_MARKET），当市场价格达到触发条件时自动执行 |
| 孤儿订单（Orphan Order） | 持仓已完全平仓但条件单仍然存在于交易所的订单，无人管理，可能触发非预期交易 |
| 完全平仓 | 持仓数量为 0 的状态，即 `positionAmt == 0` |
| `closePosition=True` | 条件单参数，表示触发后平掉全部持仓，不指定具体数量 |
| `algoId` | 币安统一账户中条件单的唯一标识符，用于取消操作 |
| `position_tracking` | `TradingExecutor` 内部字典，用于跟踪每个持仓的止盈目标和移动止盈状态 |
