### 1.2 术语表

| 术语 | 说明 |
|------|------|
| 市价单（MARKET） | 以当前市场最优价格立即成交的订单，存在滑点风险 |
| 限价单（LIMIT） | 指定具体价格的订单，只有达到指定价格时才会成交 |
| 条件单（Algo Order） | 币安统一账户中的算法订单，包括止损单（STOP_MARKET/STOP）和止盈单（TAKE_PROFIT_MARKET/TAKE_PROFIT），当市场价格达到触发条件时自动执行 |
| 止损限价单（STOP） | 触发后以限价方式执行的止损单，限价 = 止损价 x (1 + slippage) |
| 止盈限价单（TAKE_PROFIT） | 触发后以限价方式执行的止盈单，限价 = 止盈价 x (1 + slippage) |
| 孤儿订单（Orphan Order） | 持仓已完全平仓但条件单仍然存在于交易所的订单，无人管理，可能触发非预期交易 |
| algoId | 币安统一账户中条件单的唯一标识符，用于取消操作 |
| `position_tracking` | `TradingExecutor` 内部字典，用于跟踪每个持仓的止盈目标和移动止盈状态 |
| 限价单滑点（limit_order_slippage） | 限价相对触发价的偏移量，默认 0.001（0.1%），确保限价单能成交 |

## 2. 产品概述

### 2.1 背景

当前项目存在两个反复出现的问题，严重影响策略交易的安全性和稳定性：

**问题一：限价单问题**

新币做空策略（new_coin）的需求文档 V4.0 完整版第 10 节已明确要求所有订单类型使用限价单，包括开仓、止损、止盈、平仓。然而实际代码中仍然存在 8 处使用市价单（MARKET / STOP_MARKET / TAKE_PROFIT_MARKET），未按文档要求改造为限价单。市价单在流动性不足或剧烈波动时会产生严重的滑点，导致交易成本增加和预期收益偏离。

**问题二：孤儿单问题**

完全平仓后，条件单（止盈/止损单）未被自动取消，成为孤儿订单。new_coin 策略的 `cancel_all_algo_orders()` 方法依赖已废弃的 Binance API `get_open_algo_orders()` 来查询未触发的条件单，但该 API 已于 2026 年 6 月底被币安废弃，始终返回空列表，导致清理功能完全失效。孤儿订单存在以下风险：
- 价格后续反向波动可能触发非预期的交易
- 占用交易所条件单配额
- 策略状态与交易所状态不一致

### 2.2 业务目标

| 目标 | 衡量指标 | 优先级 |
|------|---------|--------|
| 消除市价单滑点风险 | new_coin 策略所有订单均为限价单 | **P0** |
| 建立交易层市价单检测机制 | 检测到市价单时记录警告日志并通过 webhook 通知 | **P1** |
| 消除孤儿订单风险 | 完全平仓后条件单被可靠取消 | **P0** |
| 建立兜底清理机制 | ai-tuner 每 30 分钟自动检测并取消孤儿条件单 | **P0** |

## 3. 问题一：限价单问题

### 3.1 问题描述

new_coin 策略的 `executor.py` 中，共有 8 处使用市价单类型，与需求文档 V4.0 第 10 节的要求不符。

### 3.2 当前代码现状

| 序号 | 方法名 | 行号 | 当前订单类型 | 问题说明 |
|------|--------|------|-------------|---------|
| 1 | `_place_short_order` | 373 | `MARKET` | 开空仓使用市价单，存在滑点风险 |
| 2 | `_save_order` | 407 | `'MARKET'` | 订单记录类型写死为 MARKET，应与实际订单类型一致 |
| 3 | `_set_stop_loss_take_profit` 止损 | 451 | `STOP_MARKET` | 止损条件单使用市价单，触发后可能滑点 |
| 4 | `_set_stop_loss_take_profit` 止盈 | 467 | `TAKE_PROFIT_MARKET` | 止盈条件单使用市价单，触发后可能滑点 |
| 5 | `_set_batch_stop_loss_take_profit` 止损 | 628 | `STOP_MARKET` | 分批止盈中的止损使用市价单 |
| 6 | `_set_batch_stop_loss_take_profit` TP1 止盈 | 652 | `TAKE_PROFIT_MARKET` | 分批止盈中的第一目标止盈使用市价单 |
| 7 | `_set_batch_stop_loss_take_profit` TP2 止盈 | 695 | `TAKE_PROFIT_MARKET` | 分批止盈中的第二目标止盈使用市价单 |
| 8 | `_close_position` 平仓 | 973 | `MARKET` | 平仓使用市价单，存在滑点风险 |

### 3.3 影响范围

- 开仓市价单：在流动性差的新币上，滑点可能达到 1%~3%，直接侵蚀预期收益
- 止损市价单：止损触发时如果市场流动性不足，实际成交价可能远低于预期止损价，导致亏损放大
- 止盈市价单：止盈触发时可能因滑点减少实际盈利
- 平仓市价单：平仓时的滑点影响最终盈亏

## 4. 问题二：孤儿单问题

### 4.1 问题描述

完全平仓后，条件单（止盈止损单）未被自动取消，成为孤儿订单。原因在于 `cancel_all_algo_orders()` 依赖的 `get_open_algo_orders()` API 已被币安废弃。

### 4.2 当前代码现状

**文件：** `strategies/new_coin/executor.py`，方法 `cancel_all_algo_orders()`（第 993~1100 行）

当前流程：
```
cancel_all_algo_orders(symbol)
  └── binance_api.get_open_algo_orders(symbol)  ← 已废弃，始终返回空列表
        └── 返回空列表 → 方法直接返回，不执行任何取消
```

**文件：** `shared/binance_api.py`，方法 `get_open_algo_orders()`（第 374~392 行）

当前实现：
```python
async def get_open_algo_orders(self, symbol: Optional[str] = None) -> List[Dict]:
    logger.debug("条件单查询API已废弃，直接返回空列表", symbol=symbol)
    return []
```

### 4.3 影响范围

- 紧急止损触发后，剩余的止盈条件单不会被取消
- 时间止损触发后，全部 3 个条件单都不会被取消
- 分批止盈触发后，剩余的止损条件单不会被取消
- 条件单在后续价格波动中可能触发非预期交易

## 5. 修复一：限价单问题 -- C方案（立即修复new_coin代码）

### 5.1 方案概述

将 `strategies/new_coin/executor.py` 中的 8 处市价单改为限价单，限价计算方式遵循需求文档 V4.0 第 10 节的规定。

### 5.2 详细变更清单

#### 5.2.1 `_place_short_order` 开空仓（第 370~375 行）

| 项目 | 当前值 | 目标值 |
|------|--------|--------|
| 订单类型 | `MARKET` | `LIMIT` |
| 限价计算 | 无 | 限价 = 当前价（不应用滑点） |
| 新增参数 | 无 | `price=current_price`（需传入 Decimal 格式当前价） |

**方法签名变更：**
```python
# 当前
async def _place_short_order(self, symbol: str, quantity: Decimal) -> Optional[Dict[str, Any]]:

# 改为
async def _place_short_order(self, symbol: str, quantity: Decimal, current_price: Decimal) -> Optional[Dict[str, Any]]:
```

**调用方变更：** `execute_short()` 中调用 `_place_short_order` 时需传入当前价格。

**注意：** 开仓限价单需要设置 `timeInForce` 参数，推荐使用 `IOC`（Immediate-or-Cancel）或 `GTC`（Good-till-Cancelled）。使用 `GTC` 确保订单在成交前持续有效，避免因瞬时价格波动导致开仓失败。

#### 5.2.2 `_save_order` 保存订单类型（第 407 行）

| 项目 | 当前值 | 目标值 |
|------|--------|--------|
| 订单类型字段 | `'MARKET'` | `'LIMIT'` |

**注意：** 此处保存的是订单记录类型，应与实际下单类型一致。如果后续开仓改为 LIMIT，此处应同步改为 `'LIMIT'`。

#### 5.2.3 `_set_stop_loss_take_profit` 止损止盈（第 448~471 行）

**止损单（第 448~455 行）：**

| 项目 | 当前值 | 目标值 |
|------|--------|--------|
| 订单类型 | `STOP_MARKET` | `STOP` |
| 限价计算 | 无 | 限价 = 止损价 x (1 + limit_order_slippage) |
| 新增参数 | 无 | `price=stop_limit_price` |

**止盈单（第 464~471 行）：**

| 项目 | 当前值 | 目标值 |
|------|--------|--------|
| 订单类型 | `TAKE_PROFIT_MARKET` | `TAKE_PROFIT` |
| 限价计算 | 无 | 限价 = 止盈价 x (1 + limit_order_slippage) |
| 新增参数 | 无 | `price=tp_limit_price` |

**限价计算逻辑：**
```python
# 从配置读取滑点参数
slippage = Decimal(str(self.config.get('trading', {}).get('limit_order_slippage', 0.001)))

# 止损限价 = 止损价 x (1 + slippage)，限价略高于止损价，触发后立即成交
stop_limit_price = self._format_price(stop_loss_price * (Decimal('1') + slippage), tick_size)

# 止盈限价 = 止盈价 x (1 + slippage)，限价略高于止盈价，触发后立即成交
tp_limit_price = self._format_price(take_profit_price * (Decimal('1') + slippage), tick_size)
```

**重要：** 止盈限价方向必须为 `(1 + slippage)`，不能写成 `(1 - slippage)`。做空止盈是买入，买入限价成交条件为市场价 <= 限价，因此限价应略高于触发价以确保成交。

#### 5.2.4 `_set_batch_stop_loss_take_profit` 分批止盈止损（第 625~698 行）

**止损单（第 625~632 行）：**

| 项目 | 当前值 | 目标值 |
|------|--------|--------|
| 订单类型 | `STOP_MARKET` | `STOP` |
| 限价计算 | 无 | 限价 = 止损价 x (1 + limit_order_slippage) |

**TP1 止盈（第 649~655 行）：**

| 项目 | 当前值 | 目标值 |
|------|--------|--------|
| 订单类型 | `TAKE_PROFIT_MARKET` | `TAKE_PROFIT` |
| 限价计算 | 无 | 限价 = 止盈价 x (1 + limit_order_slippage) |

**TP2 止盈（第 692~698 行）：**

| 项目 | 当前值 | 目标值 |
|------|--------|--------|
| 订单类型 | `TAKE_PROFIT_MARKET` | `TAKE_PROFIT` |
| 限价计算 | 无 | 限价 = 止盈价 x (1 + limit_order_slippage) |

#### 5.2.5 `_close_position` 平仓（第 970~975 行）

| 项目 | 当前值 | 目标值 |
|------|--------|--------|
| 订单类型 | `MARKET` | `LIMIT`（带市价回退） |
| 限价计算 | 无 | 限价 = 当前价 x (1 + limit_order_slippage) |
| 容错机制 | 无 | 限价单失败时回退到 MARKET |

**平仓容错逻辑（伪代码）：**
```python
try:
    # 获取当前价格
    ticker = await self.binance_api._request(...)
    current_price = Decimal(str(ticker.get('price', 0)))
    
    if current_price <= 0:
        raise ValueError("获取当前价格异常")
    
    # 计算限价
    slippage = Decimal(str(self.config.get('trading', {}).get('limit_order_slippage', 0.001)))
    limit_price = current_price * (Decimal('1') + slippage)
    limit_price = self._format_price(limit_price, tick_size)
    
    # 优先使用限价单
    order = await self.binance_api.place_order(
        symbol=symbol,
        side='BUY',
        order_type='LIMIT',
        quantity=close_quantity,
        price=limit_price
    )
except Exception as e:
    logger.warning(f"限价平仓失败，回退市价单: {e}")
    # 回退到市价单
    order = await self.binance_api.place_order(
        symbol=symbol,
        side='BUY',
        order_type='MARKET',
        quantity=close_quantity
    )
```

### 5.4 边界条件与异常处理

| 边界条件 | 处理方式 |
|---------|---------|
| 开仓限价单未成交 | 检查 `timeInForce` 参数，使用 `GTC` 确保订单持续有效；后续可在监控逻辑中处理未成交的限价单 |
| 止损限价计算值等于止损价 | 滑点默认为 0.1%，正常情况下不会相等；如果滑点配置为 0，限价 = 止损价，此时限价单可能无法立即成交 |
| 平仓限价单获取当前价异常（<=0） | 捕获异常，回退到 MARKET 市价单 |
| 平仓限价单抛异常 | 捕获异常，记录警告日志，回退到 MARKET 市价单 |
| 精度调整后限价等于触发价 | 滑点 0.1% 经精度调整后可能被截断，需确保 `_format_price` 处理后限价严格高于触发价 |
| 滑点配置为 0 | 允许，但限价单可能因价格微小波动无法成交，需在日志中提示 |

- 止损日志中订单类型为 `STOP`，不再出现 `STOP_MARKET`
- 止盈日志中订单类型为 `TAKE_PROFIT`，不再出现 `TAKE_PROFIT_MARKET`
- 平仓日志中订单类型为 `LIMIT`，失败时出现"回退市价单"警告日志
- `_save_order` 保存的订单类型为 `LIMIT`

## 6. 修复二：限价单问题 -- B方案（交易层拦截警告）

### 6.1 方案概述

在 `shared/binance_api.py` 中的 `place_order()` 和 `place_conditional_order()` 方法中增加参数校验，检测到市价单类型时记录警告日志，不拒绝执行。警告信息通过策略的 webhook 发出通知。

### 6.2 详细变更

#### 6.2.1 `place_order()` 增加市价单警告（第 394~509 行）

**修改位置：** `place_order()` 方法中，参数校验完成后、下单之前。

**检测逻辑：**
```python
# 检测市价单，记录警告日志
if order_type == 'MARKET':
    logger.warning(
        "检测到市价单，建议使用限价单",
        symbol=symbol,
        side=side,
        quantity=float(adjusted_quantity) if adjusted_quantity else None,
    )
```

**约束：** 仅记录警告，不拒绝执行，确保不影响现有业务流程。

#### 6.2.2 `place_conditional_order()` 增加市价条件单警告（第 511~665 行）

**修改位置：** `place_conditional_order()` 方法中，参数校验完成后、下单之前。

**检测逻辑：**
```python
# 检测市价条件单，记录警告日志
if order_type in ('STOP_MARKET', 'TAKE_PROFIT_MARKET'):
    logger.warning(
        "检测到市价条件单，建议使用限价条件单",
        symbol=symbol,
        side=side,
        order_type=order_type,
        stop_price=float(adjusted_stop_price),
    )
```

### 6.3 通知方式

警告日志通过 structlog 记录，日志级别为 `warning`。策略的 webhook 通知机制（如 `NotificationClient`）会捕获 `warning` 级别日志并发送通知。

**通知内容示例：**
```
【交易层警告】检测到市价单
策略: new_coin
交易对: BTCUSDT
方向: SELL
订单类型: MARKET
数量: 0.001
建议: 使用限价单（LIMIT）避免滑点风险
```

### 6.4 验证要点

- 调用 `place_order()` 时传入 `order_type='MARKET'`，日志中出现警告
- 调用 `place_conditional_order()` 时传入 `order_type='STOP_MARKET'` 或 `TAKE_PROFIT_MARKET'`，日志中出现警告
- 调用 `place_order()` 时传入 `order_type='LIMIT'`，日志中无警告

#### 7.3.4 `cancel_all_algo_orders()` 改为使用本地 algoId

**修改位置：** 第 993~1100 行

**当前逻辑（依赖已废弃 API）：**
1. 调用 `get_open_algo_orders(symbol)` 查询条件单列表（始终返回空）
2. 遍历返回列表逐一取消
3. 因始终返回空列表，实际不会执行任何取消操作

**目标逻辑（使用本地 algoId）：**
1. 从 `self.position_tracking[symbol]['algo_ids']` 获取本地存储的 algoId 列表
2. 遍历列表，对每个 algoId 调用 `binance_api.cancel_algo_order(symbol, algo_id)`
3. 幂等处理：捕获 `-2011` 错误码（Order was not found）视为成功
4. 记录取消结果统计

**伪代码逻辑：**
```python
async def cancel_all_algo_orders(self, symbol: str) -> Dict[str, Any]:
    result = {
        'total': 0,
        'cancelled': 0,
        'failed': 0,
        'algo_ids': [],
    }

    # 从本地存储获取 algoId
    tracking = self.position_tracking.get(symbol, {})
    algo_ids = tracking.get('algo_ids', {})
    
    if not algo_ids:
        logger.info("无本地记录的条件单", symbol=symbol)
        return result

    result['total'] = len(algo_ids)
    
    for role, algo_id in algo_ids.items():
        if algo_id is None:
            result['failed'] += 1
            continue
        
        try:
            await self.binance_api.cancel_algo_order(symbol, algo_id)
            result['cancelled'] += 1
            result['algo_ids'].append(algo_id)
            logger.info("取消条件单成功", symbol=symbol, algo_id=algo_id, role=role)
        except BinanceAPIError as e:
            if e.code == -2011:
                # 已不存在，视为成功（幂等）
                result['cancelled'] += 1
                result['algo_ids'].append(algo_id)
            else:
                result['failed'] += 1
                logger.warning("取消条件单失败", symbol=symbol, algo_id=algo_id, role=role, error=str(e))
        except Exception as e:
            result['failed'] += 1
            logger.warning("取消条件单异常", symbol=symbol, algo_id=algo_id, role=role, error=str(e))
    
    # 清理已取消的 algo_ids
    if symbol in self.position_tracking:
        self.position_tracking[symbol]['algo_ids'] = {}
    
    return result
```

### 7.4 边界条件与异常处理

| 边界条件 | 处理方式 |
|---------|---------|
| 条件单创建失败，algoId 为空 | 不存储空值，`algo_ids` 字典中不包含该角色的条目 |
| 策略重启时 `position_tracking` 为空 | 从数据库恢复的持仓需重新创建条件单（已有 `replenish_conditional_orders` 逻辑），补全后保存 algoId |
| 相同的 algoId 被重复取消 | `cancel_algo_order` 的 `-2011` 错误码幂等处理 |
| 多个条件单部分取消失败 | 失败的不阻塞后续取消，记录警告日志 |
| `algo_ids` 字典为空 | 直接返回，不执行任何 API 调用 |
| 平仓后清理 `position_tracking` | 在 `cancel_all_algo_orders` 调用后，清理 `algo_ids` 字段 |

## 8. 修复四：孤儿单问题 -- A方案（ai-tuner兜底清理）

### 8.1 方案概述

在 ai-tuner 中新增定时任务，每 30 分钟执行一次，通过 `condition_orders` 表与 `strategy_states` 表对比，自动取消孤儿条件单并发送飞书通知。

**处理场景：**
- **场景A（策略崩溃）**：策略容器异常，超过 `stale_hours_threshold`（2 小时）未更新策略状态，取消该策略所有 OPEN 条件单
- **场景B（持仓已平仓）**：策略正常运行，但某 symbol 已不在持仓中，取消该 symbol 的 OPEN 条件单

方案共分两个阶段实施：
- **阶段一**（已跳过）：仅检测 + 通知，不执行取消（因 `condition_orders` 表尚未建立）
- **阶段二**（当前实现）：引入 `condition_orders` 表持久化条件单记录，实现实际取消逻辑

### 8.2 当前实现范围（阶段二）

#### 8.2.1 新增共享模块：`shared/condition_orders.py`

CREATE INDEX idx_co_strategy ON condition_orders(strategy_name);

**_cancel_order 核心逻辑：**

```python
async def _cancel_order(self, order):
    """
    取消单个条件单/订单，并更新 condition_orders 表状态

    Returns:
        (bool, str): (是否成功, 错误信息或 None)
    """
    strategy_name = order['strategy_name']
    symbol = order['symbol']
    algo_id = order.get('algo_id')
    order_id = order.get('order_id')
    order_type = order.get('order_type', '')

    try:
        if algo_id is not None:
            # 条件单用 cancel_algo_order
            await self.binance.cancel_algo_order(symbol, int(algo_id))
        elif order_id is not None:
            # 普通订单用 cancel_order
            await self.binance.cancel_order(symbol, str(order_id))
        else:
            return False, "无订单ID"

        # 标记为已取消
        await mark_order_canceled(self.db, order_id=order_id, algo_id=algo_id)
        return True, None

    except Exception as e:
        error_str = str(e)
        # -2011 已不存在 → 视为取消成功
        if "-2011" in error_str or "Order does not exist" in error_str:
            await mark_order_canceled(self.db, order_id=order_id, algo_id=algo_id)
            return True, None
        # 条件单已执行 → 标记为已执行
        if "algo" in error_str.lower() and (
            "not exist" in error_str.lower() or "invalid" in error_str.lower()
        ):
            await mark_order_executed(self.db, algo_id=algo_id, order_id=order_id)
            return True, "订单已执行"
        return False, error_str
```

### 8.4 边界条件与异常处理

| 边界条件 | 处理方式 |
|---------|---------|
| 数据库连接失败 | 记录错误日志，跳过本次检查，下次重试 |
| 查询 strategy_states 返回空 | 仅处理场景A（策略无状态记录），场景B 无法判断，跳过 |
| condition_orders 表不存在 | `_ensure_table()` 自动创建，幂等操作 |
| 取消订单时 -2011 错误（订单已不存在） | 视为取消成功，更新 status=CANCELED |
| 取消订单时 algoId 已无效（条件单已执行） | 更新 status=EXECUTED，视为成功 |
| 通知发送失败 | 记录错误日志，不影响下次检查 |
| 定时任务重叠 | 使用 `coalesce=True`，前一次未完成时跳过本次 |
| 多个策略同时异常 | 汇总所有异常，一次通知发送 |

- 幂等性：重复执行不会产生副作用（订单已取消的返回 -2011 视为成功）
- condition_orders 表中状态正确更新为 CANCELED 或 EXECUTED

## 9. 修复五：条件单创建时机控制 -- 限价单成交确认后创建条件单

### 9.1 问题描述

当限价开仓单未成交时，策略会立即创建止损/止盈条件单，导致：

1. **孤儿单风险**：如果限价单最终未成交，这些条件单成为"孤儿单"（持仓不存在但条件单存在）
2. **异常执行风险**：即使后续价格波动触发条件单，也会因为无持仓而执行失败或产生异常行为

### 9.2 解决方案

在开仓限价单成交确认后，才创建止损/止盈条件单。新增 `_wait_for_order_fill` 方法轮询限价单成交状态，超时未成交则取消限价单，不创建条件单。

**核心逻辑：**

```
开仓限价单（place_limit_order）
  ↓
调用 _wait_for_order_fill 轮询成交状态
  ↓
┌─ 成交确认 → 创建止损/止盈条件单（正常流程）
└─ 超时未成交 → 取消限价单，返回 False/None，不创建条件单
```

### 9.3 涉及策略

| 策略 | 模块 | 实现方法 | 说明 |
|------|------|---------|------|
| btc_eth（MTPCS） | `strategies/btc_eth/strategy.py` | 新增 `_wait_for_order_fill` 方法 | 开仓限价单（`place_limit_order`）后调用 |
| new_coin（新币做空） | `strategies/new_coin/executor.py` | 新增 `_wait_for_order_fill` 方法 | 开仓限价单（`_place_short_order`）后调用 |
| hrs（网格策略） | `strategies/hrs/position_manager.py` | 已有 `_check_order_fill_with_timeout` 保护 | 无需修改 |

### 9.4 配置项

```yaml
# btc_eth config.yaml - risk_config.position_sizing 节
risk_config:
  position_sizing:
    entry_order_timeout_seconds: 60  # 限价单入场超时等待秒数

# new_coin config.yaml - trading 节
trading:
  entry_order_timeout_seconds: 60  # 限价单入场超时等待秒数
```

### 9.5 验收标准

| 编号 | 验收项 | 验收条件 | 验证方式 |
|------|--------|---------|---------|
| AC-T1 | 限价单成交后创建条件单 | 限价单成交确认后，止损/止盈条件单被创建 | 日志检查 + 代码审查 |
| AC-T2 | 限价单超时未成交不创建条件单 | 超时后取消限价单，不创建条件单，日志记录超时信息 | 日志检查 |
| AC-T3 | 限价单被取消/过期/拒绝不创建条件单 | 限价单非成交状态结束时，条件单不被创建 | 日志检查 |
| AC-T4 | 超时时间从配置读取 | `entry_order_timeout_seconds` 配置项生效，无硬编码 | 代码审查 |

### 9.6 边界条件与异常处理

| 边界条件 | 处理方式 |
|---------|---------|
| 限价单立即成交（轮询前已成交） | 首次查询即检测到成交，直接进入条件单创建流程 |
| 轮询期间网络异常 | 记录警告日志，继续轮询直到超时 |
| 限价单部分成交 | 根据实际成交数量决定是否创建条件单（部分成交也视为成交） |
| 超时后取消限价单失败 | 记录错误日志，不再重试（下次策略周期处理） |
| 策略重启时存在未成交限价单 | 重启后策略状态恢复，未成交限价单在交易所仍存在，策略重新开始监控 |

## 12. 依赖关系与风险

### 12.1 依赖关系

| 修复编号 | 依赖项 | 说明 |
|---------|--------|------|
| 修复一 | `config.yaml` 中已有 `limit_order_slippage` 配置 | 无需新增配置，直接使用现有配置 |
| 修复二 | 无 | 独立修改，不依赖其他修复 |
| 修复三 | 修复一（限价单改造） | 修复三中创建条件单后保存 algoId，需先完成限价单改造 |
| 修复四 | 无 | 独立模块，不依赖其他修复 |
| 修复五 | 修复一（限价单改造） | 修复五中限价单成交确认后创建条件单，需先完成限价单改造 |

### 12.2 风险分析

| 风险 | 等级 | 说明 | 应对措施 |
|------|------|------|---------|
| 限价单未成交导致开仓失败 | **中** | 开仓 LIMIT 单可能因价格偏离未成交 | 使用 `GTC` 时间策略；后续可在监控逻辑中处理未成交限价单 |
| 止损限价单未触发导致亏损放大 | **中** | 限价单在急速行情中可能未成交 | 滑点 0.1% 可确保限价略高于触发价；后续可根据市场波动调整滑点参数 |
| 平仓限价单回退失败 | **低** | 市价单回退逻辑异常 | 市价单回退在 try-catch 块内，异常已被捕获 |
| 策略重启后 `position_tracking` 缺失 | **中** | 数据库恢复的持仓无 `algo_ids` | `replenish_conditional_orders` 补单后会保存新的 algoId |
| ai-tuner 取消操作与策略冲突 | **低** | ai-tuner 和策略同时取消同一条件单 | 幂等处理（-2011 错误码视为成功） |
| 限价单方向错误导致订单不成交 | **高** | 止盈限价方向错误（如用 `1 - slippage` 替代 `1 + slippage`） | 严格代码审查，参考 V4.0 文档第 10.3 节限价方向规则 |
| _wait_for_order_fill 轮询延迟 | **低** | 轮询间隔导致条件单创建延迟 | 轮询间隔短（约 0.5~1 秒），对整体交易延迟影响极小 |
| 超时后取消限价单失败 | **低** | 取消限价单 API 异常 | 记录错误日志，下次策略周期处理 |

### 12.3 执行顺序建议

```
第一阶段：修复一（限价单改造） + 修复三（本地algoId管理）
  └── 两者关系紧密，建议同时实施
  └── 测试验证：限价单是否正常下单，algoId 是否正常保存和取消

第二阶段：修复二（交易层警告）
  └── 独立修改，可在第一阶段之后或并行实施
  └── 测试验证：市价单警告日志是否正常输出

第三阶段：修复四（ai-tuner兜底清理）
  └── 独立模块，可在前两个阶段之后实施
  └── 测试验证：定时任务是否正常执行，通知是否正常发送

第四阶段：修复五（条件单创建时机控制）
  └── 依赖修复一（限价单改造），需先完成限价单改造
  └── 测试验证：限价单成交确认后条件单被创建，超时未成交不创建条件单
```
