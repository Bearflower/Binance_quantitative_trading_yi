## 2. 背景与问题

### 2.1 现象

用户报障原文：

> "为什么 ai-tuner 每个月会跑一个月度资金分配，新币做空的分配资金只有 156.33 USDT，为什么现在新币做空策略的持仓已经有 249 USDT，这个已经造成风险了。"

### 2.2 机制现状（已确认）

月度资金分配链路：

```
ai_tuner/allocation/monthly_job.py      # 月度调度（每天 09:30 执行，代码内判断是否月末最后一天）
  → ai_tuner/allocation/allocation_calculator.py   # 按当月已实现 PnL 排名计算分配比例
  → ai_tuner/allocation/config_updater.py          # 写入三处（见下）
```

`config_updater` 写入的三个目标位置（`ai_tuner/allocation/config_updater.py:45-99`）：

| 序号 | 写入目标 | 说明 |
|------|---------|------|
| 1 | DB 表 `public.capital_allocation` | 单一真相来源，字段：`month, total_capital, strategy_count, is_first_month, entries(JSON), status, created_at` |
| 2 | `ai_tuner/config.yaml` 的 `capital_limits` | **非挂载卷**，容器重建即丢失 |
| 3 | 各策略 `config.yaml` 的 `capital_limits{monthly_limit, allocated_ratio, allocation_month, updated_at}`，并同步写 `position_sizing.total.account_ratio_cap` | 部署 tar 解压时会整体覆盖 |

### 2.4 失效链路："分配金额写入了，但完全没生效"

```
① 09-11 14:09  分配成功 → DB 写入 ✓ / ai_tuner/config.yaml 写入 ✓ / 4 个策略 config.yaml 写入 ✓
                    （服务器存在备份文件为证：
                     strategies/{btc_eth,btc_eth_aggressive,hrs,new_coin}/config.yaml.backup.20260911_14092x）
② 后续某次部署   tar 解压整体覆盖 config.yaml → capital_limits 字段被擦除 ✗
③ 当前状态       服务器与本地仓库的这 4 个策略配置均无 capital_limits 字段 ✗
                 （本地仓库 strategies/new_coin/config.yaml 从未提交该字段）
④ 运行时读取     CapitalManager.get_allocated_capital() 返回 None
                 → can_open_position() 直接放行，不做任何限额判断（fail-open）✗
⑤ 限额兜底       get_total_margin_limit() 回退到静态 trading.total_position_margin_limit
                 （strategies/new_coin/config.yaml:87 = 150），但口径又被混用（见 2.5 根因 2）
⑥ 占用统计       position_tracking 重启后 entry_quantity/entry_price 未恢复
                 → 占用被记为 0，限额判断形同虚设 ✗
⑦ 重复开仓       PATHUSDT 被重复开仓 3 次，无同币种去重拦截 ✗
⑧ 上报口径       策略按每仓固定 50 上报 → 看板显示 150，与真实 249.30 不符 ✗
```

**核心结论**：这不是"分配算错了"，而是**"分配结果没有任何一条通路能真正约束实盘开仓"**。修复对象是「限额的持久化、读取、口径、统计、去重、上报」整条执行链，而非分配算法。

### 2.5 六个根因汇总

| 编号 | 根因 | 后果 | 对应需求 |
|------|------|------|---------|
| 根因 1 | **部署覆盖**：`config.yaml` 被 tar 整体覆盖，AI 写入的 `capital_limits` 被擦除；`ai_tuner/config.yaml` 非挂载卷，容器重建即丢失 | 限额配置在部署后消失 | R2 |
| 根因 2 | **口径混用**：`can_open_position(名义值, 名义值)` 与 `get_total_margin_limit()` 用同一笔 `monthly_limit` 分别按「名义值」「保证金」两种口径校验 | 同一额度被重复放大，语义不一致（杠杆 2 倍） | R3 |
| 根因 3 | **内存态 `position_tracking` 不可靠**：重启只恢复 `algo_ids`，不恢复 `entry_quantity/entry_price`；且以 symbol 为 key，重复开仓只覆盖不累加 | 占用被记为 0，限额判断失效 | R4 |
| 根因 4 | **幽灵配置**：`trading.max_positions: 3` 在全项目代码中无任何引用 | 最大持仓数完全无效 | R5 |
| 根因 5 | **同币种重复开仓无拦截**：PATHUSDT 被重复开仓 3 次（合计 21.99 张），本地表只留 1 条 7.33 张 | 单币种风险无限放大，DB 与实际持仓不一致 | R6 |
| 根因 6 | **上报口径错误**：开仓占用按每仓固定 50 上报，与真实占用不符 | 看板 / 策略核算全部失真 | R7 |

## 3. 目标

### 3.1 一句话目标

**让月度资金分配额度成为实盘开仓的硬约束：任一时刻，任一策略的真实占用保证金不得超过其当月分配额；且该约束在部署、重启、异常、重复信号等所有场景下都不可绕过、可验证。**

### 3.2 量化验收标准

| 编号 | 验收标准（可测量） | 验证方式 |
|------|------------------|---------|
| AC-1 | 任一时刻，`new_coin` 真实占用保证金 = Σ(每仓 \|positionAmt\| × markPrice × contractSize / leverage) ≤ 生效限额（DB 月度额优先，见 R2/R3） | 采集币安 `positionRisk` 计算并比对 |
| AC-2 | 部署完成后，`docker exec trading_system-new_coin` 内可读取到当月分配额（无论来源为 DB 或 config），且与 DB `public.capital_allocation` 一致 | 部署后读取 + 对比 DB |
| AC-3 | 策略容器重启后，`position_tracking` 中每个持仓币种的 `entry_quantity/entry_price` 与交易所真实值一致（偏差 ≤ 数量精度 `step_size`） | 重启前后对比 `positionRisk` |
| AC-4 | 同一币种在已有持仓（交易所真实持仓或本地记录任一存在）时，第二次开仓信号被 100% 拒绝，且产生一条中文日志 + 一条飞书通知 | 构造重复信号测试 |
| AC-5 | `max_positions` 幽灵配置已清除：全项目 `grep "max_positions"` 在 `new_coin` 段零引用（该配置已删除），持仓规模由保证金限额唯一约束（见 R5） | 代码检测 |
| AC-6 | 策略上报的 `trading.strategy_open_positions` 各币种 margin 之和，与真实占用保证金误差 ≤ 1%（或 ≤1 USDT，取较大值） | 对比看板与 `positionRisk` |
| AC-7 | 超限拒绝开仓时，日志与飞书通知中包含：策略、币种、当前占用、本次新增、限额、拒绝原因 | 日志/通知内容检查 |
| AC-8 | 全项目 `grep "max_positions"` 的引用数与配置声明一致（无幽灵配置）；全项目无硬编码阈值 | 代码检测 |

### 3.3 非目标（本次不做）

1. 不修改月度资金分配算法（排名 / 比例 / 收益率计算口径保持不变）。
2. 不改变 `new_coin` 的交易策略信号逻辑（评分、形态、止盈止损参数不变）。
3. 不引入新的资金分配维度（如按币种分配）。
4. 不重构 `grid` 策略（不参与月度分配）。

## 4. 术语与口径定义

> 本章为强制统一口径，后续所有代码、配置、看板、报表均以此为准，避免再次出现"一个词两种解释"。

| 术语 | 定义 | 计算式 |
|------|------|--------|
| **月度分配额 / `monthly_limit`** | 月度资金分配系统给某策略的当月可用**本金（保证金）**额度，单位 USDT | DB `capital_allocation.entries[*].allocated_amount` |
| **名义价值（Notional）** | 持仓的合约面值合计 | `Σ(\|positionAmt\| × markPrice × contractSize)` |
| **占用保证金（Margin）** | 持仓实际占用的本金 | `Σ(\|positionAmt\| × markPrice × contractSize) / leverage`（PM 账户 `positionRisk` 不返回 `initialMargin` 时的估算式；`contractSize` 缺失按 1 估算并标记 `estimated`） |
| **分配比例 `allocated_ratio`** | 该策略占本月总资金的占比 | DB `entries[*].allocated_ratio` |
| **真实持仓** | 币安交易所返回的持仓（`positionAmt < 0` 视为空头） | `GET /papi/v1/um/positionRisk` |
| **本地记录** | 策略内存/DB 中的持仓记录 | `position_tracking`、`self.positions`、`new_coin.orders`、`new_coin.short_positions`、`condition_orders` |
| **条件单** | 挂单在交易所的止损/止盈算法单（`algoId`） | `condition_orders` 表 / `position_tracking[symbol]['algo_ids']` |

**口径铁律（禁止违反）**：

1. `monthly_limit` 的语义唯一，即**占用保证金上限（本金口径）**。
2. 任何一次开仓判断，**只能使用一种口径**（本需求统一为保证金口径），禁止对同一笔额度同时按名义值与保证金各校验一次。
3. 名义值与保证金之间必须通过 `leverage` 转换，`leverage` 只能从配置读取（`strategies/new_coin/config.yaml:83`），禁止写死 2。

### 4.1 统一口径的公共实现（`shared/position_baseline.py`）

保证金口径与基线重建的唯一实现来源，被 R3（限额校验）、R4（基线重建）、R7（占用上报）共同复用；`btc_eth` / `btc_eth_aggressive` / `new_coin` 等策略共用，禁止在调用方重复实现口径。

| 名称 | 类型 | 职责 |
|------|------|------|
| `calc_position_margin(position_amt, mark_price, contract_size, leverage)` | 函数 | 单仓占用保证金：`\|positionAmt\| × markPrice × contractSize / leverage`；无效入参返回 0.0，`leverage ≤ 0` 返回 0.0 |
| `calc_occupied_margin(positions, leverage)` | 函数 | 策略总占用保证金：Σ 单仓保证金，同币种多仓累加不丢数 |
| `calc_graded_positions_margin(...)` | 函数 | 分档持仓的占用保证金计算（配合分评分档仓位统计） |
| `check_entry_within_limit(strategy, symbol, signal, leverage)` | 异步函数 | 开仓限额校验唯一入口：占用 + 新开仓保证金 ≤ 生效限额 |
| `build_contract_size_map(exchange_info)` | 函数 | 从 `exchangeInfo` 构建 `{symbol: contractSize}` 映射 |
| `build_short_positions(...)` | 函数 | 从交易所持仓构建做空持仓集合（`positionAmt < 0`，空列表视为零持仓） |
| `rebuild_from_exchange(client, leverage, contract_size_map)` | 异步函数 | 启动时从交易所 `positionRisk` 重建持仓基线，返回 `BaselineRebuildResult` |
| `RebuiltPosition` / `BaselineRebuildResult` | 数据类 | 基线重建的单仓结果 / 汇总结果（含 `estimated_*` 估算标记与 `success`） |

限额优先级链与生效值由 `shared/capital_manager.py` 的 `get_effective_margin_limit()`（唯一对外限额入口）提供，见 R2/R3。

### R1 止血：PATHUSDT 超限减仓

**需求描述**
立即对 `PATHUSDT` 空头减仓，使 `new_coin` 的真实占用保证金回落到当月分配额 156.33 USDT 以内。

**减仓量计算（基于 2.3 实测数据）**

| 项目 | 值 |
|------|-----|
| 当前占用保证金 | 249.30 |
| 目标上限 | 156.33 |
| 需释放保证金 | 249.30 − 156.33 = 92.97 |
| 需释放名义价值 | 92.97 × 2 = 185.94 |
| PATHUSDT 当前数量 | 21.99 张（3 × 7.33） |
| PATHUSDT 当前名义 | 297.96 |
| **决策：平掉超出的 2 份 = 14.66 张** | 剩余 7.33 张 |
| 减仓后名义合计 | 101.03 + 99.62 + (297.96 × 7.33/21.99 ≈ 99.32) = **299.97** |
| 减仓后占用保证金 | 299.97 / 2 = **149.99 ≤ 156.33** ✓ |

**触发条件**
一次性人工执行（不设自动触发），执行前需完成前置快照。

**预期行为**

1. 执行前快照（强制，用于回滚与审计）：
   - 记录当前 `positionRisk`（三仓的 `positionAmt`、`markPrice`、名义、估算保证金）；
   - 记录 `new_coin` 各币种在 `condition_orders` / 交易所 open algo orders 中的全部 `algoId`；
   - 记录减仓前 `totalMarginBalance`、`availableBalance`。
2. 减仓操作本身：
   - 对 `PATHUSDT` 下 **BUY** 单，数量 **14.66 张**，`reduceOnly = true`，确保只减仓不反向开多；
   - 禁止使用会翻转净持仓的下单方式；执行时以交易所返回的实时 `positionAmt` 二次校准数量（若与 21.99 不一致，以实时值为准按比例重算）。
3. 条件单处理（**关键，防孤儿单**）：
   - 减仓前/后必须梳理 `PATHUSDT` 的条件单集合，**仅保留与新仓位大小匹配的一份条件单**（止损 7.33 张对应的 SL/TP），其余 2 份对应的条件单全部**显式取消**（调用现有取消逻辑，静默错误码 `cleanup_silent_error_codes: [-2022, -2011]`，见 `strategies/new_coin/config.yaml:200`）；
   - 减仓完成后必须复核：交易所已无指向 PATHUSDT 的孤儿条件单。
4. **不得影响其余两仓**（强制）：
   - 减仓操作**只允许**针对 `PATHUSDT`，禁止对 `AMCUSDT`、`APLDUSDT` 做任何下单/撤单操作；
   - 减仓前后对比 `AMCUSDT`、`APLDUSDT` 的 `positionAmt` 与条件单集合，必须完全一致。
5. 执行后校验（回填证据）：
   - 重新采集 `positionRisk`，确认占用保证金 ≤ 156.33；
   - 确认 `PATHUSDT` 仅剩 7.33 张，且对应条件单齐全（SL 存在、TP1/TP2 视策略规则）；
   - 记录到事故处置记录。

**边界与异常处理**

| 场景 | 预期行为 |
|------|---------|
| 实时 `positionAmt` ≠ 21.99 | 以实时值为准重算减仓量（保持"剩余 1 份"目标），不按固定 14.66 硬下单 |
| 减仓单部分成交 | 轮询成交状态；未成交部分按配置重试（对齐 `trading.close_position.max_retries/retry_interval`），最终仍不满足则告警人工介入 |
| 减仓后跌破下限（减多了） | 立即告警，人工评估是否补回；**禁止**用自动化脚本自动回补 |
| 行情剧烈波动 | 暂停执行，等待波动收敛；分批小额执行，降低滑点 |
| 交易所拒单（reduceOnly 冲突等） | 记录完整请求/响应，告警人工处理，不静默重试 |

**涉及位置**

- 数量精度：`strategies/new_coin/executor.py:427-...`（`_get_symbol_precision`）。

### R2 `capital_limits` 持久化（部署与容器重建后不得丢失）

**需求描述**
月度分配写入的限额配置，在**任何一次部署、任何一次容器重建**之后都必须依然可用，且与 DB 中的当月分配记录保持一致。

**触发条件**

- 每次月度分配写入后；
- 每次部署（tar 解压覆盖 `config.yaml`）后；
- 每次 `ai-tuner` / `new_coin` 容器重建后。

**候选方案对比**

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| **A. 本地仓库同步该字段** | 把 `capital_limits` 提交到 git | 实现最简单 | 每月都要重新提交一次；历史值污染仓库；月末自动分配时本地值仍为旧值，无法覆盖自动写入；极易遗漏 | 不采用 |
| **B. 部署脚本排除该文件** | 解压时跳过 `strategies/*/config.yaml` | 不再覆盖 | 代码侧新增/变更默认配置项无法下发；需长期维护排除清单；后端 `ai_tuner/config.yaml` 非挂载卷问题未解决 | 仅作辅助 |
| **C. 部署后由 ai-tuner 重新应用** | 部署完成后触发一次 reapply | 保证与 DB 一致 | 依赖部署流程编排；从"部署完成"到"reapply 完成"存在限额缺失窗口；`ai_tuner/config.yaml` 本身也会丢 | 仅作辅助 |
| **D. 运行时从 DB 读取（推荐）** | 策略开仓前查 `public.capital_allocation` 当月 `active` 记录的 `entries[*].allocated_amount` | **单一真相来源**；部署永不擦除；自动分配天然生效；无需人工同步 | 依赖 DB 可用性，需设计降级 | **推荐（主方案）** |

**推荐方案（D）的完整设计**

1. **真相来源**：DB 表 `public.capital_allocation`，取 `month = 当前月` 且 `status = 'active'` 的记录中，`entries`（JSON 数组）里 `strategy_id` 匹配的 `allocated_amount`。
2. **读取位置**：扩展 `shared/capital_manager.py`（新增 DB 读取能力）。**已实现**：对外新增异步入口 `get_effective_margin_limit()`（唯一限额入口，返回 `(限额, 来源)`）与 DB 查询 `_query_db_allocation()`；旧的同步 `get_allocated_capital()` / `get_total_margin_limit()` / `can_open_position()` 保留但打废弃告警，策略逐步迁移到新入口。
3. **降级链路（优先级从高到低）**：

   | 优先级 | 来源 | 说明 |
   |-------|------|------|
   | 1 | DB `public.capital_allocation` | 当月 active 记录中本策略条目的 `allocated_amount`（主来源，唯一真相来源） |
   | 2 | 本策略 `config.yaml` 的 `capital_limits.monthly_limit` | 兜底（部署后可能缺失） |
   | 3 | 本策略 `config.yaml` 的 `trading.total_position_margin_limit` | 静态兜底（如 `new_coin` = 150） |
   | 4 | 三级均不可用 | **fail-open（已拍板，决策 D2）**：放行开仓并记录告警日志，不阻断策略主循环 |

   > **取第一个可用值，不做 `min`**：月度额代表当月真实分配额度，必须优先于静态兜底生效，否则月度分配会被固定兜底值压制（如 `new_coin` 月度额 156.33 被静态 150 压制）。实现见 `shared/capital_manager.py::get_effective_margin_limit()`。

4. **缓存与故障处理**：
   - DB 查询结果按 TTL 缓存（TTL 从配置读取，禁止硬编码），避免每笔开仓都查库；
   - DB 查询失败时：沿用**最近一次成功读取的值**（内存缓存），并发送告警；
   - DB 与缓存均无值时，按降级链路继续，并记录中文日志说明当前生效来源。
5. **配置兜底**：建议同时采用方案 B 作为**双保险**（部署脚本不覆盖各策略 `config.yaml`），但**不得**因此取消 DB 主来源地位。
6. **`ai_tuner/config.yaml` 容器重建丢失问题**：
   - 将其纳入挂载卷（volume），或改造为**部署/启动时从 DB 重建**；
   - 明确：`ai_tuner/config.yaml` 中的 `capital_limits` 仅供 ai-tuner 自身展示/审计，**不得**作为策略限额的读取来源。
7. **一致性校验**：每次读取后可输出一条日志（当前生效来源、额度、分配月份），便于部署后核对 AC-2。

**边界与异常处理**

| 场景 | 预期行为 |
|------|---------|
| DB 无当月记录（尚未分配） | 按降级链路取配置兜底值；若也无，则按第 4 优先级处理 |
| DB 当月记录存在但该 `strategy_id` 不在 `entries` 中 | 视为无分配，走降级链路并告警 |
| 分配月份过期（`month` 早于当前月） | **不回退上月额度（已拍板，决策 D1/D3）**：查询仅匹配「当前月 + `status='active'`」，取不到即按降级链路走 ②→③，最终可能 fail-open，并记录告警日志 |
| 配置与 DB 值不一致 | **以 DB 为准**（月度额优先于静态兜底），并记录一条差异告警（含两个值），便于发现同步问题 |
| DB 连接超时/异常 | 沿用最近一次成功读取的分配额（来源标记 `db_stale`）；无缓存则降级；全程不抛异常中断策略主循环 |

**涉及位置**

- `shared/capital_manager.py`（新增 `get_effective_margin_limit` / `resolve_monthly_limit` / `can_open_within_limit` / `get_min_position_margin` / `_query_db_allocation`；`_get_nested_float` / `_read_config` 复用现有配置读取）。
- `ai_tuner/allocation/config_updater.py:101-167`（`_save_to_db`）→ 确认 DB schema 与读取查询字段一致；`:169-257`（`_update_tuner_config`）、`:259-383`（`_update_strategy_configs`）→ 明确"config 仅为兜底/审计"。
- 部署脚本（`one_click_deploy.sh` 及相关打包脚本）→ 可选双保险 B。
- `docker-compose.yml` → `ai_tuner/config.yaml` 挂载卷。

**验收标准**：AC-2。

### R3 限额口径统一（保证金口径）

**需求描述**
统一限额判断口径为**占用保证金**，与 `monthly_limit` 的资本语义对齐；禁止同一笔额度被两种口径重复校验。

**现状核对（必须理解后再改）**

`strategies/new_coin/executor.py:223-256` 存在两处并存检查：

| 位置 | 现有实现 | 口径 | 问题 |
|------|---------|------|------|
| `executor.py:223-238` | `capital_mgr.can_open_position(名义, 名义)` | **名义值** | `can_open_position`（`shared/capital_manager.py:121-151`）将参数与 `monthly_limit` 直接比较，等于要求 `名义 ≤ monthly_limit`，把本金额度当成了名义额度 |
| `executor.py:240-256` | `current_positions_value / leverage` 对比 `get_total_margin_limit()`（同返回 `monthly_limit`） | **保证金** | 把同一个 `monthly_limit` 当作保证金上限，等价于允许 `名义 ≤ monthly_limit × leverage` |

同一笔 156.33 额度，在两处分别被解释为「名义 156.33」和「保证金 156.33（= 名义 312.66）」，**两种口径指向的价值相差 2 倍（杠杆 = 2）**，语义自相矛盾，无法判断真实约束，也不会随杠杆变化自动保持一致。

> 实现备注（供开发核对）：两处为 AND 关系（任一失败即拒绝），因此**当前实际生效的是其中较紧的一侧**；由于根因 1 导致 `capital_limits` 缺失、根因 3 导致占用为 0，两处检查实际上都未起到作用。本需求要求**删除歧义根源**，而非仅调整某一侧。

**统一后的明确规定**

1. 对外只保留**一个**限额判断入口，口径为**保证金**：
   ```
   占用保证金 = Σ(|positionAmt| × markPrice × contractSize) / leverage
   允许开仓 ⟺ 占用保证金 + 新开仓保证金 ≤ 生效限额
   新开仓保证金 = 新开仓名义 / leverage
   生效限额 = 优先级链取第一个可用值（DB 月度额 → config monthly_limit → 静态兜底）
   ```
2. `leverage` 一律从配置读取（`strategies/new_coin/config.yaml`），禁止写死。
3. 删除 `can_open_position` 中"名义直比 `monthly_limit`"的语义，`shared/capital_manager.py` 对外只有一种解释：新增 **`get_effective_margin_limit()`（唯一限额入口）** 与 **`can_open_within_limit(occupied, new)`**，旧的 `get_allocated_capital()` / `get_total_margin_limit()` / `can_open_position()` 保留仅为兼容未改造调用方，调用时打废弃告警。
4. `trading.total_position_margin_limit` 作为**静态兜底**（第三优先级），**不与 `monthly_limit` 取 `min`**；月度额可用时**月度额优先**（取第一个可用值）。二者均为保证金口径。
5. 单笔仓位大小（`single_position_margin=50`）必须与分配额度联动：当剩余可用额度不足以容纳一个完整单笔仓位时，**按剩余额度缩小仓位**；缩仓后保证金 < `trading.min_position_margin`（`new_coin` = 25.0）则**拒绝开仓**（已拍板，决策 D4；实现见 `CapitalManager.get_min_position_margin()`），**禁止**"分配多少都不影响单笔仓位"的现状。

**触发条件**

每次开仓信号到达时，在执行下单前统一校验。

**预期行为**

- 校验失败：拒绝开仓，返回具体原因（含当前占用、新增、限额），写中文日志 + 飞书通知；
- 校验通过：仅此一次判断即可，不再有第二处口径不同的检查；
- 所有数值（`leverage`、`monthly_limit`、`total_position_margin_limit`）均来自配置/DB，日志中打印生效值便于审计。

**边界与异常处理**

| 场景 | 预期行为 |
|------|---------|
| 已超限（存量仓位使占用 > 限额） | 拒绝一切新开仓，仅允许减仓；发送超限告警（原因文案 `总持仓保证金超限(占用/限额)`） |
| `leverage` 配置缺失 / ≤ 0 / 非数值 | **已实现**：`strategies/new_coin/executor.py` 不再 `get('leverage', 2)` 猜测，直接 `logger.error` + 置 `_leverage_valid=False`，`execute_short` 据此**拒绝开仓**并告警（R3 边界） |
| `monthly_limit` 与 `total_position_margin_limit` 不一致 | **月度额优先（取第一个可用值，不做 min）**，并记录 `月度额与静态兜底不一致，月度额优先` 差异日志 |
| PM 账户无法获取精确 `initialMargin` | 用 `|positionAmt| × markPrice × contractSize / leverage` 估算（见 R4），统一使用 `shared/position_baseline.py` 同一估算函数，避免多处口径不一 |

**涉及位置**

- `strategies/new_coin/executor.py`（两处检查合并为一处；`leverage` 严格校验）。
- `shared/capital_manager.py`（`get_effective_margin_limit` / `resolve_monthly_limit` / `can_open_within_limit` / `get_min_position_margin`；旧的 `get_total_margin_limit` / `can_open_position` 标注废弃）。
- `shared/position_baseline.py`（`calc_position_margin` / `calc_occupied_margin` / `check_entry_within_limit`）。
- `strategies/new_coin/config.yaml`（`leverage` / `single_position_margin` / `min_position_margin` / `total_position_margin_limit`）。

**验收标准**：AC-1、AC-7；并需验证"同一笔额度不再被放大 2 倍"（配置 `leverage=2` 时，`monthly_limit=156.33` 允许的名义上限为 312.66，而非 156.33 或 625.32）。

### R4 持仓基线重建（重启后占用计算正确）

**需求描述**
策略启动/重启时必须从交易所重建 `position_tracking` 的持仓基线（`entry_quantity` / `entry_price` / 占用），确保占用计算不因重启而失真。

**现状核对**

`strategies/new_coin/strategy.py:1526-1562` 在恢复状态时，**只从 `condition_orders` 表恢复 `algo_ids`**，恢复的条目结构为 `{'algo_ids': {}}`，**不含** `entry_quantity` / `entry_price`。而占用计算 `strategies/new_coin/executor.py:224-228` 依赖这两个字段：

```python
for _, track in self.position_tracking.items():
    pos_qty = track.get("entry_quantity", 0)
    pos_price = track.get("entry_price", 0)
    current_positions_value += float(pos_qty) * float(pos_price)
```

因此重启后 `entry_quantity/entry_price` 缺失 → 占用累加为 0 → 限额判断形同虚设。

**触发条件**

- 策略启动时；
- 容器重启后；
- 周期性复核（建议每个持仓巡检周期，与现有状态保存周期一致，周期从配置读取，禁止硬编码）。

**预期行为**

1. 启动时调用交易所 `GET /papi/v1/um/positionRisk`（`new_coin` 已有调用先例，见 `strategies/new_coin/strategy.py:1658-1671`），对每个 `positionAmt < 0` 的币种：
   - 若本地 `position_tracking[symbol]` 已存在且字段完整 → 保留本地 `entry_price`（更准确）；
   - 若缺失 → 用交易所可用字段重建：
     - `entry_price` 优先取交易所返回的 `entryPrice`；若不可用则取当前 `markPrice` 作为近似，并记录告警（标记为估算值）；
     - `entry_quantity` 取 `|positionAmt|`（绝对值）；
     - 写入占用相关派生字段（名义 / 保证金）。
2. **占用计算函数唯一化**：抽取一个公共函数 `calc_occupied_margin(positions, leverage)`（或等价方法），R3、R4、R7 全部复用，禁止多处重复实现（遵守"禁止重复代码"）。
3. **PM 账户不返回 `initialMargin` 的处理（明确写死规则）**：
   - 统一使用 `占用保证金 = 名义 / leverage` 估算；
   - 名义 = `Σ(|positionAmt| × markPrice × contractSize)`（`contractSize` 若接口不返回，从交易对精度信息获取或按 1 处理并记录）；
   - 估算逻辑集中在一处，日志中标注 `estimated=true`，便于看板区分"精确值 / 估算值"；
   - 若后续交易所接口可提供 `initialMargin`，则优先使用真实值（预留分支）。
4. **同币种多仓不丢数**：`position_tracking` 以 `symbol` 为 key，重复开仓会覆盖而非累加（根因 3 的附带问题）。要求改为**以"币种 + 持仓序号"为唯一键**，或对同币种多份仓位做**累加**，确保占用统计不丢数。与 R6（禁止重复开仓）配合：R6 生效后同币种应为单份仓位，但仍需保证历史遗留多仓在统计上不丢数。
5. **恢复后可观测**：启动日志必须打印每个持仓币种的重建结果（`symbol`、`entry_quantity`、`entry_price`、来源=本地/交易所、是否估算）。
6. **基线同步回 `position_tracking`（已实现，满足 AC-3）**：新增 `strategies/new_coin/strategy.py::_sync_baseline_to_tracking(executor, rebuilt)`。基线重建后，把每个持仓币种的 `entry_price` / `entry_quantity` / `entry_time` 同步写入 `executor.position_tracking`，并**保留已有 `algo_ids` / `atr`**（不覆盖条件单与动态止损状态）。此举修复「重启后占用被记为 0 → 在已有占用之上继续满额度开仓」的资金安全缺口，确保重启后 `position_tracking` 与交易所持仓一致。
7. **基线未就绪期间禁止开仓（已实现）**：`executor.baseline_ready` 初值由 `True` 改为 **`False`**（与注释语义一致）；基线重建成功前保持 `False`，开仓前置检查据此拒绝开新仓（仅允许减仓）。

**边界与异常处理**

| 场景 | 预期行为 |
|------|---------|
| 交易所接口失败 | 保留本地已有基线；无本地基线的币种标记为"未知占用"，并按**保守策略**处理（视为已占用满额，禁止新开仓）并告警 |
| 交易所返回 `positionAmt = 0` | 视为无持仓，清理该币种 `position_tracking` 与占用 |
| 本地与交易所数量不一致（如 DB 只留 7.33、实际 21.99） | **以交易所为准**；记录一致性告警；修复 DB 记录（`new_coin.orders` / `short_positions`）使其与实际一致 |
| `markPrice` 缺失 | 回退到最新 K 线收盘价（K 线服务本地缓存，禁止在服务器跑回测），仍缺失则该仓占用按"未知"保守处理 |
| 重建过程中策略主循环 | 重建完成前**禁止开新仓**（仅允许减仓），避免用不完整基线做判断 |

**涉及位置**

- `strategies/new_coin/strategy.py:1490-1562`（`_restore_state` / 恢复逻辑）→ 增补持仓基线重建。
- `strategies/new_coin/strategy.py:1658-1671`（`positionRisk` 调用）→ 抽取为公共方法复用。
- `strategies/new_coin/executor.py:224-228`（占用累加）→ 改为调用统一计算函数。
- `strategies/new_coin/executor.py:2283-2400`（`clear_position_tracking` / `replenish_conditional_orders` 一带）→ 与基线重建保持一致。

**验收标准**：AC-3、AC-1。

### R5 `max_positions` 废弃删除（幽灵配置清理）

**需求描述**
`trading.max_positions` 在全项目代码中无任何引用（幽灵配置），使"最大持仓数"完全无效。本次**已拍板采用废弃删除方案（决策 D5）**：直接删除该配置，消除幽灵配置，持仓规模由保证金限额唯一约束；不得保留"配置存在但无代码引用"的状态。

**拍板结论（已实现）**

- **已删除** `strategies/new_coin/config.yaml` 中的 `trading.max_positions`（仅 new_coin 段；`grid` 段保留，`hrs` 段保留——其被 `hrs_adapter.py` 用作回撤基数）。全项目 `grep "max_positions"` 在 new_coin 段零引用。

- 静态兜底值：`total_position_margin_limit` —— `btc_eth` 210 / `btc_eth_aggressive` 210 / `hrs` 110 / `new_coin` 150（USDT）。

**触发条件**

收到新币种/同币种开仓信号时，由 R3 限额校验与 R6 判重统一拦截（不再有独立的持仓数校验）。

**预期行为**

- 占用保证金已达生效限额：拒绝新开仓，返回原因 `总持仓保证金超限(占用/限额)`，写中文日志 + 飞书通知；
- 额度允许且币种无持仓：正常开仓；
- 平仓/全平后，占用随之下调（以 R4 的交易所真实持仓基线为准）。

**边界与异常处理**

| 场景 | 预期行为 |
|------|---------|
| 分批次止盈后仍持仓（部分平仓） | 该币种占用按剩余数量重算，不重复计入 |
| 单币种多份历史遗留仓位 | 占用**累加不丢数**（见 R4），配合 R6 清理，不重复放大风险 |
| 决定废弃该配置（本次采用） | **已完成**：删除 `config.yaml` 中的 `max_positions` 及注释，`grep` 在 new_coin 段结果为零；替代约束为生效保证金限额（R3） |

**涉及位置**

- `strategies/new_coin/config.yaml`（已删除 `max_positions`；保留 `min_position_margin` / `duplicate_symbol_notify_window_seconds` 等）。
- `strategies/new_coin/strategy.py` / `executor.py`（开仓前置检查：R3 限额 + R6 判重，替代原持仓数校验）。

**验收标准**：AC-5（幽灵配置已清除）、AC-8。

### R6 同币种禁止重复开仓

**需求描述**
同一币种不得重复开仓。开仓前必须同时检查**交易所真实持仓**与**本地记录**，两者取并集判断；只要任一存在该币种持仓，即拒绝新的开仓信号。

**触发条件**

每个开仓信号到达时、执行下单前（与 R3 校验同一入口，顺序：先判重，再判额度）。

**预期行为**

1. 判重数据源（取并集，任一命中即视为"已持仓"）：

   | 来源 | 读取方式 |
   |------|---------|
   | 交易所真实持仓 | `GET /papi/v1/um/positionRisk`，`positionAmt < 0` 的 `symbol` 集合 |
   | 内存跟踪 | `position_tracking` 的 key 集合 |
   | 策略持仓 | `self.positions` 的 key 集合 |
   | 数据库记录 | `new_coin.orders` / `new_coin.short_positions` 中未平仓记录 |

2. 命中"已持仓" → **拒绝开仓**，返回原因"该币种已有持仓，禁止重复开仓"，并：
   - 写中文日志（含 `symbol`、交易所持仓数量、本地记录来源）；
   - 发送飞书通知（降频，避免刷屏：同一 `symbol` 在配置的时间窗口内只通知一次，窗口从配置读取）。
3. 若发现"交易所已持仓但本地无记录"（如 PATHUSDT 场景）→ 除拒绝外，额外触发**一致性修复告警**（提示本地记录缺失），并纳入 R4 的基线重建。
4. 判重成功（该币种无任何持仓）→ 进入 R3 额度校验。

**边界与异常处理**

| 场景 | 预期行为 |
|------|---------|
| 交易所接口失败 | 以本地记录为准（并集降级）；若本地也无记录，按**保守策略**拒绝该币种开仓并告警（宁可漏开不可重开） |
| 持仓刚被条件单全部平掉、交易所尚未刷新 | 以交易所为准；允许在下一轮信号重试，不做强制延迟 |
| 本地记录残留（已平仓未清理） | 优先以交易所为准判定"无持仓"；同时清理本地残留记录并告警 |
| 手工/人工介入导致的多仓 | 判重逻辑同样生效；仅允许通过 R1 类减仓操作调整 |

**涉及位置**

- `strategies/new_coin/executor.py:223` 之前（开仓前置检查区）→ 新增判重检查。
- `strategies/new_coin/executor.py:153`（`position_tracking` 初始化）、`:2283-2285`（`clear_position_tracking`）。
- `strategies/new_coin/strategy.py:1658-1671`（`positionRisk` 调用）→ 抽取复用。
- 通知：`shared/notification.py`（飞书）。

**验收标准**：AC-4。

### R7 占用上报口径修正

**需求描述**
策略上报 `trading.strategy_open_positions` 的保证金必须为**真实占用**，与 R3 口径一致，使看板与策略自身核算正确。

**现状核对**

`strategies/new_coin/strategy.py:1639-1673`（`_sync_open_positions_to_db`）：每个持仓币种的 `margin` 直接取配置 `single_position_margin`（默认 50），与真实占用无关。因此当前三仓上报合计 = 3 × 50 = **150**，而真实占用为 **249.30**（看板 `open_margin=249.28` 来自另一通路，两处口径同样需要统一）。

**预期行为**

1. 上报字段计算统一调用 R4 的公共函数：
   - `margin = |positionAmt| × markPrice / leverage`（真实占用，估算场景标注 `estimated`）；
   - `quantity = |positionAmt|`（真实数量，包含同币种累计，禁止只报 1 份）。
2. 每币种一行，合计 = 策略真实占用保证金，与币安 `positionRisk` 计算值误差 ≤ 1%（或 ≤1 USDT，取较大值）。
3. `sync_open_positions` 调用参数与字段语义（`shared/strategy_state.py:77-130`）保持不变，仅修正传入值。
4. 上报失败或数据缺失时：**不得**用固定值（50）填充；应标记为不可用并保留上一有效值，同时告警。

**边界与异常处理**

| 场景 | 预期行为 |
|------|---------|
| `positionRisk` 不可用 | 保留上一有效上报值，标记 `stale`，告警；禁止用固定 50 或 0 覆盖 |
| 部分币种数量获取失败 | 仅缺失币种标记不可用，其余正常上报（不做整表覆盖） |
| 策略无持仓 | 上报空集合，合计 0（正常） |

**涉及位置**

- `strategies/new_coin/strategy.py:1627-1673`（`_sync_open_positions_to_db` 及其注释中的口径说明）。
- `shared/strategy_state.py:77-130`（`sync_open_positions`，确认字段语义后复用）。

**验收标准**：AC-6、AC-1。

## 7. 风险、连带影响与回滚

### 7.1 R1 减仓操作的风险与回滚

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 减仓即实现亏损 | 若 PATHUSDT 当前浮亏，减仓锁定亏损 | 属风险处置的必要成本；执行前评估浮亏金额并记录，避免在极端行情扩大滑点 |
| 市价单滑点 | 实际成交价偏离预期 | 分批小额执行；优先使用限价单 + 滑点容忍（对齐 `limit_order_slippage`） |
| 误伤其他仓位 | 影响 AMCUSDT/APLDUSDT | 强制限定 `symbol=PATHUSDT`；执行前后逐仓对比校验 |
| 孤儿条件单 | 减仓后残留条件单触发，造成误平/反向 | 减仓前梳理 → 仅保留 1 份 → 其余显式取消 → 执行后复核交易所无孤儿单 |
| 减仓过量 | 占用远低于额度，资金闲置 | 以实时 `positionAmt` 二次校准；执行后复核占用 |

**回滚方式（重要）**
减仓是**不可逆的实盘操作**（无法"撤销"成交）。因此回滚方案为：

1. 以"减仓前快照"为基准，人工评估是否需要重新开仓补回；
2. **禁止**自动化脚本自动回补，必须人工确认后按正常开仓流程执行（且受 R2/R3/R4/R6 新约束）；
3. 若误伤其他仓位，立即按"恢复目标仓位"人工处置，并记录事故。

### 7.2 连带影响（必须一并纳入）

`shared/capital_manager.py` 被多个策略共用，改动会影响：

| 策略 | 是否参与月度分配 | 当前 `capital_limits` 状态 | 影响 |
|------|----------------|--------------------------|------|
| `new_coin` | 是 | **已被部署擦除** | 直接受影响（本次主对象） |
| `btc_eth` | 是 | **已被部署擦除** | R2/R3 改动直接影响；同样存在"额度未生效"风险 |
| `btc_eth_aggressive` | 否（与 `btc_eth` 共用分配结果，见 `ai_tuner/allocation/config_updater.py:28-32`） | **已被部署擦除** | 同上 |
| `hrs` | 是 | **已被部署擦除** | 同上 |
| `grid` | 否 | 不涉及 | 不参与分配，无需变更；但 `shared/` 变更仍会导致其容器重建，需回归验证不报错 |

**结论**：
1. R2（持久化）与 R3（口径统一）修复必须**同时覆盖 4 个策略**（`btc_eth` / `btc_eth_aggressive` / `hrs` / `new_coin`），否则只修 new_coin 会让其他策略继续裸奔。
2. `shared/capital_manager.py` 是共享模块，任何接口语义变更（如 `can_open_position` 口径调整）必须**排查全部调用方**，避免误伤。
3. 因 `hrs` 的 Dockerfile 使用 `COPY . /app/`，本次任何项目文件变更都会触发 `hrs-strategy` 重建，部署时需纳入变更范围分析。
4. 部署后必须 `docker ps` 确认**所有**容器在运行（含易遗漏的 `kline-monitor`）。

### 7.3 灰度与验证顺序建议

```
① 本地开发 + 本机测试（禁止服务器回测）
② 先修 R3/R4/R6/R7（代码层，不改变线上持仓）
③ 部署到服务器 → 五层验证（容器/镜像/VERSION/MD5/日志）
④ R1 减仓（人工执行，带快照与复核）
⑤ 验证 AC-1..AC-8
⑥ 观察一个完整巡检周期（确认无重复开仓、占用稳定、上报一致）
```
