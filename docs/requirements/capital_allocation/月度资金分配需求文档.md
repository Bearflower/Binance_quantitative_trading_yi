# 月度资金分配系统 - 需求文档

> **版本**: v1.1
> **创建日期**: 2026-07-14
> **最后更新**: 2026-07-15
> **状态**: 已确认

---

## 1. 功能概述

每月最后一天，统计各主动策略的月度已实现收益率，根据收益率排名动态分配未来一个月各策略的资金使用占比。实现"优胜劣汰"的资金分配机制，让表现最好的策略获得更多资金。

---

## 2. 参与策略

### 2.1 参与分配的策略

| 策略 | 策略ID | 类型 |
|------|--------|------|
| MTPCS 策略 | `btc_eth` | 主动开仓型 |
| 新币做空策略 | `new_coin` | 主动开仓型 |
| HRS 混合反转策略 | `hrs` | 主动开仓型 |

### 2.2 不参与分配的策略

| 策略 | 策略ID | 原因 |
|------|--------|------|
| 网格交易策略 | `grid` | 半自动挂单等待成交的被动型策略，资金长期被占用，收益率波动小，混入排名会扭曲主动策略的优胜劣汰 |

**网格策略保持独立运行**，资金额度单独划拨，不参与每月动态再平衡。

### 2.3 未来新增策略

新增策略（如 Grid 之外的其它主动开仓型策略）如需参与资金分配，必须在 `ai_tuner/config.yaml` 中预先配置以下字段：

```yaml
- strategy_id: "new_strategy"
  name: "新策略"
  # ... 现有字段 ...
  capital_allocation:
    enabled: true                    # 是否参与资金分配
    fallback_ratio: 0.15            # 首月无历史数据时的默认占比
```

未配置 `capital_allocation.enabled: true` 的策略，系统拒绝纳入分配池。

## 3. 分配结构

### 3.1 固定部分

| 项目 | 占比 | 说明 |
|------|------|------|
| 风险备用金 | **10%** | 固定不变，不参与排名分配 |

### 3.2 动态分配部分

主动策略共分 **90%** 的资金，按月度收益率排名分配：

| 排名 | 占 90% 的比例 | 占总资金比例（N=3 时） |
|------|--------------|----------------------|
| 第 1 名 | 40% | 36% |
| 第 2 名 | 30% | 27% |
| 第 3 名 | 20% | 18% |
| 第 4 名 | 10% | 9%（N=4 时） |
| 第 N 名 | 递减权重 | 按排名递减 |

### 3.3 通用权重公式

对于 N 个主动策略，权重序列为递减等差数列：

```
权重 = [40%, 30%, 20%, 10%, ...] 对应排名 1, 2, 3, 4, ...
```

排名第 k 的策略占 90% 中的权重为：`max(10%, 50% - (k-1) × 10%)`

### 3.4 最低保障

**不设硬性最低保障比例**，严格按排名分配。长期垫底的策略自然获得更少资金，体现优胜劣汰。

## 4. 首月初始分配

系统首次运行（无历史收益率数据）时，使用默认基准分配：

| 策略 | 默认占比 |
|------|---------|
| MTPCS 策略 | 30% |
| 新币做空策略 | 40% |
| HRS 混合反转策略 | 20% |
| 风险备用金 | 10% |

**合计** | **100%**

## 5. 收益率计算

### 5.1 计算口径

**只计算已实现 PnL（已平仓盈亏）**，不包含未实现浮盈/浮亏。

**理由**：资金分配决定"下个月能用多少本金去开仓"。如果计入未实现浮盈（账面盈利），可能导致该策略持仓过重、账面浮盈很大，但实际现金没回来，反而占用了下个月本应给其他策略的现金。**现金为王，落袋为安**。

### 5.2 收益率公式

```
月度收益率 = 本月该策略已实现 PnL / 月初分配给该策略的 USDT 金额
```

**分母说明**：使用月初分配给该策略的资金额度，而非总账户余额。这样才能反映该策略"用给它的那笔钱赚了多少钱"，是衡量策略资金使用效率的核心指标。

### 5.3 数据来源

从各策略数据库的交易记录表中，筛选当月已平仓的订单，汇总净利润：

| 策略 | 数据表 | 关键字段 |
|------|--------|---------|
| MTPCS | `btc_eth.trades` | `executed_at`, `price`, `quantity`, `commission` |
| 新币做空 | `new_coin.orders` | `created_at`, `price`, `quantity` |
| HRS | 待确认（需确认 HRS 的交易记录表） | |

### 5.4 平仓识别

- 有明确平仓记录的（如 `btc_eth.trades` 中的完整交易记录）：直接汇总
- 需通过持仓状态变化（`status = 'closed'` 的平仓记录）计算盈亏

## 6. 分配结果生效

### 6.1 生效方式

**限制各策略的最大名义开仓金额（Max Notional）**。

在 `ai_tuner/config.yaml` 中增加动态字段 `capital_limits`，各策略在执行开仓信号时，**累计持有的所有仓位名义价值（面值 × 价格）之和不得超过分配额度**。

### 6.2 开仓检查逻辑

```
计算当前所有持仓的名义价值总和
if (当前名义价值 + 新开仓名义价值) > 分配额度:
   拒绝该开仓信号
else:
   允许开仓
```

### 6.3 额度计算

```
策略分配额度 = 总可用资金 × 该策略分配比例
```

- 总可用资金 = 总账户余额 - 风险备用金
- 风险备用金固定为总资金的 10%

## 7. 数据存储

### 7.1 主存储：数据库表 `capital_allocation`

新建 PostgreSQL 表，记录每月分配历史：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | SERIAL | 主键 |
| `month_date` | DATE | 分配月份（如 2026-07-31） |
| `strategy_id` | VARCHAR(50) | 策略ID |
| `strategy_name` | VARCHAR(100) | 策略名称 |
| `rank` | INTEGER | 本月排名 |
| `monthly_pnl` | DECIMAL(20, 8) | 本月已实现 PnL |
| `monthly_return` | DECIMAL(10, 6) | 本月收益率 |
| `allocated_ratio` | DECIMAL(5, 4) | 下月分配比例（如 0.36 表示 36%） |
| `allocated_amount` | DECIMAL(20, 8) | 下月分配金额（USDT） |
| `created_at` | TIMESTAMP | 创建时间 |

### 7.2 运行时读取：`ai_tuner/config.yaml`

调度器算出结果后，**同时写入** `ai_tuner/config.yaml` 中的 `capital_limits` 字段：

```yaml
capital_limits:
  btc_eth:
    ratio: 0.36        # 36%
    amount_usdt: 3600   # 假设总资金 10000 USDT
  new_coin:
    ratio: 0.27        # 27%
    amount_usdt: 2700
  hrs:
    ratio: 0.18        # 18%
    amount_usdt: 1800
  risk_reserve:
    ratio: 0.10        # 10%（固定）
    amount_usdt: 1000
  total:
    ratio: 1.0
    amount_usdt: 10000
```

数据库用于历史回溯和审计，config.yaml 用于各策略实时读取（避免每次查数据库）。

## 8. 执行时间

| 项目 | 设定 |
|------|------|
| 执行频率 | 每月一次 |
| 执行时间 | **每天 09:30（北京时间 UTC+8），代码内通过 `calendar.monthrange` 判断是否为月末最后一天** |
| 生效时间 | 次月 00:00 起新仓位走新比例 |
| 调度方式 | 与现有周度调度一致的 APScheduler 机制 |

**技术说明**：APScheduler 的 cron 触发器不支持 `last` 关键字（每月最后一天），因此采用"每天 09:30 执行，代码内判断是否为月末最后一天"的方案。非月末自动跳过，月末触发完整流程。

## 10. 数据库表结构

### 10.1 新建表 `capital_allocation`

```sql
CREATE TABLE IF NOT EXISTS public.capital_allocation (
    id SERIAL PRIMARY KEY,
    month_date DATE NOT NULL,                    -- 分配月份
    strategy_id VARCHAR(50) NOT NULL,            -- 策略ID
    strategy_name VARCHAR(100) NOT NULL,         -- 策略名称
    rank INTEGER NOT NULL,                       -- 本月排名
    monthly_pnl DECIMAL(20, 8) NOT NULL DEFAULT 0,  -- 本月已实现 PnL
    monthly_return DECIMAL(10, 6) NOT NULL DEFAULT 0, -- 本月收益率
    allocated_ratio DECIMAL(5, 4) NOT NULL,      -- 下月分配比例
    allocated_amount DECIMAL(20, 8) NOT NULL DEFAULT 0, -- 下月分配金额
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    UNIQUE(month_date, strategy_id)              -- 每月每策略一条记录
);

-- 创建索引
CREATE INDEX idx_capital_allocation_month ON public.capital_allocation(month_date);
CREATE INDEX idx_capital_allocation_strategy ON public.capital_allocation(strategy_id);
```

## 12. 风险与注意事项

1. **数据完整性**：必须确保各策略的交易记录完整准确，特别是已平仓订单的 PnL 计算
2. **时间一致性**：所有时间统一使用 UTC+8（北京时间），避免跨时区问题
3. **首次运行**：首月无历史数据，使用默认基准分配
4. **新增策略**：新增策略必须在 config.yaml 中预设 `fallback_ratio`，否则不纳入分配池
5. **网格策略独立性**：网格策略资金独立，不受月度分配影响
6. **回滚方案**：若月度分配计算失败，应保持上月分配比例不变，并发送告警通知
