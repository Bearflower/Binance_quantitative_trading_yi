# 月度资金分配系统 - 需求文档

> **版本**: v1.2
> **创建日期**: 2026-07-14
> **最后更新**: 2026-09-21
> **状态**: 已确认
> **关联文档**: [策略资金限额强制执行需求文档](./策略资金限额强制执行需求文档.md)（限额执行链，v1.1）

---

## 1. 功能概述

每月最后一天，统计各主动策略的月度已实现收益率，根据收益率排名动态分配未来一个月各策略的资金使用占比。实现"优胜劣汰"的资金分配机制，让表现最好的策略获得更多资金。

---

## 2. 参与策略

### 2.1 参与分配的策略

| 策略 | 策略ID | 类型 |
|------|--------|------|
| MTPCS 策略 | `btc_eth` | 主动开仓型 |
| MTPCS 激进版策略 | `btc_eth_aggressive` | 主动开仓型 |
| 新币做空策略 | `new_coin` | 主动开仓型 |
| HRS 混合反转策略 | `hrs` | 主动开仓型 |

> **激进版独立参与（2026-09-21 变更）**：`btc_eth_aggressive`（MTPCS 激进版）**独立参与**月度资金分配，作为第 4 个参与策略。此前激进版通过 `config_updater` 的 `_SHARED_FUND_MIRROR` 资金镜像共用原版 `btc_eth` 的分配结果，该机制已移除，激进版按自身月度表现独立排名、独立获得分配额度。

### 2.2 不参与分配的策略

| 策略 | 策略ID | 原因 |
|------|--------|------|
| 网格交易策略 | `grid` | 半自动挂单等待成交的被动型策略，资金长期被占用，收益率波动小，混入排名会扭曲主动策略的优胜劣汰 |

**网格策略保持独立运行**，资金额度单独划拨，不参与每月动态再平衡。

### 2.3 未来新增策略

新增策略（如 Grid 之外的其它主动开仓型策略）如需参与资金分配，必须在 `ai_tuner/config.yaml` 中预先配置以下字段：

```yaml
- strategy_id: "new_strategy"
  name: "新策略"
  # ... 现有字段 ...
  capital_allocation:
    enabled: true                    # 是否参与资金分配
    fallback_ratio: 0.15            # 首月无历史数据时的默认占比
```

未配置 `capital_allocation.enabled: true` 的策略，系统拒绝纳入分配池。

## 3. 分配结构

### 3.1 固定部分

| 项目 | 占比 | 说明 |
|------|------|------|
| 风险备用金 | **15%** | 固定不变，不参与排名分配 |

### 3.2 动态分配部分

主动策略共分 **85%** 的资金（1 - 15% 备用金），按月度收益率排名分配：

| 排名 | 分配比例（占总资金） |
|------|---------------------|
| 第 1 名 | 30% |
| 第 2 名 | 25% |
| 第 3 名 | 20% |
| 第 4 名 | 10% |

> **比例语义（2026-09-21 变更）**：`rank_ratios` 配置值直接对应**占总资金比例**，总和 = 0.85 = 1 - 0.15（风险备用金）。分配金额 = `total_capital × rank_ratios[rank-1]`，无需再乘以可分配比例（85%）。

### 3.3 通用权重公式

对于参与分配的策略，权重序列由配置 `rank_ratios` 决定（排名按收益率从高到低）：

```
权重 = [30%, 25%, 20%, 10%] 对应排名 1, 2, 3, 4
```

排名第 k 的策略分配比例 = `rank_ratios[k-1]`（配置驱动，总和 = 1 - reserve_ratio）。参与策略数量超出 `rank_ratios` 长度时，超出部分分配比例为 0 并记录告警日志。

### 3.4 最低保障

**不设硬性最低保障比例**，严格按排名分配。长期垫底的策略自然获得更少资金，体现优胜劣汰。

## 4. 首月初始分配

系统首次运行（无历史收益率数据）时，使用默认基准分配（`fallback.ratios` 配置）：

| 策略 | 默认占比 |
|------|---------|
| MTPCS 策略 | 35% |
| MTPCS 激进版策略 | 10% |
| 新币做空策略 | 25% |
| HRS 混合反转策略 | 15% |
| 风险备用金 | 15% |

**合计** | **100%**

> **比例语义（2026-09-21 变更）**：首月 `fallback.ratios` 中的比例同样为**占总资金比例**，分配金额 = `total_capital × ratio`（此前误按"可分配资金 × ratio"计算，已修复）。各比例总和 = 0.85 = 1 - 0.15（风险备用金）。

## 5. 收益率计算

### 5.1 计算口径

**只计算已实现 PnL（已平仓盈亏）**，不包含未实现浮盈/浮亏。

**理由**：资金分配决定"下个月能用多少本金去开仓"。如果计入未实现浮盈（账面盈利），可能导致该策略持仓过重、账面浮盈很大，但实际现金没回来，反而占用了下个月本应给其他策略的现金。**现金为王，落袋为安**。

### 5.2 收益率公式

```
月度收益率 = 本月该策略已实现 PnL / 该策略月初实际占用的持仓保证金(open_margin)
```

**分母说明（2026-09-21 变更）**：分母由"月初分配资金(`allocated_amount`)"改为"月初实际占用保证金(`open_margin`)"。

- **变更原因**：部分策略实际占用保证金远高于名义分配额（如 HRS 存量持仓 + 累计亏损远超分配额），按分配额作分母会产生 `-185%` 这类失真的收益率。
- **口径原则**：从实际出发，以该策略月初真正占用市场资金的多少来度量资金使用效率，更能反映真实占用水平。
- **数据来源**：`public.strategy_position_snapshot_history`（小时级持仓对账快照），取该策略本月最早一条快照的 `open_margin` 作分母。
- **回退策略**：本月无历史快照时，回退取早于本月最近一条快照的 `open_margin`；完全无记录时返回 0（收益率记为 0，不做除零）。
- **已知限制**：历史表目前最早仅到 2026-09-10 17:00，本月缺少月初数据，本月收益率可能仍失真；下月起历史积累完整后自然修复。

### 5.3 数据来源

所有参与策略统一从 `trading.trade_records` 表查询当月已实现盈亏（`pnl_collector.py`），按落库中文名 `strategy` 列匹配：

| 数据表 | 关键字段 | 说明 |
|--------|---------|------|
| `trading.trade_records` | `strategy`（落库中文名）、`realized_pnl`、`executed_at` | 所有参与策略统一数据源 |

> **落库中文名显式映射（2026-09-21 变更）**：`trade_records.strategy` 存中文名（如 "MTPCS策略"）。hrs 的**配置名**（"HRS混合反转策略"）与**落库名**（"HRS策略"）不一致，若直接按配置名查询会导致 hrs 的 PnL 恒为 0。`pnl_collector.py` 通过 `_STRATEGY_DB_NAME_OVERRIDES = {"hrs": ["HRS策略"]}` 显式映射修正。
- MTPCS：落库名 "MTPCS策略"；激进版：落库名 "MTPCS激进策略"；新币做空：落库名 "新币做空策略"；HRS：落库名 "HRS策略"

### 5.4 平仓识别

- 有明确平仓记录的（如 `btc_eth.trades` 中的完整交易记录）：直接汇总
- 需通过持仓状态变化（`status = 'closed'` 的平仓记录）计算盈亏

### 5.5 最近止损次数统计

**止损判定依据**：`trading.trade_records.close_reason = 'STOP_LOSS'`。

**打标机制**：各主动策略（btc_eth / new_coin / hrs）在止损平仓时调用 `TradeLogger.log_stop_loss()` 在 `trade_records` 表写入 `close_reason='STOP_LOSS'` 标记，统一复用 `shared/base_strategy` 的公共方法 `mark_stop_loss()`。该标记与止盈、手动平仓（`close_reason` 为空或其他值）明确区分，避免误判止损。

**看板统计**：看板 `data_service_docker._get_stop_stats()` 按该标记统计近 N 天止损笔数与每日分布，用于展示"最近止损次数"。

## 6. 分配结果生效

### 6.1 生效方式

**限制各策略的最大占用保证金（Max Margin，保证金口径）**。

分配结果通过 `capital_limits` 配置 / DB `public.capital_allocation` 提供，各策略在执行开仓信号时，**累计持有的所有仓位占用保证金之和不得超过生效限额**。占用保证金计算口径（全项目唯一）：

```
占用保证金 = Σ(|positionAmt| × markPrice × contractSize) / leverage
```

> **口径修订说明（2026-09-21）**：本节原定义限额口径为「最大名义开仓金额（Max Notional）」，即直接比较「名义价值之和 ≤ 分配额度」。因 `monthly_limit` 的资本语义是**本金（保证金）**，名义口径会把额度按杠杆放大（杠杆 2 倍时被放大 2 倍），已统一为**保证金口径**。详见 [策略资金限额强制执行需求文档](./策略资金限额强制执行需求文档.md) 第 4 章与 R3。

### 6.2 开仓检查逻辑

```
计算当前所有持仓的占用保证金总和（同币种多仓累加）
生效限额 = 优先级链取第一个可用值：
   ① DB public.capital_allocation 当月 active 记录 → entries[strategy_id].allocated_amount
   ② 策略 config.yaml → capital_limits.monthly_limit
   ③ 策略 config.yaml → trading.total_position_margin_limit（静态兜底）
   ④ 三级均不可用 → fail-open 放行并告警
if (当前占用保证金 + 新开仓保证金) > 生效限额:
   拒绝该开仓信号（或按剩余额度缩仓，缩仓后低于 min_position_margin 则拒绝）
else:
   允许开仓
```

> 限额优先级链**取第一个可用值，不做 `min`**（月度额优先于静态兜底）；实现见 `shared/capital_manager.py::get_effective_margin_limit()`。

### 6.3 额度计算

```
策略分配额度 = 合约账户净资产 × 该策略分配比例
```

- 合约账户净资产 = 账户总权益（accountEquity / totalMarginBalance），含可用余额 + 持仓保证金 + 未实现盈亏，从 `get_account_info()` 获取
- 不使用可用余额（availableBalance）口径：会低估可分配资金、误判各策略占比
- 风险备用金固定为总资金的 15%
- **分配比例 `allocated_ratio` 月初算定整月不变，`allocated_amount` 由每日任务按当日净资产重算（见 8.1 每日刷新金额）**

## 7. 数据存储

### 7.1 主存储：数据库表 `capital_allocation`

PostgreSQL 表 `public.capital_allocation`，**按月一条记录**（策略明细以 JSONB `entries` 数组内嵌），记录每月分配历史：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | SERIAL | 主键 |
| `month` | DATE（UNIQUE） | 分配月份，**每月一条记录**（唯一约束） |
| `total_capital` | DECIMAL(20, 8) | 当月总资金池（合约账户净资产） |
| `strategy_count` | INTEGER | 参与分配的主动策略数量 |
| `is_first_month` | BOOLEAN | 是否首月（无历史数据，使用默认基准分配） |
| `entries` | JSONB | 各策略明细数组，每项含 `strategy_id` / `strategy_name` / `rank` / `monthly_pnl` / `monthly_return` / `allocated_ratio` / `allocated_amount` |
| `status` | VARCHAR(20) | 记录状态，默认 `active`（策略限额读取仅匹配 `status='active'`） |
| `created_at` | TIMESTAMP | 创建时间 |

> **幂等写入**：`INSERT ... ON CONFLICT (month) DO NOTHING`，同一月份不重复写入。

### 7.2 运行时读取：各策略 `config.yaml`

调度器算出结果后，**同时写入** 各策略 `config.yaml` 的 `capital_limits` 字段（注意：**策略运行时的主来源是 DB**，config 仅为兜底）：

```yaml
# strategies/<策略>/config.yaml
capital_limits:
  monthly_limit: 156.33        # 下月分配额度（USDT，保证金口径）
  allocated_ratio: 0.30        # 分配比例（如 0.30 表示 30%）
  allocation_month: "2026-09"  # 分配月份
  updated_at: "2026-09-11 14:09:23"  # 最后更新时间
  db_cache_ttl_seconds: 300    # DB 分配额缓存有效期（秒）
  db_query_timeout_seconds: 3.0 # DB 查询超时（秒）
```

> **注意（2026-09-21 修订）**：旧版本本节给出的 `capital_limits: {策略ID: {ratio, amount_usdt}}` 示例已过时。实际写入各策略 `capital_limits` 的字段为 `monthly_limit` / `allocated_ratio` / `allocation_month` / `updated_at`，并新增 DB 读取保护项 `db_cache_ttl_seconds` / `db_query_timeout_seconds`。

**运行时读取优先级（取第一个可用值，不做 `min`）**：

1. DB `public.capital_allocation` 当月 `status='active'` 记录 → `entries[strategy_id].allocated_amount`（**主来源，唯一真相来源**）
2. 策略 `config.yaml` → `capital_limits.monthly_limit`（兜底）
3. 策略 `config.yaml` → `trading.total_position_margin_limit`（静态兜底）
4. 三级均不可用 → fail-open 放行并告警

> **为什么必须运行时读 DB（docker 挂载事实）**：`btc-eth-strategy`、`btc-eth-aggressive-strategy`、`new-coin-strategy` 三个容器**均无 `config.yaml` 挂载**——config 打进镜像，宿主机修改或 AI 月度写入后需**重建镜像才生效**。因此 AI 月度分配写宿主机 config 对前三者不生效，必须运行时读 DB（仅 `hrs-strategy` 挂载了 `./strategies/hrs/config.yaml:/app/strategies/hrs/config.yaml:rw`）。数据库既用于历史回溯/审计，也是策略限额的权威运行时来源。

## 8. 执行时间

| 项目 | 设定 |
|------|------|
| 执行频率 | 每月一次 |
| 执行时间 | **每天 09:30（北京时间 UTC+8），代码内通过 `calendar.monthrange` 判断是否为月末最后一天** |
| 生效时间 | 次月 00:00 起新仓位走新比例 |
| 调度方式 | 与现有周度调度一致的 APScheduler 机制 |

**技术说明**：APScheduler 的 cron 触发器不支持 `last` 关键字（每月最后一天），因此采用"每天 09:30 执行，代码内判断是否为月末最后一天"的方案。非月末自动跳过，月末触发完整流程。

### 8.1 每日刷新金额

分配比例 `allocated_ratio` 于月初一次算定，**整个月保持不变**；但合约账户净资产每日增减，故新增每日定时任务，用当日净资产重算当月 `active` 分配记录中各策略的 `allocated_amount`，使各策略可开仓额度随净资产动态更新。

| 项目 | 设定 |
|------|------|
| 执行频率 | 每交易日一次 |
| 执行时间 | **每天北京时间 00:15**（cron `15 0 * * *`，取自 `config.yaml` → `capital_allocation.daily_refresh_cron`） |
| 计算逻辑 | 当日合约账户净资产 × 该策略 `allocated_ratio`，结果保留 2 位小数 |
| 写入范围 | 仅 UPDATE 数据库 `public.capital_allocation` 的 `entries[*].allocated_amount` 与 `total_capital` |
| 边界约束 | **绝不修改各策略 config.yaml**；不加备份；`reserve` 备用金不进 `entries`，天然不刷新 |
| 技术来源 | `ai_tuner/allocation/daily_refresher.py`（`DailyAllocationRefresher`）、净资产取自 `ai_tuner/allocation/balance_provider.py::get_actual_balance()`，由 `ai_tuner/main.py` 注册每日任务 |

**容错规则（以下任一条件命中均保留旧值）**：
1. `capital_allocation.daily_refresh` 未启用
2. 当日净资产为 `None` 或 ≤ 0
3. 当月无 `active` 记录
4. `entries` 结构非法
5. 联网失败/请求异常

## 11. 系统架构变更

### 11.1 新增模块

## 12. 风险与注意事项

1. **数据完整性**：必须确保各策略的交易记录完整准确，特别是已平仓订单的 PnL 计算
2. **时间一致性**：所有时间统一使用 UTC+8（北京时间），避免跨时区问题
3. **首次运行**：首月无历史数据，使用默认基准分配
4. **新增策略**：新增策略必须在 config.yaml 中预设 `fallback_ratio`，否则不纳入分配池
5. **网格策略独立性**：网格策略资金独立，不受月度分配影响
6. **回滚方案**：若月度分配计算失败，应保持上月分配比例不变，并发送告警通知
7. **配置生效依赖运行时读 DB**：`btc-eth-strategy` / `btc-eth-aggressive-strategy` / `new-coin-strategy` 三个容器无 `config.yaml` 挂载（config 打进镜像，需重建镜像才生效）；AI 月度分配写宿主机 config 对前三者不生效，**必须依赖运行时读 DB**（DB 为唯一真相来源）。

> **说明（2026-09-21）**：原第 7 条「btc_eth 与 btc_eth_aggressive 共用同一份额度」的已知风险已消除——激进版改为**独立参与**月度资金分配（见第 2.1 节），两策略各自获得独立额度，不再存在"合计占用可超月度额"的问题。
