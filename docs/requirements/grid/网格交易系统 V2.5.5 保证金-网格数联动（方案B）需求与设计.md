## 1. 背景与问题

### 1.1 现象

V2.5 引入「多因子保证金引导」后，一次实际推送里同时出现了三组互相矛盾的数值（样例为线上真实推送）：

```
📐 建议网格参数
- 网格数量: 7 格
- 网格间距: 15.48 USDT
💰 资金可行性提醒
每格仅0.28张，不足1张。请将保证金增至1791 USDT，或减少网格数量至5格
💰 保证金引导（建议加码）
- 当前保证金: 500 USDT
- 建议保证金: 936 USDT（+87%）
- 调整幅度: 建议增加 150 USDT（限幅30%）
```

按 P=2558.48、L=10、M=500 复算：

| 数值 | 来源 | 结果 |
|---|---|---|
| 每格张数 | `M×L/(P×N)` = `500×10/(2558.48×7)` | **0.28 张** |
| 7 格每格≥1张所需保证金 | `P×N/L` = `2558.48×7/10` | **1791 USDT** |
| 建议保证金 | 五因子 `base×状态×趋势×波动×BTC×费率` | **936 USDT**（限幅后实际 650） |
| 936 保证金下每格张数 | `936×10/(2558.48×7)` | **0.52 张（仍 <1）** |
| 500 保证金下最多可支撑的网格数 | `floor(500×10/2558.48)` | **1 格** |

**结论：即便完全按「保证金引导」加码到 936（或限幅后的 650），每格张数仍然 <1 张，`≥1张` 约束根本没有被解决。** 同一推送里给用户的三个数字互相打架。

### 1.2 根因：三条链路各算各的

| # | 数值 | 计算位置 | 输入 | 是否受保证金影响 |
|---|---|---|---|---|
| 1 | 网格数量 N | [grid_calculator.py](file:///Users/yl/vscode/Binance_quantitative_trading/strategies/grid/grid_calculator.py#L527-L552) | 仅 ATR 比值，夹 `[min,max]` | **否** |
| 2 | 资金可行性（每格张数） | [grid_calculator.py](file:///Users/yl/vscode/Binance_quantitative_trading/strategies/grid/grid_calculator.py#L929-L975) | **固定配置 `trading.margin`** | 用了错的保证金 |
| 3 | 建议保证金 M | [margin_advisor.py](file:///Users/yl/vscode/Binance_quantitative_trading/strategies/grid/margin_advisor.py#L488-L493) | 五因子 × `trading.margin` | **否（与 N 无关）** |

调用处在 [signal_bot.py](file:///Users/yl/vscode/Binance_quantitative_trading/strategies/grid/signal_bot.py#L295-L314)：可行性检查传的是 `self.default_margin`（恒等于配置值 500），而推送的却是 `advice.suggested_margin`（936）——**两个数字被拼进同一条消息却来自不同口径**。

## 2. 目标与非目标

### 2.1 目标

1. **统一保证金口径**：资金可行性检查一律使用「建议保证金」M，与保证金引导板块同源。
2. **网格数量受资本约束**：最终网格数 `N_final = min(N_struct, N_profit, N_cap)`，其中 `N_cap` 由 M 反推。
3. **不可行时给出可执行的真实出口**：资本撑不住最小网格数时，明确给出「所需保证金」与「所需杠杆」，不再给不可行建议。
4. **同一条推送内数值自洽**：网格数量、建议保证金、可行性提示可互相复算。

### 2.2 非目标

- 不改动市场状态判定（V2.4 三层预警）与五因子系数公式。
- 不改动价格区间、止盈止损、上移/下移的计算口径。
- 不自动下单、不自动调保证金/杠杆（仍是半自动信号灯）。
- 不实现 D-4 的 0.6% 间距提示分支。
- 不修 1.3 节末尾的展示不自洽问题（另立任务）。**A-review 澄清（2026-10-09）**：T3 将 C2 降网格逻辑并入约束链后，`profit_rate`/`grid_spacing` 必须按 `N_final` 统一重算——现状 [signal_bot.py](file:///Users/yl/vscode/Binance_quantitative_trading/strategies/grid/signal_bot.py#L504-L513) 降网格后仅覆写 `grid_count` 而 spacing/profit_rate 仍是旧值，属实现怪癖，在 T3 重构路径上自然消除，不算范围蔓延；除此之外的展示问题（如样例 15.48 间距与区间公式的对账）仍不在本方案范围。

## 4. 架构设计

### 4.1 改造前后数据流

**改造前**

```
market_analysis
   ├─ margin_advisor.compute_advice  ──► M（五因子，与 N 无关）
   └─ _calculate_grid_params         ──► N_struct（仅 ATR + 利润率）
validate_position_size(margin = trading.margin=500)  ──► 可行性（错口径）
拼装：N_struct + M + 基于 500 的可行性  ← 三者不一致
```

**改造后**

```
market_analysis
   ├─ margin_advisor.compute_advice  ──► M（五因子）
   └─ _calculate_grid_params(margin=M)
          ├─ N_struct（ATR 比值，夹 [N_min, N_max]）
          ├─ N_profit = floor(W/(P×r_min))     # 等差；等比见 4.2 精确口径
          └─ N_cap    = floor(M×L/(P×q_min))
          └─► resolve_capital_feasibility(...)
                 ├─ 可行 → N_final = min(N_struct, N_profit, N_cap)
                 └─ 不可行 → N_final = N_struct（仅供参考） + M_required/L_required
拼装：N_final + M + 同口径可行性（三者可互相复算）
```

### 4.2 核心公式与不变量

设：

- `P` 当前价格，`L` 杠杆（`trading.leverage`），`M` 建议保证金
- `W = upper_boundary - lower_boundary`
- `r_min = grid.min_profit_rate`（0.01）
- `q_min = trading.min_quantity`（0.01 ETH = 1 张，见 §9）
- `N_min` = 震荡 `grid.min_grid_count`(5) / 弱趋势 `grid.weak_trend_min_grid_count`(4)
- `N_max` = 震荡 `grid.max_grid_count`(12) / 弱趋势 `grid.weak_trend_max_grid_count`(10)

约束：

| 约束 | 公式 | 含义 |
|---|---|---|
| C1 结构 | `N ≤ N_struct` | 市场波动结构给出的网格密度上限 |
| C2 利润率 | 等差：`N ≤ N_profit = floor(W/(P×r_min))`；等比：`N ≤ floor(ln(U/Lb)/ln(1+r_min))` | 每格利润率 ≥ r_min。**A-review 补充（2026-10-09）**：等比下 `W/(P×r_min)` 仅为近似，实现必须沿用现有 [validate_profit_rate](file:///Users/yl/vscode/Binance_quantitative_trading/strategies/grid/grid_calculator.py#L825-L881) 按 `grid_mode` 精确计算（等差/等比分别推导）或用等比精确式，禁止用近似公式替代造成临界场景差 1 |
| C3 资本 | `N ≤ N_cap = floor(M×L/(P×q_min))` | 每格下单张数 ≥ q_min |
| C4 下限 | `N ≥ N_min` | 策略最小网格数 |

判定：

```
N_feasible = min(N_struct, N_profit, N_cap)
if N_feasible >= N_min:
    N_final = N_feasible        # 可行；binding = argmin
else:
    不可行
    M_required = ceil(N_min × P × q_min / L)     # 同杠杆所需保证金
    L_required = ceil(N_min × P × q_min / M)     # 同保证金所需杠杆
```

**A-review 补充（2026-10-09）：binding 并列时的归属。** `min` 的 argmin 不唯一时（如样例 N_struct=7 与 N_profit=7 并列），按 **STRUCT > PROFIT > CAPITAL** 优先级取绑定项——与「结构为基准口径、资本仅单向压制」的设计取舍一致，保证文案稳定可测。

**不变量（必须在测试中验证）**

1. 可行时：`qty_per_grid = M×L/(P×N_final) ≥ q_min`
2. 可行时：`N_min ≤ N_final ≤ N_struct`
3. 可行时：`N_final` 满足利润率下限（若 C2 为绑定项则恰好取等）
4. 不可行时：`N_feasible < N_min`，且 `M_required`、`L_required` 均为可达值

**重要设计取舍（联动是「单向下压 + 门槛反推」，不是对称升降）**

- 保证金上调 **不会**让网格数突破 `N_struct`。`N_struct` 由 ATR 结构决定，上调保证金只解除 C3 的压制；盲目加网格会压低每格利润率、偏离波动结构。
- 保证金不足时网格数被下压；压到 `N_min` 以下即判不可行，转而反推所需保证金/杠杆。
- 因此本方案回答用户的问题为：**「网格数量的基准口径不随保证金变，但资本约束会单向压低它；资金可行性提醒/建议必须与建议保证金同口径并随之变化。」**

## 9. 修订：min_quantity 单位缺陷（A 段重开，2026-10-10；A-review 第二轮复核后 **GA 通过**，见 9.11）

> 本节为上线后发现的 FR-06 设计缺陷的权威修订口径，取代 §3.1 FR-06、§4.2、§4.5、§7 样例、§3.2 AC-04~07/10 中因 `min_quantity` 单位错误而失效的表述。

### 9.1 缺陷定性与根因

上线后用户实测：按 10:05 推送建议在币安**成功建成 12 格网格**，推翻 D 段「681 保证金不足以建 12 格」的断言。根因：

- `trading.min_quantity: 1` 被代码当作「1 ETH」进入公式 `N_cap = floor(M×L/(P×q_min))`，实际 ETHUSDT 永续 **1 张 = 0.01 ETH**，放大约 100 倍。
- 全 `strategies/grid` 无 `contract_size` 换算；quantity 全程 ETH 口径（`grid.base_quantity: 0.001` = 0.001 ETH）。
- 因此「资本可行性提醒」全线误报（详见 handoff）。

数值对比（生产样例 P=2494.39, M=673, L=10）：

| | N_cap | N_final | 结论 |
|---|---|---|---|
| 旧（错） | floor(6730/2494.39)=**2** | min(12,7,2)=2 | 误判资本不可行 |
| 新（对） | floor(6730/24.9439)=**269** | min(12,7,269)=**7** | 可行，binding=PROFIT |

### 9.2 核实结论（前置关卡）

- `config.yaml` `symbols` 仅 `ETHUSDT`（唯一交易对；`margin_guide.btc_consistency.btc_symbol=BTCUSDT` 仅用于 BTC 一致性检测，不参与网格下单）。
- `realtime_alert.symbol=ETHUSDT` 与网格信号主链无关。
- 全仓无 `contract_size/contractSize`；`base_quantity`/`min_quantity` 均直接以 ETH 数值进入计算，唯一单位误标点 = `min_quantity: 1` + 文案「张」。
- **无其他币种/路径同错。**
- **A-review 补证（2026-10-10 第二轮）**：生产合并配置链路已独立核实——`strategies/grid/tuning_overrides/.active=V20260830`，该 override（`V20260830.yaml`）仅覆盖 `grid.base_grid_count` / `grid.grid_spacing_atr_multiplier`，**不覆盖 `trading.min_quantity`**；`trading` 节在生产合并配置中保持 `config.yaml` 原值。⇒ 修改 `config.yaml` 的 `min_quantity` 即在生产生效，不存在「override 覆盖导致修复失效」的路径。

### 9.3 FR-06 重定义（权威口径）

- `trading.min_quantity` 单位 = **ETH**（基础币），取值 **0.01**。
- 换算：ETHUSDT 永续合约 **1 张 = 0.01 ETH** ⇒ `min_quantity = 0.01 ETH = 1 张`。
- 公式 `N_cap = floor(M×L/(P×q_min))` **结构不动**；`q_min` 与 `qty_per_grid` 同步以 ETH 计。
- 本次**不引入 `contract_size` 参数**（当前仅 ETHUSDT）。
- 文案「张」统一改为「ETH」，包括旧路径 `_build_legacy_funding_text`（handoff 记为 `_build_capital_section`，实际函数名为 `_build_legacy_funding_text`）。
