# 网格实时 shadow 队列溢出排查（2026-10-29）

## 结论

生产日志里的 `storage_degraded` 主要是 **ETHUSDT `@trade` 原始成交队列溢出**，不是 SQLite 达到 1 GB 水位。当前实现刻意逐出最旧成交、保留最新成交，延续了 2026-10-13 的修复口径；这能保护整秒末笔价，但不能证明逐笔边界事实完整。每次实际逐出多少笔、涉及哪些秒，目前没有计数或持久审计，无法事后精确量化。

## 证据与方法

- 北京时间 2026-10-29 12:34:52–14:14:24，`trading_system-grid-realtime` 日志有 **10 次** `storage_degraded` 降级及各自恢复；每次约 2–59 秒。每分钟维护任务可清除此标志，因此日志持续时间不等于队列拥塞持续时间。
- 生产容器 `VERSION` 为 `1e22cae5d30bae83811a9e9ab769ac3ce6b31c95`，`main.py` SHA-256 为 `6e9f4c2e18df84a8444dd42d0c1bdd5a04f2485be9922b500b5317b08f05632a`，与仓库的逐出逻辑一致：`_pump_feed()` 检测到 `Queue.full()` 后设 `_storage_degraded=True`、`get_nowait()` 逐出最旧成交，再放入新成交；另一置位路径是 `Delivery.maintenance()` 检测 DB+WAL+SHM 超过 `storage.max_bytes`。
- 排查时 DB、WAL、SHM 合计约 **4.25 MB**，配置 `storage.max_bytes=1,073,741,824` 字节；容器未 OOM、未异常重启。结合两条置位路径，确认本轮降级由队列满触发。当前配置 `delivery.queue_capacity=1000`，主循环每约 1 秒集中 drain 一次。
- 独立研究库近三小时每秒聚合成交数均值约 9.7，p99=69，最高 711。以每条聚合成交的 `last_trade_id-first_trade_id+1` **估算**对应原始成交量，均值约 39.7 笔/活跃秒、p99=314、最高 2,822；10 次降级各自前后 5 秒内，都有至少 1 秒估算量达到 1,000。两路数据源 ID 不同，本统计仅作负载相关性证据，不能据此计算在线实际逐出笔数。
- 研究库近 72 小时估算原始成交峰值：单秒 8,618、连续 2 秒 11,619、连续 3 秒 15,481、连续 5 秒 21,927；283 个秒级窗口超过 1,000。`sum(max(0, 每秒估算量-1000))=264,256` 是容量压力指标，**不是实际丢弃笔数**，因队列 drain 相位、WS 到达时间和各秒连续积压未知。
- 定向验证：`test_pump_feed_queue_full_evicts_oldest_keeps_newest` 与 `test_run_maintenance_every_60_ticks` 均通过（2 passed）。已有[知识记录](../knowledge/issues/Binance_quantitative_trading-20261013-grid-feed-queue-drop-latest.md)记载该逐出策略及约 4.7 次/时的历史瞬态观察。

## 影响边界

- 实时服务仍为 `mode: shadow`、`shadow_research.enabled: false`。本轮核对会话 25 `ACTIVE`、心跳小于 1 秒、参考 `SENT`、无 pending；8 条 outbox 均为 `SHADOW`。行情连接持续健康，独立落库器聚合成交和 1 秒采样持续更新。
- 逐出最旧成交可保住在线队列中最新的成交价，但 `_emit_facts()` 会遍历已 drain 成交；被逐出的笔可能含有区间穿越事实。现有队列溢出路径不会像断线处理那样清空旧滚动样本、触发 300 秒重新预热，也没有记录逐出数量/时间范围。因此不能用健康恢复后的 `health={}` 证明影子事件样本完整。
- `HealthMonitor` 对同一原因使用固定 `event_id`；`Delivery._insert_event()` 对重复 ID 幂等跳过。反复出现的队列溢出在日志可见，SQLite 的 event/outbox 计数不会逐次增加，不能据此反推发生次数。
- 研究库的聚合 ID 和秒采样连续性不证明在线原始逐笔流完整；两者不可直接按 ID 对账。现有日志与数据库不足以重建丢失的在线边界事实或精确评估 M3 指标偏差。

## 后续处理建议

1. 将队列溢出与磁盘容量分别命名和计量：记录累计逐出数、最近逐出时间/ID 范围、队列峰值及按秒分布；健康事件需保留每次发生的审计事实。
2. 为队列溢出定义明确的行情缺口恢复口径：暂停依赖完整窗口的判断，清除持续计时，必要时重新预热，并保持新鲜价格下的边界事实处理；用定向测试覆盖溢出、恢复、参考切换和 shadow 不外发。
3. 用近 72 小时真实负载重放压力测试选取有界容量和消费节奏；单纯把 1,000 调大没有零丢失保证。完成后重新核对 M2 的峰值降级/队列故障验收，再决定哪些在线影子时段可用于 M3。

## 本地修复与验证

- 将生产队列容量由 1,000 调至 20,000，覆盖本次近 72 小时观测到的连续 3 秒原始成交估算峰值 15,481。该估算不能保证未来零溢出。
- 队列满时仍逐出最旧成交、保留最新价；另行累计逐出数、记录最后逐出 ID/时间，并将 `feed_queue_overflow` 与 `storage_degraded` 分开。前者不再由数据库容量维护任务清零。
- 溢出后清空滚动样本，暂停依赖完整窗口的状态判断，最后一次逐出后重新预热最长窗口 300 秒；每次降级均使用独立健康事件 ID 落库。shadow 模式下健康事件只留 `SHADOW` 行。
- `python3 -m pytest tests/test_grid_realtime -q`：317 passed；独立 `test_feed.py`：37 passed。新增测试覆盖溢出计数、预热、重复审计、shadow 状态及观测峰值容量。

上述修改目前仅在 `codex/grid-shadow-queue-fix` 本地分支；生产配置、代码及数据库未变。上线后仍需只读核对运行态、真实逐出数与健康事件，并重新评估 M2/M3 样本可用时段。
