# XAUUSDT MTCPS 影子仿真与小资金灰度设计

**日期**：2026-10-18

**状态**：设计方向已确认，书面 spec 待用户复核

**目标品种**：`XAUUSDT` Binance USDⓈ-M TradFi 黄金永续合约

**候选策略**：MTCPS 原版、MTCPS 激进版

**灰度资金**：300 USDT

**用户最终亏损红线**：90 USDT（30%）

## 1. 背景

用户希望验证 XAUUSDT 是否适合 MTCPS，但不希望将实验数据、资金占用或运行风险混入现有 MTCPS 原版和激进版。

XAUUSDT 是 TradFi 商品永续合约，虽然与普通 USDⓈ-M 永续合约使用相似的保证金和结算机制，但其指数价格、标记价格和传统市场非活跃时段具有特殊规则。它于 2026 年 1 月才上线，可用历史样本不足一年。因此，历史回测不足以单独支撑实盘决策，需要独立的前向影子验证。

参考：[Binance Futures TradFi 永续合约说明](https://www.binance.com/en/support/announcement/detail/ecf7318c0d434c339e80878588e700d0)。

## 2. 目标与非目标

### 2.1 目标

1. 在不真实下单的前提下，收集 MTCPS 原版和激进版对 XAUUSDT 的前向决策。
2. 观察期结束后，用真实 1m 行情按时间顺序回放虚拟订单、成交、止损、分批止盈、移动止损和时间止损。
3. 将手续费、资金费、滑点、限价未成交和资金占用纳入结果。
4. 用可重复、可审计的报告选出最多一个实盘候选版本。
5. 候选版本通过准入门槛后，以独立的 300 USDT 限额开始小资金实盘灰度。

### 2.2 非目标

- 不将 XAUUSDT 加入现有 `btc_eth` 或 `btc_eth_aggressive` 交易对池。
- 不在影子阶段调用币安下单、撤单、设置杠杆或修改持仓的接口。
- 不向 `trading.trade_records` 写入伪造的成交和持仓。
- 不让 XAU 影子实例参与 AI 自动调参或月度资金分配。
- 不因为交易样本过少而自动放宽信号门槛。
- 不复制第三套 MTCPS 生产源码。

## 3. 方案选择

### 3.1 候选方案

| 方案 | 方式 | 优点 | 缺点 |
|---|---|---|---|
| A. 信号落库 + 周期后批量回放 | 实时只记录虚拟订单意图，期末按 1m 行情重建完整交易生命周期 | 在线代码少，不维护虚拟持仓，容易重放和审计 | 观察期内不提供完整实时模拟盈亏 |
| B. 持续模拟账户 | 每个调度周期推进虚拟订单和持仓 | 可实时查看资金曲线 | 需要模拟撮合、订单状态机、重启恢复和异常对账，长期负担较高 |
| C. 极小资金直接实盘 | 跳过影子期 | 成交最真实 | 无法先验证适配性，不符合风险隔离目标 |

### 3.2 决策

选择方案 A。“发单”在本设计中特指生成并保存**虚拟订单意图**，不代表向币安发送任何请求。

## 4. 系统边界与实例标识

### 4.1 影子实例

```yaml
instance_id: mtcps_xau_shadow
symbol: XAUUSDT
execution_mode: shadow_batch
real_ordering_enabled: false
initial_virtual_equity_usdt: 300
profiles:
  - xau_original
  - xau_aggressive
```

影子实例使用独立容器和独立数据命名空间，但复用 MTCPS 分析代码与已有行情服务。

### 4.2 数据隔离

- 影子事件和回放结果使用 PostgreSQL `research` schema。
- 影子期不写入 `trading.trade_records`、真实策略状态表或当前看板持仓聚合表。
- 现有看板不展示该实例；观察结果通过独立研究报告输出。
- 两个 profile 各自使用 300 USDT 虚拟初始权益，不共享保证金或持仓。

### 4.3 安全隔离

影子容器使用 `ReadOnlyBinanceClient`。它只允许行情、交易规则、标记价格、资金费率等只读请求，并对任何订单、撤单、杠杆、保证金或持仓修改方法 fail closed：直接拒绝、记录错误并发送告警。

`execution_mode=shadow_batch` 只是第一道开关，只读客户端是第二道强制边界。即使业务代码误调下单方法，也不能触达交易所写接口。

## 5. 配置与参数口径

### 5.1 代码复用

当前 MTCPS 代码中的 `btc_eth`、配置目录、资金分配 ID、频率控制名和看板上报 ID 存在多处硬编码。实施时应将它们收敛为显式的运行时实例配置，而不是复制 `strategies/btc_eth` 目录。

至少需参数化：

- `instance_id`
- `record_name`
- `config_path`
- `execution_mode`
- `capital_strategy_id`
- `circuit_breaker_pool`
- `state_reporting_enabled`
- `real_ordering_enabled`

生产默认值必须保持现有行为，不改变 `btc_eth` 和 `btc_eth_aggressive` 的启动口径。

### 5.2 首轮候选配置

首轮不使用 XAU 样本反向优化信号参数，以免在短样本上过拟合。

- `xau_original` 的信号门槛使用 MTCPS 原版 ETH 保守基线。
- `xau_aggressive` 的信号门槛使用 MTCPS 激进版 ETH 基线。
- 两组都必须在配置中显式声明 `XAUUSDT` 的 `symbol_config`，禁止依赖隐式默认回退。
- 信号等级门槛和退出规则保留两版各自的差异。
- 为使回放结果与未来 300 USDT 实盘可比，两组都叠加相同的 pilot 外层资金约束：最大单笔保证金 30 USDT、最大并发持仓 1、最大杠杆 3x。

首轮 `XAUUSDT` 显式配置如下：

| 参数 | `xau_original` | `xau_aggressive` |
|---|---:|---:|
| `adx_min` | 35 | 30 |
| `vol_ratio_base.S` | 1.8 | 1.8 |
| `atr_abs_min` | 0.007 | 0.006 |
| `atr_percentile` | 50 | 50 |
| `atr_factor_strong` | 0.8 | 0.8 |
| `s_min_score` | 88 | 82 |
| `max_daily_trades` | 1 | 1 |
| `position_ratio_s` | 0.50 | 0.50 |

该表是首轮观察的固定基线，对应当前两版 ETH 的显式参数。若上线观察前生产 ETH 参数又发生变化，也不随之自动改写本表；任何变更必须开启新 `run_id`。

候选配置在观察周期开始时冻结。每条决策事件记录 `config_hash` 和 `git_commit`；中途修改配置必须开启新的 `run_id`，不得与旧样本混算。

## 6. 影子采集数据模型

### 6.1 `research.shadow_runs`

每个观察周期一条记录：

- `run_id`
- `instance_id`
- `started_at` / `ended_at`
- `status`
- `symbol`
- `initial_virtual_equity_usdt`
- `git_commit`
- `config_hashes`
- `data_cutoff_at`
- `created_at`

### 6.2 `research.shadow_decision_events`

按 profile、symbol 和调度时点记录不可变决策事件：

- `run_id`
- `profile_id`
- `symbol`
- `scheduled_at`
- `evaluated_at`
- `decision`：`candidate` / `no_signal` / `analysis_error`
- `direction`、`grade`、`score`
- `reference_price`
- `intended_order_type`、`intended_entry_price`
- `stop_loss_rule`
- `tp1_rule`、`tp2_rule`
- `trailing_rule`
- `time_stop_rule`
- `feature_snapshot`
- `reason_codes`
- `config_hash`
- `git_commit`
- `source_kline_close_times`

唯一键为 `(run_id, profile_id, symbol, scheduled_at)`，使调度重试幂等。

### 6.3 `research.shadow_replay_trades`

回放器派生的交易明细，不是实时影子持仓：

- 来源决策事件 ID
- 拟入场时间与价格
- 是否成交及未成交原因
- 虚拟数量、名义价值、保证金和杠杆
- 止损、TP1、TP2、移动止损和时间止损事件
- 总盈亏、手续费、资金费、滑点和净盈亏
- MAE、MFE、持仓时长
- 退出原因
- 回放引擎版本和输入数据截止时间

## 7. 决策采集流程

```text
定时触发
  → 确认 1h / 4h / 1d K 线已闭合
  → 对 original / aggressive 两个 profile 分别运行只读分析
  → 记录全量决策事件（包括 no_signal 和 error）
  → 不调用 execute_signal
  → 不建立虚拟在线持仓
```

采集阶段不应用现有真实持仓、真实成交或真实频率状态过滤候选信号。可能依赖持仓、冷却期、每日交易次数或资金占用的有状态执行门槛，在批量回放时按时间顺序统一施加。

为避免改变生产 `analyze()` 语义，实施时需把“无状态市场决策”与“有状态执行资格检查”拆成可单独调用的边界。生产主流程仍按原顺序调用两者。

## 8. 批量回放规则

### 8.1 时序与防未来数据

- 回放严格按 `scheduled_at` 排序。
- 信号只能使用当时已闭合的 K 线。
- 成交判定从信号产生后的第一根 1m K 线开始。
- 回放数据截止时间必须写入结果，保证同一输入可重复。

### 8.2 入场与成交

- 限价订单有效期固定为两版现行生产值 300 秒；只有在该窗口内被 1m 高低价穿越才算成交。
- 未成交订单记录为 `expired_unfilled`，不产生持仓。
- 市价意图按下一根 1m K 线可用价格加保守滑点成交。
- 价格和数量按当时的 Binance `tickSize`、`stepSize` 和最小名义价值约束舍入。

### 8.3 有状态执行门槛

对每个 profile 独立维护以下回放状态：

- 虚拟权益和可用资金
- 当前持仓
- 每日交易计数
- 单品种冷却期
- 连续亏损暂停状态
- 组合级软停和硬停状态

任一门槛拒绝的候选信号仍保留，并记录结构化 `rejection_reason`。

### 8.4 退出、费用与保守口径

- 回放支持初始止损、TP1、TP2、移动止损、时间止损和期末强制标记。
- 同一根 1m K 线同时穿越止损和止盈且无法从更细数据判断顺序时，采用保守的“止损先发生”口径。
- 准入主口径对所有成交保守地按 taker 每边 5 bps 计算手续费。如能取得账户当期可审计费率，可在报告中增加“实际费率口径”，但不替代保守准入口径。
- 资金费使用实际历史费率和持仓跨越的结算时点计算。
- 滑点基准固定为每边 2 bps；额外输出每边 1 bps、2 bps、4 bps 三档压力测试。限价挂单在成交判定中不额外加入场滑点，但其退出仍按对应压力档计算。
- 非活跃时段和传统市场活跃时段分组统计，不将两者只汇总为一个数字。

## 9. 观察周期与样本要求

1. 上线影子实例前，用自 XAUUSDT 上线起可取得的历史数据对两个 profile 跑基线回测。
2. 历史回测只用于发现明显缺陷、校验交易频率和检查参数量级，不单独触发实盘准入。
3. 前向影子期首次中期检查为 14 天。
4. 正式评估需同时满足：前向运行至少 30 天，且该 profile 至少有 12 笔已结束的有效虚拟交易。
5. 最长观察 8 周。8 周后仍不足 12 笔时，结论为“样本不足，暂不准入”，而非自动放宽参数。

## 10. 报告与准入门槛

### 10.1 必须输出的指标

每个 profile 分别输出：

- 调度次数、分析成功率、候选信号数
- 虚拟订单数、成交率、未成交原因
- 执行门槛拒绝原因分布
- 总盈亏、手续费、资金费、滑点、净盈亏
- 胜率、平均盈利、平均亏损、盈亏比、Profit Factor、单笔期望
- 最大回撤、最大连续亏损、最差单笔亏损
- MAE、MFE、平均持仓时长
- 止损、TP1、TP2、移动止损和时间止损的退出占比
- LONG / SHORT 分组结果
- 传统市场活跃时段 / 非活跃时段分组结果
- 滑点压力测试
- 原版与激进版在相同时点的决策差异

### 10.2 实盘准入条件

一个 profile 必须同时满足：

1. 已结束有效虚拟交易不少于 12 笔。
2. 扣除手续费、资金费和基准滑点后的净盈利为正。
3. Profit Factor 不低于 1.20。
4. 最大回撤不高于 15%。
5. 不存在无保护状态、重复平仓或数量越界等回放不变量违反。
6. 净盈利不是由单笔交易贡献；扣除最佳单笔后，组合不得出现明显的结构性亏损。
7. 在 2x 基准滑点压力测试下，不触发 30% 最终亏损红线。

若两个 profile 都通过，只选择风险调整后期望更高、回撤更小且结果更稳定的一个上线。若两者都未通过，结论为暂不接入 XAUUSDT。

## 11. 300 USDT 实盘灰度

通过准入后创建独立实例 `mtcps_xau_pilot`，仅启用胜出的一个 profile。

### 11.1 资金与仓位

- 固定分配额：300 USDT。
- 不参与 AI 月度资金分配和自动调参。
- 最大并发持仓：1。
- 最大单笔保证金：30 USDT。
- 最大杠杆：3x。
- 下单数量还必须满足当时 XAUUSDT 交易规则。
- 计划单笔止损金额控制在 3–5 USDT；若根据止损距离反推的仓位超过 30 USDT 保证金上限，以 30 USDT 为准。

### 11.2 亏损分级

亏损口径从 pilot 启用时的 300 USDT 独立基准权益计算，包含已实现盈亏、未实现盈亏、手续费和资金费。

- 亏损达 45 USDT（15%）：软停。禁止新开仓，保留现有保护和退出逻辑，发送高优先级告警，需人工复核后才可恢复。
- 亏损达 75 USDT（25%）：硬停。撤销本实例的未成交入场单，按安全市价方式平掉归属本实例的 XAU 持仓，禁用实例并告警。
- 90 USDT（30%）：最终亏损红线。25% 硬停为手续费、滑点和跳空预留 5% 缓冲，目标是不让实际亏损穿透该红线。

### 11.3 归属与故障隔离

- `record_name` 使用 `mtcps_xau_pilot`。
- pilot 与现有 MTCPS 原版、激进版互相加入 `competing_record_names`。
- 现有两个 MTCPS 交易对池仍不含 XAUUSDT；该互斥配置是防御误配置的第二道保护。
- pilot 使用独立数据库 schema、独立日志目录、独立容器和独立健康检查。

## 12. 异常处理

### 12.1 影子采集

- 某个 profile 分析失败时，写入 `analysis_error` 事件，另一个 profile 继续。
- K 线未闭合、缺失或时间戳不连续时，该调度周期不产生 candidate，并记录数据质量原因。
- 写库失败不得回退为本地下单或调用真实执行链路。
- 任何只读客户端拒绝事件均视为高优先级安全告警。

### 12.2 回放

- 缺少 1m K 线、资金费率或交易规则快照时，回放标记为不完整，不允许生成“通过准入”结论。
- 同一输入和同一引擎版本的重复回放必须产生一致的交易明细和汇总指标。
- 引擎版本变更后的结果使用新 `replay_run_id`，不覆盖旧结果。

## 13. 测试设计

### 13.1 安全测试

- `shadow_batch` 模式下任何下单、撤单、杠杆或保证金修改调用都必须失败。
- 影子运行不写 `trading.trade_records`、生产持仓状态表或看板聚合表。
- 生产两个 MTCPS 实例未显式配置新参数时，启动和交易行为不变。

### 13.2 采集测试

- profile 之间的配置和状态不泄漏。
- 调度重试不产生重复事件。
- `candidate`、`no_signal` 和 `analysis_error` 的字段契约稳定。
- 配置变化能被 `config_hash` 检出，且不会与原 run 混算。
- 未闭合 K 线不参与决策。

### 13.3 回放测试

- LONG / SHORT 的限价成交、止损和分批止盈。
- 同根 K 线触发多个价位时的保守顺序。
- TP1 后的剩余数量和移动止损。
- 时间止损、冷却期、每日交易次数和最大并发持仓。
- 手续费、资金费和滑点。
- `tickSize`、`stepSize`、最小数量和最小名义价值。
- 15% 软停、25% 硬停和 30% 最终红线的边界。
- 同一输入的确定性重放。

### 13.4 报告测试

- 交易明细与汇总盈亏、费用和回撤守恒。
- 无交易和样本不足时不会误判为通过。
- 最佳单笔贡献度和滑点压力测试可重现。
- 活跃时段和非活跃时段分组之和与全量口径一致。

## 14. 部署与可回退性

### 14.1 影子阶段

- 使用新 compose service，不替换现有 MTCPS 容器。
- 影子容器失败不能阻塞现有策略的健康检查或调度。
- 停止和回退影子阶段只需停用该 service；无需修改现有交易对池或清理真实持仓。

### 14.2 实盘 pilot 阶段

- 影子和实盘 pilot 使用不同的 `instance_id`、数据库 schema 和容器名。
- 从 shadow 切换到 live 不通过原地修改开关完成，而是启用新的 pilot service，避免影子数据和实盘状态混合。
- 停用 pilot 前先按归属确认未成交单和持仓，再撤单、平仓和停服务。

## 15. 验收标准

影子系统只有同时满足以下条件才视为交付：

1. 能对 XAUUSDT 按调度生成原版和激进版的全量决策事件。
2. 影子容器无法通过任何代码路径调用 Binance 写接口。
3. 影子数据不进入现有交易记录、策略持仓、看板绩效或月度资金分配。
4. 回放器能从决策事件和 1m 行情确定性地重建交易明细。
5. 报告同时给出两个 profile 的指标、拒绝原因、风险分组和准入结论。
6. 新增参数化不改变现有 `btc_eth` 和 `btc_eth_aggressive` 的默认行为。
7. 最终结论只能是“原版准入”、“激进版准入”或“暂不准入”之一，不允许两个 XAU 实盘实例同时上线。

## 16. 实施顺序

1. 先参数化 MTCPS 实例身份和执行模式，并用回归测试锁定现有两个生产实例的默认行为。
2. 建立只读 Binance 安全边界。
3. 拆分无状态市场决策和有状态执行资格检查。
4. 建立 `research` schema 和幂等决策事件写入。
5. 增加 original / aggressive 两个冻结 profile 和 XAUUSDT 显式配置。
6. 实现确定性批量回放器和对比报告。
7. 用历史数据跑基线回测和安全验收。
8. 部署影子实例，开始最长 8 周的前向观察。
9. 达到时间和样本门槛后生成准入报告。
10. 只在候选版本通过准入且用户确认后，再单独设计和启用 `mtcps_xau_pilot` 实盘服务。
