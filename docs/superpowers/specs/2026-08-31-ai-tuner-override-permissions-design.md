# ai-tuner 覆盖层目录权限修复设计

## 问题与根因

`ai-tuner` 以 `UID 1000:GID 1000` 运行，并通过 bind mount 将宿主机 `./strategies` 映射到 `/app/strategies`。生产服务器上的 `strategies/new_coin/tuning_overrides` 属于 `UID 501:GID 20`，权限为 `0755`，因此调优进程不能在该目录创建原子写入临时文件。

现有代码尝试由容器内非 root 进程执行 `chmod(0777)`，但该进程不是目录所有者，操作会失败；异常又被静默忽略，最终在 `tempfile.mkstemp()` 处表现为 `Permission denied`。

## 目标

- 立即恢复所有已注册策略覆盖层的可写能力。
- 每次部署都建立一致、最小化的权限状态，避免解压或目录重建后复发。
- 发生权限配置错误时输出可诊断信息，不再吞掉异常。
- 保持 `ai-tuner` 以非 root 用户运行。

## 方案

### 服务器权限

在宿主机为每个策略创建 `tuning_overrides`，统一设置为 `UID 1000:GID 1000`、目录权限 `0775`。不修改整个 `strategies` 树，也不使用全局 `0777`。

### 部署保障

在 ai-tuner 部署脚本重建容器之前执行幂等权限预检：从 `ai_tuner/config.yaml` 的启用策略或当前策略目录集合中确定目标目录，创建缺失目录并设置 `1000:1000/0775`。任何目录修复失败都必须终止部署，不能带着错误权限启动新容器。

完整部署路径和 ai-tuner 专用部署路径都调用同一段权限准备逻辑，避免两个入口行为分叉。

### 应用诊断

`ConfigOperator.apply_overrides()` 不再尝试无效的 `chmod`。写入前检查覆盖层目录是否可写；不可写时记录路径、当前进程 UID/GID、目录 UID/GID 和权限，然后返回失败。原子写入及 `.active` 回滚行为保持不变。

## 测试

- 回归测试模拟覆盖层目录不可写，验证操作失败且不会生成版本文件或 `.active`。
- 测试诊断日志包含权限上下文。
- 部署权限准备逻辑使用临时目录测试，验证创建、属主/权限设置以及失败时退出。
- 运行 `ai_tuner/tests/test_config_operator.py` 和相关部署脚本静态检查。

## 生产验收

1. 修复前记录目录属主、模式、容器 UID 和当前镜像版本。
2. 对所有策略覆盖层执行权限准备，并确认容器内 UID 1000 可创建、写入、原子替换及删除探针文件。
3. 部署修复后的 ai-tuner，核对 `VERSION`、镜像 ID 和关键文件哈希。
4. 通过应用代码写入一个不激活的临时测试目录，确认原子写入路径可用；不修改生产策略参数。
5. 检查健康接口和新日志，确认无新增 `Permission denied`、容器保持 healthy。

## 回滚

代码部署失败时恢复部署前镜像并重建容器。权限变更仅影响 `tuning_overrides` 目录；如需回退，可依据修复前快照恢复原属主和模式。覆盖层 YAML 与 `.active` 文件不删除、不覆盖。
