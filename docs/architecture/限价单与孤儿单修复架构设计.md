## 1. 概述

### 1.1 问题背景

本架构文档针对量化交易系统中两个核心问题制定修复方案：

**问题一：限价单问题** -- new_coin 策略中 8 处使用市价单（MARKET / STOP_MARKET / TAKE_PROFIT_MARKET），未按需求文档 V4.0 要求改造为限价单，在流动性不足或剧烈波动时产生严重滑点。

**问题二：孤儿单问题** -- 完全平仓后条件单（止盈/止损单）未被自动取消，原因是 `cancel_all_algo_orders()` 依赖已废弃的 `get_open_algo_orders()` API。

### 1.2 修复方案概览

| 修复编号 | 方案名称 | 涉及模块 | 优先级 |
|---------|---------|---------|--------|
| 修复一 | C方案：修复new_coin代码，市价单改限价单 | `strategies/new_coin/executor.py` | **P0** |
| 修复二 | B方案：交易层拦截警告 | `shared/binance_api.py` | **P1** |
| 修复三 | B方案：修复本地algoId管理 | `strategies/new_coin/executor.py`, `strategy.py` | **P0** |
| 修复四 | A方案：ai-tuner兜底清理 | `ai_tuner/cleanup/orphan_cleanup.py`（新增） | **P2** |

### 1.3 架构设计原则

- **最小改动原则**：尽量复用现有代码结构，不引入无关重构
- **向后兼容**：所有修改不破坏现有业务流程，不改变 API 签名
- **可配置原则**：所有业务参数通过 `config.yaml` 管理，禁止硬编码
- **幂等原则**：取消操作幂等处理，重复执行不产生副作用
- **容错原则**：关键路径有 fallback 机制，确保交易不中断

### 2.2 限价计算逻辑设计

#### 2.2.1 通用限价计算公式

所有限价单的限价计算遵循同一公式，从 `config.yaml` 读取滑点参数：

```python
# 从配置读取滑点参数（统一入口）
slippage = Decimal(str(self.config.get('trading', {}).get('limit_order_slippage', 0.001)))
```

| 场景 | 公式 | 方向说明 | 数学原理 |
|------|------|---------|---------|
| 开仓限价（做空SELL） | 限价 = 当前价 | 不应用滑点，以当前价挂单 | 卖单：限价 <= 当前价可成交 |
| 止损限价（做空BUY） | 限价 = 止损价 x (1 + slippage) | 限价略高于触发价 | 买单：限价 >= 市场价可成交 |
| 止盈限价（做空BUY） | 限价 = 止盈价 x (1 + slippage) | 限价略高于触发价 | 买单：限价 >= 市场价可成交 |
| 平仓限价（做空BUY） | 限价 = 当前价 x (1 + slippage) | 限价略高于当前价 | 买单：限价 >= 市场价可成交 |

**关键设计决策说明**：

做空策略的止损和止盈方向均为 `BUY`（买入平仓）。对于 `BUY` 方向的限价单，成交条件为 `限价 >= 当前市场价`。因此限价应略高于触发价，确保触发后能立即成交。

```
例：做空止损价 = 100 USDT, slippage = 0.001 (0.1%)
  止损限价 = 100 x (1 + 0.001) = 100.1 USDT
  当市场价 >= 100 时触发止损，限价单以 <= 100.1 的价格成交
  100.1 >= 100，因此限价单能立即成交
```

#### 2.2.2 精度处理

限价计算后必须经过 `_format_price()` 进行精度调整，确保符合交易所的 `tickSize` 要求：

```python
# 精度调整逻辑
def _format_price(self, price: Decimal, tick_size: Decimal) -> Decimal:
    normalized = tick_size.normalize()
    return (price / normalized).quantize(Decimal('1'), rounding='ROUND_HALF_UP') * normalized
```

**边界处理**：精度调整后限价可能等于触发价（当滑点过小且精度截断时）。需要确保：
- 精度调整后限价严格 >= 触发价（对于 BUY 方向）
- 如果精度调整后限价 == 触发价，记录 INFO 日志提示

#### 2.3.5 `_close_position()` -- 平仓（带市价回退容错）

```
改造前：MARKET
改造后：LIMIT（带市价回退容错机制）
```

**平仓容错机制设计**：

```
┌─────────────────────────────────────────────────────────────────┐
│                    平仓限价单执行流程                               │
│                                                                   │
│  1. 获取当前价格 current_price                                     │
│     ├── 成功 → 计算限价 = current_price × (1 + slippage)          │
│     └── 失败（价格<=0）→ 直接回退到市价单                          │
│                                                                   │
│  2. 下限价平仓单 (LIMIT, price=limit_price)                       │
│     ├── 成功 → 返回成功                                           │
│     └── 异常 → 记录警告日志，执行回退                              │
│           │                                                       │
│           └── 3. 回退到市价平仓单 (MARKET)                        │
│                 ├── 成功 → 返回成功                               │
│                 └── 失败 → 记录错误日志，返回失败                  │
└─────────────────────────────────────────────────────────────────┘
```

**代码架构**：

```python
async def _close_position(self, symbol, close_percent, reason) -> bool:
    # ... 获取持仓、计算数量等前置逻辑 ...
    
    try:
        # 获取当前价格
        ticker = await self.binance_api.get_ticker(symbol)
        current_price = Decimal(str(ticker.get('price', 0)))
        
        if current_price <= 0:
            raise ValueError(f"当前价格异常: {current_price}")
        
        # 计算限价
        slippage = Decimal(str(self.config.get('trading', {}).get('limit_order_slippage', 0.001)))
        limit_price = current_price * (Decimal('1') + slippage)
        limit_price = self._format_price(limit_price, tick_size)
        
        # 优先使用限价单
        order = await self.binance_api.place_order(
            symbol=symbol, side='BUY',
            order_type='LIMIT', quantity=close_quantity,
            price=limit_price, timeInForce='GTC'
        )
        # ... 成功处理 ...
        
    except Exception as e:
        logger.warning(f"限价平仓失败，回退市价单: {e}", symbol=symbol)
        # 回退到市价单
        try:
            order = await self.binance_api.place_order(
                symbol=symbol, side='BUY',
                order_type='MARKET', quantity=close_quantity
            )
            # ... 成功处理 ...
        except Exception as e2:
            logger.error(f"市价平仓也失败: {e2}", symbol=symbol)
            return False
```

### 2.5 边界条件矩阵

| 边界条件 | 影响 | 处理策略 |
|---------|------|---------|
| 开仓限价单未成交 | 仓位未建立 | 使用 `GTC` 时间策略，后续监控逻辑处理 |
| 止损限价计算值等于止损价 | 限价单可能无法立即成交 | 滑点默认为 0.1%，正常情况下不会相等 |
| 精度调整后限价等于触发价 | 限价单无法成交 | 记录 INFO 日志，提示调整滑点参数 |
| 平仓获取当前价异常 | 无法计算限价 | 捕获异常，直接回退到市价单 |
| 平仓限价单抛异常 | 平仓失败 | 捕获异常，回退到市价单 |
| 滑点配置为 0 | 限价 = 触发价 | 允许，记录 INFO 日志提示风险 |

### 3.4 Webhook 通知机制

#### 3.4.1 通知方法设计

在 `BinanceClient` 中新增 `_notify_market_order_warning()` 私有方法：

```python
async def _notify_market_order_warning(
    self,
    symbol: str,
    side: str,
    order_type: str,
    quantity: Optional[Decimal] = None,
    stop_price: Optional[Decimal] = None,
) -> None:
    """
    发送市价单警告通知
    
    通过策略的 webhook 发出通知，不阻塞主流程。
    通知发送失败不影响正常下单流程。
    """
    try:
        message = (
            f"【交易层警告】检测到市价单\n"
            f"交易对: {symbol}\n"
            f"方向: {side}\n"
            f"订单类型: {order_type}\n"
        )
        if quantity:
            message += f"数量: {float(quantity)}\n"
        if stop_price:
            message += f"触发价: {float(stop_price)}\n"
        message += "建议: 使用限价单避免滑点风险"
        
        # 使用 notification_client 发送通知
        # 如果 BinanceClient 未初始化 notification_client，则跳过
        if hasattr(self, 'notification_client') and self.notification_client:
            await self.notification_client.send(
                message=message,
                level="warning",
                project="default"
            )
    except Exception as e:
        logger.debug("发送市价单警告通知失败", error=str(e))
```

#### 3.4.2 通知生命周期

```
下单请求
    │
    ▼
BinanceClient.place_order()
    │
    ├── 参数校验
    ├── [市价单检测] ── 检测到 MARKET ──→ 记录警告日志
    │                                       │
    │                                       ▼
    │                               发送 webhook 通知（异步，不阻塞）
    │                                       │
    │                                   ┌───┴───┐
    │                                   │ 成功  │ 失败
    │                                   └───┬───┘
    │                                       │
    │                                   忽略（不重试）
    │
    ├── 精度调整
    ├── 参数组装
    └── API调用（正常下单，不受检测影响）
```

### 3.5 设计约束

- **不拒绝执行**：仅记录警告和发送通知，不影响正常下单流程
- **不阻塞**：通知发送失败不抛出异常，吞掉异常后继续
- **不重复通知**：同一方法调用中检测到多次市价单，每次独立记录（调用方决定频次）
- **无状态**：检测逻辑不依赖任何状态，纯参数校验

### 4.3 新增辅助方法

在 `TradingExecutor` 中新增 `_save_algo_id()` 方法，封装 algoId 存储逻辑：

```python
def _save_algo_id(self, symbol: str, role: str, algo_id: int) -> None:
    """
    保存条件单的 algoId 到本地内存
    
    Args:
        symbol: 交易对
        role: 角色 ('sl'/'tp'/'tp1'/'tp2')
        algo_id: Binance 返回的 algoId
    """
    if algo_id is None:
        return
    
    if symbol in self.position_tracking:
        if 'algo_ids' not in self.position_tracking[symbol]:
            self.position_tracking[symbol]['algo_ids'] = {}
        self.position_tracking[symbol]['algo_ids'][role] = algo_id
        logger.debug(
            "保存条件单algoId",
            symbol=symbol,
            role=role,
            algo_id=algo_id,
        )
```

### 4.4 创建条件单时保存 algoId 的流程

```
_set_stop_loss_take_profit() / _set_batch_stop_loss_take_profit()
    │
    ├── 1. 计算止损/止盈价格
    │
    ├── 2. 调用 place_conditional_order() 创建条件单
    │       │
    │       └── 返回结果 { 'algoId': 123456789, ... }
    │
    ├── 3. 调用 _save_algo_id(symbol, 'sl', algo_id)
    │       └── 写入 position_tracking[symbol]['algo_ids']['sl']
    │
    ├── 4. 调用 place_conditional_order() 创建止盈单
    │       │
    │       └── 返回结果 { 'algoId': 987654321, ... }
    │
    ├── 5. 调用 _save_algo_id(symbol, 'tp', algo_id)
    │       └── 写入 position_tracking[symbol]['algo_ids']['tp']
    │
    └── 6. 继续后续逻辑（日志记录等）
```

**关键设计点**：

1. **保存时机**：在 `place_conditional_order()` 返回后立即保存，确保不会丢失
2. **空值处理**：如果返回结果中没有 `algoId`，不保存，不报错
3. **覆盖处理**：如果同一个 `role` 已有 algoId，新的值覆盖旧的（如策略重启后补单）
4. **初始化确保**：在 `_save_algo_id()` 内部检查 `position_tracking[symbol]` 是否存在，不存在则跳过

### 4.5 平仓时取消条件单的流程

```
cancel_all_algo_orders(symbol)  ← 方法签名不变，内部逻辑重写
    │
    ├── 1. 从 position_tracking[symbol]['algo_ids'] 获取本地 algoId 列表
    │       └── 格式：{'sl': id1, 'tp1': id2, 'tp2': id3}
    │
    ├── 2. 判断是否为空
    │       ├── 空 → 直接返回，记录 INFO 日志
    │       └── 非空 → 继续
    │
    ├── 3. 遍历 algo_ids 字典，对每个 algo_id 调用 cancel_algo_order()
    │       │
    │       ├── 成功 → cancelled +1
    │       │
    │       ├── 失败（BinanceAPIError）
    │       │       ├── -2011（已不存在）→ cancelled +1（幂等）
    │       │       └── 其他错误 → failed +1，记录警告
    │       │
    │       └── 失败（其他异常）→ failed +1，记录警告
    │
    ├── 4. 清理 position_tracking[symbol]['algo_ids'] = {}
    │
    └── 5. 返回取消结果统计
```

**与 HRS PositionManager 的对比**：

| 特性 | HRS PositionManager | new_coin TradingExecutor（修复后） |

### 4.6 策略重启恢复流程

策略重启后，`position_tracking` 为空，但数据库中的持仓状态会恢复。通过 `replenish_conditional_orders` 补单后，重新保存 algoId。实际实现中，`_replenish_done` 标志控制补单逻辑只执行一次，避免重复补单：

```
策略重启
    │
    ├── 从数据库恢复持仓状态
    │
    ├── _replenish_done = False（初始状态）
    │
    ├── replenish_conditional_orders() 补单
    │       │
    │       ├── 计算 ATR（从 K 线服务获取，使用 config 中 atr_period 配置）
    │       │
    │       ├── 仅补全 TP2 条件单（不重复创建 SL 和 TP1）
    │       │   原因：SL 和 TP1 使用 closePosition=true，已与交易所绑定；
    │       │   若重复创建，会与交易所已有条件单冲突
    │       │
    │       ├── TP2 有效性检查
    │       │       ├── 价格 <= 0 → 跳过，记录警告日志
    │       │       ├── 当前价已低于 TP2 目标 → 直接市价平仓（不挂条件单）
    │       │       └── 正常 → 创建 TP2 限价条件单
    │       │
    │       ├── 精度格式化
    │       │       ├── _format_quantity()：使用 step_size 格式化数量
    │       │       └── _format_price()：使用 tick_size 格式化价格
    │       │
    │       ├── 保存新的 algoId → position_tracking[symbol]['algo_ids']['tp2']
    │       │
    │       ├── 重试机制
    │       │       ├── all_success 标志：全部成功时置 True
    │       │       └── sync_failed 标志：部分失败时记录，下次循环重试
    │       │
    │       └── _replenish_done = True（标记补单完成）
    │
    └── 正常进入监控循环
```

### 4.7 边界条件矩阵

| 边界条件 | 处理策略 |
|---------|---------|
| 条件单创建失败，algoId 为空 | `_save_algo_id()` 内部检查 None，不存储 |
| 策略重启后 `position_tracking` 为空 | `replenish_conditional_orders` 补单后保存新 algoId |
| 相同 algoId 被重复取消 | `cancel_algo_order` 的 `-2011` 错误码幂等处理 |
| 多个条件单部分取消失败 | 失败的不阻塞后续取消，记录警告日志 |
| `algo_ids` 字典为空 | 直接返回，不执行任何 API 调用 |
| 平仓后清理 `position_tracking` | 在 `cancel_all_algo_orders` 调用后，清空 `algo_ids` 字段 |

#### 5.3.3 查询策略持仓状态

```python
async def _query_strategy_states(self):
    """查询各策略当前持仓状态"""
    rows = await self.db.fetch_all("""
        SELECT strategy_name, state_data, updated_at
        FROM strategy_states
        WHERE state_key = 'main'
        ORDER BY strategy_name
    """)
    result = {}
    for row in rows:
        sn = row['strategy_name']
        state_data = row.get('state_data', {})
        if not isinstance(state_data, dict):
            state_data = {}
        positions = state_data.get('positions', {})
        if not isinstance(positions, dict):
            positions = {}
        symbols = set(positions.keys())
        result[sn] = {
            "symbols": symbols,
            "updated_at": row['updated_at'],
        }
    return result
```

### 5.4 取消订单逻辑

#### 5.4.1 _cancel_order 核心逻辑

```python
async def _cancel_order(self, order):
    """
    取消单个条件单/订单，并更新 condition_orders 表状态

    Returns:
        (bool, str): (是否成功, 错误信息或 None)
    """
    strategy_name = order['strategy_name']
    symbol = order['symbol']
    algo_id = order.get('algo_id')
    order_id = order.get('order_id')
    order_type = order.get('order_type', '')

    try:
        if algo_id is not None:
            # 条件单用 cancel_algo_order
            await self.binance.cancel_algo_order(symbol, int(algo_id))
            logger.info("孤儿条件单已取消", strategy=strategy_name, symbol=symbol,
                        algo_id=algo_id, type=order_type)
        elif order_id is not None:
            # 普通订单用 cancel_order
            await self.binance.cancel_order(symbol, str(order_id))
            logger.info("孤儿普通订单已取消", strategy=strategy_name, symbol=symbol,
                        order_id=order_id, type=order_type)
        else:
            return False, "无订单ID"

        # 标记为已取消
        await mark_order_canceled(self.db, order_id=order_id, algo_id=algo_id)
        return True, None

    except Exception as e:
        error_str = str(e)
        # -2011 已不存在 → 视为取消成功
        if "-2011" in error_str or "Order does not exist" in error_str:
            await mark_order_canceled(self.db, order_id=order_id, algo_id=algo_id)
            return True, None
        # 条件单已执行 → 标记为已执行
        if "algo" in error_str.lower() and (
            "not exist" in error_str.lower() or "invalid" in error_str.lower()
        ):
            await mark_order_executed(self.db, algo_id=algo_id, order_id=order_id)
            return True, "订单已执行"
        logger.warning("取消失败", strategy=strategy_name, symbol=symbol, error=error_str)
        return False, error_str
```

#### 5.4.2 各策略订单类型与取消 API

| 策略 | 条件单类型 | 存储字段 | 取消 API |
|------|-----------|---------|---------|
| **btc_eth** | 普通限价单（stop_loss/tp1/tp2） | `order_id` | `cancel_order(symbol, order_id)` |
| **hrs** | 条件单（sl/tp1/tp2） | `algo_id` | `cancel_algo_order(symbol, algo_id)` |
| **new_coin** | 条件单（sl/tp1/tp2） | `algo_id` | `cancel_algo_order(symbol, algo_id)` |

#### 5.4.3 幂等性与安全保护

| 保护措施 | 实现方式 |
|---------|---------|
| **避免重复取消** | 每次取消后更新 `status=CANCELED`，查询时只查 `status=OPEN` |
| **误操作保护** | 场景A：仅取消超过 `stale_hours` 未更新的策略；场景B：仅取消持仓中已不存在的 symbol |
| **异常隔离** | 单个订单取消失败不影响其他订单 |
| **日志记录** | 详细记录每次取消操作的内容和结果 |

创建止损/止盈单时，记录 `order_id` 到 `condition_orders` 表。

#### 5.8.3 HRS 策略（strategies/hrs/position_manager.py）

在 `add_algo_id()` 方法中同步写入数据库，需注入 `db` 参数。

#### 5.8.4 新币做空策略（strategies/new_coin/executor.py）

在 6 处创建条件单后同步写入 `condition_orders` 表。

### 5.9 边界条件矩阵

| 边界条件 | 处理策略 |
|---------|---------|
| 数据库连接失败 | 记录错误日志，跳过本次检查，下次重试 |
| 查询 strategy_states 返回空 | 仅处理场景A（策略无状态记录），场景B 无法判断，跳过 |
| condition_orders 表不存在 | `_ensure_table()` 自动创建，幂等操作 |
| 取消订单时 -2011 错误（已不存在） | 视为取消成功，更新 status=CANCELED |
| 取消订单时 algoId 已无效（已执行） | 更新 status=EXECUTED，视为成功 |
| 通知发送失败 | 记录错误日志，不影响下次检查 |
| 定时任务重叠 | 使用 `coalesce=True`，前一次未完成时跳过本次 |
| 多个策略同时异常 | 汇总所有异常，一次通知发送 |

### 8.2 风险与应对

| 风险 | 等级 | 影响 | 应对措施 |
|------|------|------|---------|
| 限价单未成交导致开仓失败 | 中 | 错过开仓机会 | 使用 `GTC` 时间策略；后续监控逻辑处理未成交单 |
| 止损限价单未触发导致亏损放大 | 中 | 亏损超出预期 | 滑点 0.1% 确保限价略高于触发价；可调整滑点参数 |
| 平仓限价单回退失败 | 低 | 平仓失败 | 市价单回退在 try-catch 块内，异常已被捕获 |
| 策略重启后 `position_tracking` 缺失 | 中 | 无法取消条件单 | `replenish_conditional_orders` 补单后会保存新的 algoId |
| ai-tuner 取消操作与策略冲突 | 低 | 重复取消 | 幂等处理（`-2011` 错误码视为成功） |
| 限价单方向错误导致订单不成交 | 高 | 订单不成交 | 严格代码审查，参考 V4.0 文档第 10.3 节限价方向规则 |
| condition_orders 表记录遗漏 | 中 | 孤儿单无法被检测 | 代码审查中重点检查各策略创建条件单时是否同步写入 |
| ai-tuner 中 BinanceClient 初始化失败 | 中 | 清理任务无法执行 | 初始化时检查 binance_client 是否为空，为空则跳过注册 |
