## 1. 产品概述

### 1.1 背景介绍

Binance_quantitative_trading 是一个统一的量化交易系统，旨在整合多个独立策略，实现资源共享、统一管理和高效运维。系统采用模块化单体架构，通过共享核心模块降低代码重复率，提高开发效率和系统可维护性。

### 1.2 业务目标

- **资源整合**: 统一管理K线数据、通知服务、API连接等共享资源
- **降低成本**: 避免重复订阅数据源，减少API调用次数，降低交易成本
- **提高效率**: 统一监控、统一日志、统一部署，提升运维效率
- **便于扩展**: 模块化设计，便于新增策略和功能扩展
- **风险控制**: 统一风控体系，避免策略间冲突

### 1.3 用户人群

- **量化交易员**: 使用系统进行自动化交易
- **策略开发者**: 开发和测试新的交易策略
- **系统运维人员**: 监控和维护系统运行

### 1.4 成功指标

- 系统可用性 ≥ 99.9%
- 策略启动时间 < 30秒
- 数据获取延迟 < 100ms
- API调用成功率 ≥ 99.5%
- 代码复用率 ≥ 70%

### 2.2 架构说明

#### 2.2.1 模块化单体架构

系统采用**模块化单体架构**，结合了单体架构和微服务架构的优点：

**优势**:
- **开发效率高**: 共享核心模块，避免重复开发
- **部署简单**: 策略独立部署，核心模块统一管理
- **性能优越**: 模块间直接调用，无网络开销
- **易于调试**: 统一日志和监控，问题定位快速
- **成本可控**: 资源共享，降低基础设施成本

**架构特点**:
- **共享核心模块**: 作为Python包，被所有策略引用
- **策略独立部署**: 每个策略运行在独立的Docker容器中
- **统一数据源**: 所有策略共享同一个PostgreSQL数据库
- **统一API连接**: 共享Binance API连接池

#### 2.2.2 分层设计

**策略层 (Strategy Layer)**:
- 每个策略独立运行在Docker容器中
- 策略之间完全隔离，互不影响
- 策略可以独立升级、回滚、重启
- 策略通过共享核心模块访问公共资源

**共享核心模块层 (Shared Core Layer)**:
- 提供统一的服务接口
- 封装通用业务逻辑
- 管理共享资源连接
- 提供工具函数和配置管理

**基础设施层 (Infrastructure Layer)**:
- 提供数据库服务
- 提供容器运行环境
- 提供日志收集和存储
- 提供监控和告警服务

#### 2.2.3 回测引擎 V2 架构（新增）

**设计原则**:
- **薄层引擎**: 回测引擎只负责"时间推进 + 成交模拟"，不包含策略逻辑
- **业务复用**: 通过 `sys.path` 注入直接复用 `strategies/` 下的生产级业务模块
- **严格防未来函数**: `ExchangeSimulator.get_klines()` 基于 `current_time` 严格截断数据
- **配置驱动**: 所有参数通过 `config.yaml` 统一管理，杜绝硬编码

**核心组件**:

| 组件 | 文件 | 职责 |
|------|------|------|
| BacktestEngineV2 | `backtest/grid/backtest_engine.py` | 回测主引擎，时间线推进 |
| ExchangeSimulator | `backtest/grid/exchange_simulator.py` | 模拟交易所，提供 BinanceClient/KLineService 兼容接口 |
| TrailingStopSimulator | `backtest/grid/trailing_stop_simulator.py` | 移动止盈模拟器，三步状态机 |
| BacktestMarketStateWrapper | `backtest/grid/backtest_engine.py` | 封装 MarketStateDetector，适配回测场景 |
| OrderSimulator | `backtest/grid/exchange_simulator.py` | 订单模拟撮合（限价单成交判定） |

**ETHUSDT 专版**:
- 回测引擎内置 `_apply_ethusdt_defaults()` 方法
- 自动覆盖 ETHUSDT 的专用网格参数（基础20格、范围8-30、ATR倍数4x）

```python
class NotificationClient:
    def __init__(self, service_url: str, use_direct_webhook: bool = True):
        # 从环境变量加载项目 -> Webhook URL 映射
        self._webhook_mapping = self._load_webhook_mapping()
        # {
        #   "grid":      os.getenv("FEISHU_WEBHOOK_GRID"),
        #   "btc_eth":   os.getenv("FEISHU_WEBHOOK_BTC_ETH"),
        #   "new_coin":  os.getenv("FEISHU_WEBHOOK_NEW_COIN"),
        #   "default":   os.getenv("FEISHU_WEBHOOK"),
        # }

    async def send(self, message: str, level: str = "info", project: str = "default"):
        if self.use_direct_webhook and project in self._webhook_mapping:
            # 直接发送到项目专属飞书群
            return await self._send_to_feishu_webhook(
                webhook_url=self._webhook_mapping[project],
                message=message, level=level
            )
```

#### 3.2.2 策略接口规范

所有策略必须实现统一的接口：

```python
from abc import ABC, abstractmethod

class BaseStrategy(ABC):
    """策略基类"""

    def __init__(self, config: dict):
        """初始化策略"""
        self.config = config
        self.binance_api = None
        self.db = None
        self.kline_service = None
        self.notification = None

    @abstractmethod
    def initialize(self):
        """初始化策略资源"""
        pass

    @abstractmethod
    def on_kline(self, kline: dict):
        """K线更新回调"""
        pass

    @abstractmethod
    def on_order(self, order: dict):
        """订单更新回调"""
        pass

    @abstractmethod
    def on_trade(self, trade: dict):
        """成交更新回调"""
        pass

    @abstractmethod
    def run(self):
        """运行策略"""
        pass

    @abstractmethod
    def stop(self):
        """停止策略"""
        pass
```

#### 3.2.3 BTC/ETH 策略模块架构（v6.19+ 新增）

BTC/ETH 策略（MTPCS）在 v6.19 版本中引入了市场状态识别机制，在 v6.20 版本中新增了震荡市策略子系统，实现了「趋势策略 + 震荡策略」双模式切换。

##### 市场状态识别子模块（market_state.py）

**文件位置**: `strategies/btc_eth/market_state.py`

**职责**: 基于5条件判定当前市场状态，输出 `STRONG_TREND`（强趋势）或 `RANGING`（震荡）。

**5条件判定规则**:

| 序号 | 指标 | 判定逻辑 | 权重 |
|------|------|----------|------|
| 1 | ADX | ADX > 阈值 → 趋势，否则 → 震荡 | 核心 |
| 2 | 布林带宽度（BB Width） | BB宽度 < 阈值 → 震荡，否则 → 趋势 | 核心 |
| 3 | 价格变化率 | 价格变化率 < 阈值 → 震荡 | 辅助 |
| 4 | EMA21 斜率 | EMA21斜率绝对值 < 阈值 → 震荡 | 辅助 |
| 5 | K线形态确认 | 连续小实体K线 → 震荡确认 | 辅助 |

**输出接口**:
```python
class MarketState:
    """市场状态识别结果"""
    state: str          # "STRONG_TREND" 或 "RANGING"
    confidence: float   # 判定置信度 0.0-1.0
    details: dict       # 各条件判定明细
```

##### 震荡市策略子系统（strategy.py）

**文件位置**: `strategies/btc_eth/strategy.py`

**职责**: 在震荡市场环境下，执行低风险、高频次的小额交易策略。

**核心方法**:

| 方法 | 职责 |
|------|------|
| `_analyze_ranging()` | 震荡市策略入口，协调各子方法 |
| `_check_ranging_frequency()` | 频率控制，限制震荡市交易频次（冷却期、每日上限） |
| `_calculate_ranging_score()` | 评分体系，综合RSI、布林带位置、K线形态等计算震荡交易信号评分 |
| `_determine_ranging_direction()` | 方向判定，根据RSI超买超卖、布林带位置等确定做多/做空方向 |

**震荡策略参数**（通过 `ranging_strategy` 配置节管理）:
- 单笔仓位：趋势策略的 50%
- 止盈目标：0.5%-1.0%（快速止盈）
- 止损范围：0.3%-0.5%（严格止损）
- 冷却期：30分钟（高频交易）
- 每日上限：10笔

##### 策略模式切换流程

```
┌──────────────────────────────────────────────────────────────┐
│                      每根K线触发                              │
│                          │                                    │
│                          ▼                                    │
│              ┌───────────────────────┐                       │
│              │  MarketState.detect() │                       │
│              │  5条件市场状态判定     │                       │
│              └───────────┬───────────┘                       │
│                          │                                    │
│              ┌───────────▼───────────┐                       │
│              │   strategy_mode = ?   │                       │
│              └───────────┬───────────┘                       │
│                          │                                    │
│          ┌───────────────┼───────────────┐                   │
│          ▼                               ▼                    │
│  ┌───────────────┐               ┌───────────────┐           │
│  │ STRONG_TREND  │               │   RANGING     │           │
│  │ 趋势策略模式   │               │ 震荡策略模式   │           │
│  ├───────────────┤               ├───────────────┤           │
│  │· 回调确认     │               │· 评分计算     │           │
│  │· 成交量验证   │               │· 频率控制     │           │
│  │· S/A/B/C评级  │               │· 方向判定     │           │
│  │· 冷却期4h     │               │· 冷却期30min  │           │

│  └───────────────┘               └───────────────┘           │
│          │                               │                    │
│          └───────────────┬───────────────┘                   │
│                          ▼                                    │
│              ┌───────────────────────┐                       │
│              │     下单 / 跳过       │                       │
│              └───────────────────────┘                       │
└──────────────────────────────────────────────────────────────┘
```

**切换规则**:
1. 每根K线触发时，先执行 `MarketState.detect()` 判定市场状态
2. 根据 `strategy_mode` 分流到对应的策略处理逻辑
3. 趋势策略模式下，震荡策略不执行；震荡策略模式下，趋势策略不执行
4. 状态切换时，清空对方策略的中间状态（如回调计数、评分缓存等）
5. 通过飞书通知推送模式切换事件

##### 订单执行模块（v6.20.3 新增）

**文件位置**: `strategies/btc_eth/strategy.py`

**职责**: 统一管理所有订单类型的执行，全部使用限价单，消除市价单滑点风险和额外手续费。

**订单类型与执行方式**:

| 订单类型 | 币安订单类型 | 限价计算方式 | 说明 |
|----------|-------------|-------------|------|
| 开仓单 | `LIMIT` | 买一价（做多）/ 卖一价（做空） | 沿用 v6.13.2 方案 |
| 止损单 | `STOP` | `_calculate_stop_limit_price()` | 止损限价单，偏移 0.2% |
| 止盈单 | `TAKE_PROFIT` | `_calculate_tp_limit_price()` | 止盈限价单，偏移 0.15% |
| 平仓单 | `LIMIT` | 买一价（平多）/ 卖一价（平空） | 全部平仓原因统一使用限价单 |

**止损限价偏移计算**（`_calculate_stop_limit_price`）:

```
做多止损（SELL）：限价 = 触发价 × (1 - 0.002)  // 触发价向下偏移 0.2%
做空止损（BUY）：限价 = 触发价 × (1 + 0.002)   // 触发价向上偏移 0.2%
```

**止盈限价偏移计算**（`_calculate_tp_limit_price`）:

```
做多止盈（SELL）：限价 = 触发价 × (1 - 0.0015)  // 触发价向下偏移 0.15%
做空止盈（BUY）：限价 = 触发价 × (1 + 0.0015)   // 触发价向上偏移 0.15%
```

**平仓限价单执行流程**（v6.20.3 超时重试机制）:

```
  下限价平仓单
      │
      ▼
  轮询等待成交（默认 10 秒超时，2 秒间隔）
      │
      ├── 已成交 → 结束
      │
      └── 超时未成交
            │
            ▼
        ┌── 重试循环（最多 3 次）──┐
        │                          │
        │  取消未成交的旧单         │
        │  等待 2 秒               │
        │  重新下限价单             │
        │  轮询等待成交             │
        │  已成交 → 跳出循环       │
        │                          │
        └──────────────────────────┘
            │
            ▼
        全部重试结束仍不成交 → 记录错误日志，不再降级为市价单
```

**配置参数**（`close_limit_order` 配置节）:

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `enabled` | true | 是否启用限价平仓 |
| `timeout_seconds` | 10 | 首次等待成交超时（秒） |
| `poll_interval_seconds` | 2 | 轮询间隔（秒） |
| `max_retries` | 3 | 超时后最大重试次数 |
| `retry_interval_seconds` | 2 | 重试间隔（秒） |
| `applicable_reasons` | 全部 8 种原因 | 适用限价平仓的平仓原因列表 |

**手续费对比**:

| 场景 | 旧方案（v6.20） | 新方案（v6.20.3） | 节省 |
|------|----------------|-------------------|------|
| 止损单 | `STOP_MARKET`（taker 0.05%） | `STOP`（maker 0.02%） | 60% |
| 止盈单 | `TAKE_PROFIT_MARKET`（taker 0.05%） | `TAKE_PROFIT`（maker 0.02%） | 60% |
| 平仓单（部分） | `MARKET`（taker 0.05%） | `LIMIT`（maker 0.02%） | 60% |

**与 v6.13.2 的区别**:

v6.13.2 仅将开仓单从市价单改为限价单。v6.20.3 在此基础上，将止损单、止盈单和全部平仓单也统一改为限价单，实现了全量委托单的限价化。同时，v6.20.3 取消了 v6.13.2 中"限价单超时降级为市价单"的兜底逻辑，改为纯限价单重试机制，确保永远不会产生 taker 手续费。

## 8. 容错设计

### 8.1 异常处理策略

| 异常类型 | 处理策略 | 重试次数 | 降级方案 |
|---------|---------|---------|---------|
| 网络超时 | 自动重试 | 3次 | 使用缓存数据 |
| API限流 | 等待后重试 | 5次 | 降低请求频率 |

### 8.2 数据一致性保障

- **事务处理**: 关键操作使用数据库事务
- **幂等性**: 重复操作不会产生副作用
- **状态检查**: 操作前检查状态有效性
- **数据校验**: 严格校验数据格式和范围

### 8.3 服务降级策略

- **K线服务降级**: 使用本地缓存数据
- **通知服务降级**: 只记录日志，不发送通知
- **API服务降级**: 降低请求频率，延长超时时间
- **数据库降级**: 使用内存缓存，延迟写入
