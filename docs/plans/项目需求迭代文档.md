### 3.2 V2.8 趋势过滤增强

#### 3.2.1 变更背景

V2.8 版本针对趋势过滤机制进行增强，核心目标是：**在标准模式入场前，增加 EMA 斜率检查作为第二道趋势过滤防线**，防止在 EMA 趋势方向与开仓方向相悖时入场，降低逆势交易风险。

#### 3.2.2 config.yaml 参数变更

| 参数路径 | 旧值 | 新值 | 说明 |
|----------|:----:|:----:|------|
| `scoring.technical.min_primary_pattern_score` | 1.0 | **2.5** | 提高基础形态评分门槛，需更高评分的技术形态才能触发信号 |
| `scoring.trend_filter.long.max_deviation` | 0.97 | **0.99** | 做多价格偏离 EMA20 上限从 -3% 收紧至 -1% |
| `scoring.trend_filter.short.max_deviation` | 1.03 | **1.01** | 做空价格偏离 EMA20 上限从 +3% 收紧至 +1% |
| `scoring.trend_filter.ema_slope` | （无） | **新增配置段** | 新增 EMA 斜率检查模块 |

#### 3.2.3 新增 ema_slope 配置段

```yaml
scoring:
  trend_filter:
    ema_slope:
      enabled: true              # 是否启用 EMA 斜率检查
      period: 3                  # 计算最近 3 根 4h K 线的 EMA20 平均斜率
      min_slope_for_long: -0.0005  # 做多最低斜率要求（允许轻微下行，但不超过 -0.05%）
      max_slope_for_short: 0.0005  # 做空最高斜率要求（允许轻微上行，但不超过 +0.05%）
```

#### 3.2.4 scoring_engine.py 新增方法

| 方法 | 功能描述 |
|------|----------|
| `_calc_ema_slope(klines, period, slope_period)` | 计算 EMA20 最近 3 根 K 线的平均变化率。斜率 = (EMA_last - EMA_first) / (slope_period * EMA_first)，正值表示 EMA 上行，负值表示 EMA 下行 |
| `_check_ema_slope(direction, klines_4h, ema_period)` | 检查 EMA 斜率是否支持开仓方向。做多时要求斜率 >= min_slope_for_long，做空时要求斜率 <= max_slope_for_short |
| `_check_standard_trend_filter(direction, current_price_4h, ema_4h, klines_4h)` | 两步过滤流程：第一步进行价格偏离检查（继承原有逻辑），第二步进行 EMA 斜率检查（新增 V2.8 逻辑） |

#### 3.2.5 趋势过滤流程（V2.8）

标准模式（standard/semi_emm）入场前执行以下两步过滤：

```
第 1 步：价格偏离过滤
  - 做多：当前价格 >= EMA20 × 0.99（较 V2.5 收紧，原为 0.97）
  - 做空：当前价格 <= EMA20 × 1.01（较 V2.5 收紧，原为 1.03）

第 2 步：EMA 斜率过滤（V2.8 新增）
  - 计算 EMA20 最近 3 根 4h K 线的平均变化率
  - 做多：EMA 斜率 >= -0.0005（允许轻微下行，趋势不能明显向下）
  - 做空：EMA 斜率 <= 0.0005（允许轻微上行，趋势不能明显向上）

两步过滤均通过 → 允许入场
任一过滤未通过 → 禁止入场，记录失败原因
```

#### 3.2.6 技术面评分门槛调整

- `min_primary_pattern_score` 从 1.0 提高至 **2.5**：基础形态（含替代形态）的最低评分要求提高，确保只有具有足够技术面支撑的形态才能触发信号，降低低质量信号的入场概率。

#### 3.2.7 影响范围

| 影响项 | 说明 |
|--------|------|
| 标准模式趋势过滤 | 两步过滤（价格偏离 + EMA 斜率），仅在 standard/semi_emm 模式下生效 |
| EMM 模式 | 不受影响，EMM 使用独立的极端市场过滤逻辑 |
| LV-RM 模式 | 使用独立的 LV-RM 趋势过滤逻辑（含 EMA 斜率合并检查） |
| 信号质量 | 基础形态评分门槛提高，低质量信号减少 |
| 入场频率 | 预期降低，因价格偏离收紧 + EMA 斜率过滤会过滤掉部分边缘信号 |

### 3.3 V2.8.1 趋势过滤反转模式修复

#### 3.3.1 问题背景

V2.8 的 EMA 斜率检查要求做多时 EMA 斜率 >= -0.05%（不能有明显下行），做空时 EMA 斜率 <= 0.05%（不能有明显上行）。但 HRS 是**反转策略**，其交易方向与趋势相反：

- **做多**：买在价格低于 EMA20 的下跌中 → EMA 斜率通常为负
- **做空**：卖在价格高于 EMA20 的上涨中 → EMA 斜率通常为正

EMA 斜率检查是**趋势跟踪机制**，与反转策略的"逆势交易"理念存在根本性冲突，导致 V2.8 部署后 HRS 策略无任何开仓信号。

#### 3.3.2 修复方案

**趋势过滤反转模式（reversal_mode）**：新增 `reversal_mode` 配置参数，使趋势过滤方向与反转策略一致。

**scoring_engine.py 变更：**

| 变更 | 说明 |
|------|------|
| `_check_lv_rm_trend_filter` 新增 `reversal_mode` 参数 | 反转模式下做多允许价格低于 EMA20，做空允许价格高于 EMA20 |
| `_check_standard_trend_filter` 传入 `reversal_mode` | 标准模式趋势过滤方向与反转策略一致 |
| 反转模式下跳过 EMA 斜率检查 | 仅保留价格偏离过滤作为趋势保护 |

**config.yaml 参数变更：**

| 参数路径 | 旧值 | 新值 | 说明 |
|----------|:----:|:----:|------|
| `scoring.trend_filter.reversal_mode` | （无） | `true` | 启用反转模式趋势过滤 |
| `scoring.trend_filter.long.min_price` | （无） | `1.01` | 反转做多上限：EMA20 × 1.01 |
| `scoring.trend_filter.long.max_deviation` | 0.99 | `0.97` | 反转做多下限：EMA20 × 0.97 |
| `scoring.trend_filter.short.max_price` | （无） | `0.99` | 反转做空下限：EMA20 × 0.99 |
| `scoring.trend_filter.short.max_deviation` | 1.01 | `1.03` | 反转做空上限：EMA20 × 1.03 |
| `scoring.technical.min_primary_pattern_score` | 2.5 | `2.0` | 降低形态评分门槛，允许偏弱形态通过 |

### 3.4 V2.8.3 总持仓保证金比例上限检查

#### 3.4.1 问题背景

`config.yaml` 中定义了 `position_sizing.total.account_ratio_cap: 0.30`（总持仓保证金上限 = 账户余额 × 30%），但**没有任何代码读取该配置**。现有代码仅读取 `position_sizing.single`（单笔仓位限制），总持仓保证金不受控制。

同时，`ai_tuner/config.yaml` 中 HRS 的资金分配比例为 `fallback.ratios.hrs: 0.20`（20%），但 HRS 的 config 中写的是 30%，两者不一致。

#### 3.4.2 修复方案

**strategy.py 变更：** 在 `_open_position` 方法开仓前增加总持仓保证金比例上限检查：

```python
# 读取 config.yaml 中的配置
total_sizing_config = self.config.get("position_sizing", {}).get("total", {})
total_ratio_cap = total_sizing_config.get("account_ratio_cap")

# 计算上限
max_total_margin = balance * total_ratio_cap

# 计算当前持仓总保证金 + 新仓位保证金
if current_total_margin + new_margin > max_total_margin:
    # 跳过开仓，记录日志
```

**config.yaml 参数变更：**

| 参数路径 | 旧值 | 新值 | 说明 |
|----------|:----:|:----:|------|
| `position_sizing.total.account_ratio_cap` | 0.30 | **0.20** | 与资金分配比例 20% 保持一致 |

#### 3.4.3 影响范围

| 影响项 | 说明 |
|--------|------|
| 总持仓保证金 | 受 `position_sizing.total.account_ratio_cap` 限制，不超过账户余额 × 比例 |
| 开仓决策 | 总保证金超限时跳过开仓，记录日志 |
| 配置来源 | 动态读取 `config.yaml`，修改配置后重启容器生效，无需修改代码 |

#### 3.4.4 月度资金分配自动同步

`position_sizing.total.account_ratio_cap` 由每月运行的 AI 资金分配系统自动同步更新：

**`ai_tuner/allocation/config_updater.py` 变更：** `_update_strategy_configs` 方法在每月写入 `capital_limits` 时，同步写入 `position_sizing.total.account_ratio_cap`：

```python
adjustments = {
    "capital_limits": capital_limits,                    # 原有的月度限额
    "position_sizing.total.account_ratio_cap": ratio,    # 新增：同步总保证金比例上限
}
```

**同步规则：** `position_sizing.total.account_ratio_cap` = 当月分配比例（`allocated_ratio`）

**示例：**
- 首月：HRS 分配比例 20% → `account_ratio_cap = 0.20`
- 次月：HRS 排名第 3，分配比例 20% → `account_ratio_cap = 0.20`
- 次月：HRS 排名第 1，分配比例 40% → `account_ratio_cap = 0.40`

这样每次分配跑完后，`config.yaml` 中的 `position_sizing.total.account_ratio_cap` 会自动更新为最新分配比例，策略代码无需任何修改。

## 7. 看板策略级盈亏/止盈/委托口径统一修复（v6.33，2026-09-20）

### 7.3 顺带修复：时区日期归属 bug

### 7.5 收益率期初口径修复（v6.33.1，2026-09-21）

> 本子节在 v6.33 看板口径统一（7.1-7.4）基础上，进一步修复"本期净盈亏 42.87 vs 总盈亏 -55.78"的期初基准错位问题。注意：此差异本身有一半属正常——两个区域本就是不同口径（详见下文），重大异常主要由期初基准错位放大。

#### 7.5.1 问题背景

dashboard 月度看板出现"本期净盈亏 42.87"与"总盈亏 -55.78"悬殊不一致，根因有二：

1. **口径本就不同（正常差异）**：本期净盈亏来自 `get_account_returns`（`equity_snapshot` 净资产快照增量，含**未实现盈亏与出入金**）；总盈亏来自 `trade_records` 已实现盈亏聚合。两者本身不应相等，属预期现象。
2. **期初基准错位（严重 bug）**：`equity_snapshot` 快照任务 9/10 才上线，9/1-9/9 无快照。原 `get_account_returns` 对周/月/年取"周期起始日**及之后最早一条快照**"作为兜底，导致月度期初被错取为 9/10 的 518.75。于是本月净盈亏只算了 9/10-9/20 十一天，**漏算 9/1-9/9（含 HRS 大量亏损）**，造成悬殊差异。

#### 7.5.2 修复方案

`dashboard/backend/services/data_service_docker.py` 的 `get_account_returns` 期初快照改为**严格取周期起点日**：

- 日 = 昨日、周 = 本周一、月 = 本月 1 号、年 = 本年度 1/1；
- 周期起点无快照即标记 `yield_unavailable=true`，前端显示"--"并提示"历史数据积累中"，不再用"周期起始日之后最早一条"做错误兜底。

#### 7.5.3 补录尝试与决策（不补录、标记不可用）

曾尝试从 Binance `income` 反推补录 9/1-9/9 净资产快照，但**实测偏差 -10.74 USDT**：

- PM 账户净资产含**未实现浮动盈亏**，而 `income` 只含**已实现**部分，两者无法互相反推；
- PM 账户无官方历史净资产快照接口（`sapi accountSnapshot` 仅覆盖普通合约账户）。

故放弃补录方案，采用"标记不可用"。自 10 月 1 日起系统自动积累快照，**下月起月度口径完全正确**。

#### 7.5.4 验证结果

- 线上 `monthly` 接口返回 `yield='--'` / `yield_unavailable=true` / `period_pnl=null`；
- `daily` 正常（-3.0%、期初 559.98、净盈亏 -16.84）；
- dashboard-api 容器五层部署验证通过（容器健康 / 镜像 ID / VERSION / 关键文件 MD5 / 日志 0 错误）。

## 8. 佣金落库为 0 的事后回填修复（v6.34，2026-09-21）

> 状态：**已代码实现、待部署**。本功能为 dashboard 数据后台的"佣金回填"修复，涉及 `shared/` 公共逻辑，按部署规范需全量重建策略容器 + dashboard，并执行五层验证。

### 8.1 问题背景

币安合约 / PM 账户在**下单接口**返回的响应中**不含 `commission` 字段**（佣金只在 `userTrades` 成交明细接口返回）。导致：

- `trading.trade_records.commission` 列恒为 0；
- dashboard 看板"总佣金"恒为 0，无法反映真实交易成本。

### 8.2 修复方案（用户拍板）

采用**事后回填**策略，**不在下单时获取佣金**（避免拉长下单链路、引入下单延迟）。

#### 8.2.1 公共逻辑：`shared/trade_logger.py`

新增公共方法：

```python
TradeLogger.reconcile_commissions(binance_client, lookback_hours=24)
```

处理逻辑：

1. 查询最近 `lookback_hours` 小时内 **`commission=0` 且 `order_id` 非空** 的行；
2. 按 `(symbol, order_id)` 去重；
3. 调用 `get_user_trades` 累加该订单的真实佣金；
4. **幂等 UPDATE**：仅当该行 `commission` 仍为 0 时才写入回填值，避免重复累加/覆盖。

#### 8.2.2 公共只读方法：`shared/binance_api.py`

新增 `get_user_trades` 只读方法，按账户类型路由：

- **PM 账户**：`/papi/v1/um/userTrades`
- **普通合约账户**：`/fapi/v1/userTrades`

#### 8.2.3 调度宿主：dashboard 后端

- 新增任务脚本 `services/commission_reconcile_job.py`；
- 在 `main_docker.py` 中注册 APScheduler `IntervalTrigger` 定时任务；
- 默认频率：**每 1 小时**执行一次，回填窗口 **24 小时**；
- 周期 / 窗口通过环境变量配置：
  - `COMMISSION_RECONCILE_INTERVAL_SECONDS`（周期，秒）
  - `COMMISSION_RECONCILE_LOOKBACK_HOURS`（回填窗口，小时）

### 8.3 覆盖局限

- 仅回填 **`order_id` 非空** 的行（以开仓单为主）；
- **交易所条件单平仓**（成交使用新的 `orderId`，库中无对应行）佣金**无法按 order_id 归集**，此部分留待后续深化处理。

### 8.4 部署说明

- 本次改动涉及 `shared/` 公共代码，按部署规范需**全量重建策略容器 + dashboard**；
- 执行五层部署验证（容器状态 / 镜像 ID / VERSION / 关键文件 MD5 / 日志无错误）。

### 8.5 明确不处理

- **grid 不直接交易，故不落库佣金，不修复**（用户明确要求）。

## 9. 架构隐患记录：数据后台调度过于集中（2026-09-21）

> **性质**：设计隐患登记（dashboard 数据后台调度架构），非本次功能代码变更。

### 9.1 隐患描述

当前所有**数据后台任务**的 APScheduler 调度实例全部集中在：

```
dashboard/backend/main_docker.py
```

这些定时任务包括但不限于：

- 净资产快照；
- 指标预计算；
- 持仓对账；
- 佣金回填（见本迭代 §8）。

### 9.2 风险

- **dashboard 撤掉后，这些定时任务全部停摆**，数据后台能力整体失效；

### 9.3 正确方向（建议）

1. **独立数据后台宿主**，承载上述定时任务；
2. **dashboard 退化为纯展示**（仅承载查询渲染）；
3. 公共逻辑已沉淀在 `shared/`，具备可移植性，迁移成本可控。

## 10. 策略资金限额强制执行（方案 D，2026-09-21）

### 10.1 背景

线上事故：ai-tuner 月度给 `new_coin` 分配 156.33 USDT，但该策略实际占用保证金达 249 USDT（超限 59%）。根因是"分配结果没有任何一条通路能真正约束实盘开仓"——部署覆盖、口径混用、内存态占用失真、幽灵配置、重复开仓、上报口径错误。本次落地**方案 D 资金限额强制执行**，让月度分配额度成为实盘开仓的硬约束。需求见 [策略资金限额强制执行需求文档](../requirements/capital_allocation/策略资金限额强制执行需求文档.md)。

### 10.2 核心实现

| 项 | 内容 |
|----|------|
| **统一保证金口径** | `margin = \|positionAmt\| × markPrice × contractSize / leverage`（全项目唯一，见 `shared/position_baseline.py`） |
| **限额优先级链** | DB `public.capital_allocation` 当月 `active` 记录 `entries[*].allocated_amount` → 策略 config `capital_limits.monthly_limit` → `trading.total_position_margin_limit`（静态兜底）→ 三级均不可用则 **fail-open 放行并告警**。**取第一个可用值，不做 min**（决策 D5/D2） |
| **公共函数** | `shared/position_baseline.py` 新增 `calc_position_margin` / `calc_occupied_margin` / `calc_graded_positions_margin` / `check_entry_within_limit` / `build_contract_size_map` / `build_short_positions` / `rebuild_from_exchange` |
| **基线同步** | 新增 `strategies/new_coin/strategy.py::_sync_baseline_to_tracking`：基线重建后把每个持仓币种的 `entry_price`/`entry_quantity`/`entry_time` 写入 `executor.position_tracking`，保留已有 `algo_ids`/`atr`（满足 AC-3，修复"重启后占用记为 0"缺口） |
| **杠杆严格校验** | `strategies/new_coin/executor.py` 不再 `get('leverage', 2)` 猜测；缺失/≤0/非数值 → `logger.error` + `_leverage_valid=False` + `execute_short` 拒绝开仓 |
| **基线就绪标志** | `executor.baseline_ready` 初值由 `True` 改为 `False`（与注释一致），重建完成前禁止开新仓 |
| **缩仓规则** | 额度不足按剩余额度缩仓；缩仓后保证金 < `trading.min_position_margin`（`new_coin` = 25.0）则拒开 |
| **删除幽灵配置** | 删除 `new_coin` 段 `trading.max_positions`（`grid`/`hrs` 段保留，`hrs` 段被 `hrs_adapter.py` 用作回撤基数） |
| **新增配置** | 各策略 `capital_limits.{db_cache_ttl_seconds: 300, db_query_timeout_seconds: 3.0}`；`new_coin` 新增 `trading.min_position_margin: 25.0`、`trading.duplicate_symbol_notify_window_seconds: 3600` |
| **静态兜底值** | `btc_eth` 210 / `btc_eth_aggressive` 210 / `hrs` 110 / `new_coin` 150（USDT） |
| **ai_tuner 适配** | `new_coin_adapter.py` 回撤基数由 `single_position_margin × max_positions` 改为 `trading.total_position_margin_limit` |

### 10.3 已知风险（本次不修）

**btc_eth 与 btc_eth_aggressive 共用同一份月度分配额度**，但两策略各自只统计自身占用保证金，会导致**合计占用可超月度额**。用户已明确本次不修复，作为已知风险记录。

### 10.4 docker 挂载事实（解释为何必须运行时读 DB）

`btc-eth-strategy`、`btc-eth-aggressive-strategy`、`new-coin-strategy` 三个容器**均无 `config.yaml` 挂载**（config 打进镜像，需重建镜像才生效）；仅 `hrs-strategy` 挂载了 `./strategies/hrs/config.yaml:/app/strategies/hrs/config.yaml:rw`。因此 AI 月度分配写宿主机 config 对前三者不生效，**必须运行时读 DB**（DB 为单一真相来源，是方案 D 的必要性依据）。

### 10.5 验收结果

- 单元测试：`547 passed, 1 xfailed`（全量通过）
- 代码审查：已通过（无硬编码、无重复代码、无幽灵参数/配置）
- 部署：涉及 `shared/`，按变更范围分析需重建 `btc_eth` / `btc_eth_aggressive` / `hrs` / `new_coin` / `ai-tuner` 共 5 个容器
