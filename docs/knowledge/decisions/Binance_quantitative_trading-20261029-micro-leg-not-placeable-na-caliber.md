# 微仓比例腿数量取整为 0 时按 N/A 处理，不补足最小下单量

## 背景

按比例拆分的止盈腿在微仓下会被精度截断为 0（如 `initial 0.03 × TP1 比例 0.3` 按步长 0.01 取整得 0），交易所拒绝零数量订单。此时该腿既不可能挂出，又被保护完整性判定计为缺失，导致补挂重试耗尽并持续告警（2026-10-27 `trading_system-btc_eth_aggressive` 真实发生，见关联 issue）。

## 备选方案

- **A 补足到最小下单量**：把该腿数量抬到 1 个步长。缺点：改变开仓后的实际止盈比例，等于悄悄放大该腿仓位，与 `initial_quantity × 比例` 的口径不符。
- **B 按比例减仓清零**：识别为微仓后直接平掉整个仓位（沿用 R06/D3 的「微仓清零」思路）。缺点：为一条挂不出的止盈腿牺牲整笔持仓，代价与风险不对称。
- **C 视为 N/A**：记录该腿不可挂、从完整性判定中豁免，不补足、不减仓。

## 决策

采用 **C** 的方向：取整为 0 的 TP 腿记为 N/A（`PositionState.not_placeable_legs`），完整性判定与缺失列举均豁免；硬止损始终全量保护。软件 TP1 数量同样取整为 0 时会全仓平仓；此口径已经独立复审并随 `174de235` 部署。

## 理由

- 该腿经济上不存在对应可下单数量，「挂不出」不等于「保护缺失」，不应触发补挂重试与耗尽告警。
- 不人为放大单腿数量，避免止盈比例失真；也不为一条腿清仓，避免过度反应。
- 硬止损是全量仓位的保护底线，不受该口径影响，风险敞口未被放大。

## 后果

- 2026-10-29 复审补充：现有软件 TP1 数量取整为 0 时会改为**全仓平仓**，并非维持原目标比例。实现新增 TP 等级持久化与旧单保守识别，避免把唯一 TP2 误认作 TP1；生产活跃仓位旧单已逐单对账并迁移，随后随 `174de235` 部署，并已上线生产容器 `925d6693`（`DEPLOY_TIME=2026-10-29 07:38:27 UTC`、`DEPLOY_ID=00008101`），部署后 18 小时补挂耗尽告警 0 次。

- 收益：补挂重试恢复收敛，告警噪声消除；口径与实际可交易量一致。
- 技术债：`not_placeable_legs` **仅内存态、不落库**，进程重启后按当前持仓量与精度重新判定；TP 单等级现已持久化，旧无等级单保持保守处理。N/A 腿在交易所侧确无对应止盈单，止盈只能由软件侧逻辑执行。加仓时重新评估可挂性。
