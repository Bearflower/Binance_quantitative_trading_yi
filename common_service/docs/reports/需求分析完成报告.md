## 📊 需求总结

### 服务对象（5 个系统）

| 系统名称 | 使用服务 | 集成方式 |
|---------|---------|---------|
| BTC/ETH 交易系统 | K 线数据 + 通知 | API 调用 |
| 新币做空系统 | K 线数据 + 通知 | API 调用 |
| 网格交易系统 | K 线数据 + 通知 | API 调用 |
| 服务器巡检系统 | 通知 | API 调用（Shell） |
| A 股筛选系统 | 通知 | API 调用 |

### 核心功能

#### K 线数据服务

**数据采集**:
- 支持币种：BTCUSDT, ETHUSDT, BNBUSDT（可扩展）
- 支持周期：15m, 1h, 4h, 1d
- 采集频率：按周期自动采集
- 限流保护：遵守币安 API 限流规则

**指标计算**:
- 基础指标：MA(5/10/20/60), EMA(5/10/20), RSI(14), MACD
- 高级指标：ATR(14), 布林带 (20,2), 成交量均线

**数据存储**:
- PostgreSQL 14+ 分区表
- 按币种 + 周期分区
- 数据保留策略：30 天（做空系统）或 180 天（其他）

**API 接口**:
- GET /api/v1/klines - 查询 K 线数据
- GET /api/v1/indicators - 查询指标数据
- GET /api/v1/health - 健康检查

#### 通知服务

**消息发送**:
- 统一接口：POST /api/v1/send
- 支持格式：text, markdown, card
- 支持级别：info, warning, error
- 5 个项目独立 webhook 配置

**异步队列**:
- Redis 消息队列
- 后台 Worker 异步处理
- 队列容量：10000 条

**可靠性**:
- 错误重试：最多 3 次，递增延迟
- 频率控制：60 条/分钟（可配置）
- 配置热更新：支持不重启更新

**API 接口**:
- POST /api/v1/send - 发送消息
- GET /api/v1/queue/status - 队列状态
- GET /api/v1/health - 健康检查

### 性能指标

| 指标 | 目标值 | 测量方式 |
|------|-------|---------|
| K 线 API 响应时间 | < 500ms | 95% 请求 |
| 通知 API 响应时间 | < 100ms | 消息入队 |
| 通知吞吐量 | > 1000 条/分钟 | 持续压力 |
| K 线查询吞吐量 | > 100 次/秒 | 持续压力 |
| 服务可用性 | ≥ 99.5% | 月度统计 |
| 消息成功率 | ≥ 99% | 发送统计 |

## 🎯 关键技术决策

### 1. 服务拆分策略

**决策**: 拆分为两个独立服务（K 线数据服务 + 通知服务）

**理由**:
- 职责清晰，便于维护
- 可独立扩展
- 故障隔离
- 技术栈最优选择

### 2. 数据库选型

**决策**: PostgreSQL 14+ 分区表

**理由**:
- 强大的 SQL 功能
- 原生分区表支持
- 时区数据处理
- 成熟稳定

### 3. 消息队列

**决策**: Redis 7+ List 结构

**理由**:
- 高性能（内存操作）
- 简单可靠
- 持久化支持
- 与 FastAPI 集成良好

### 4. 异步处理

**决策**: 后台 Worker 异步消费队列

**理由**:
- API 快速响应
- 削峰填谷
- 失败重试不影响主流程
- 可水平扩展 Worker 数量

### 5. 部署方式

**决策**: Docker Compose 一键部署

**理由**:
- 环境一致性
- 部署简单
- 易于扩展
- 便于运维
