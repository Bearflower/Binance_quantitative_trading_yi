## 1. 项目概述

### 1.1 项目目标

建设统一的基础设施服务层，为 5 个交易/监控系统提供共享的数据采集、处理和通知能力，降低系统耦合度，减少重复开发和维护成本。

### 1.2 核心价值

- **降低 API 调用频率**：统一数据采集，避免重复请求币安 API
- **统一通知能力**：标准化消息发送接口，支持异步队列
- **数据一致性**：所有系统使用同一数据源，避免数据差异
- **降低维护成本**：公共模块统一管理，减少重复代码

### 1.3 服务对象

| 系统名称 | 项目路径 | 使用服务 |
|---------|---------|---------|
| BTC/ETH 交易系统 | `/Users/yl/vscode/bianace_btcethbnb_trade` | K 线数据 + 通知服务 |
| 新币做空系统 | `/Users/yl/vscode/bianace_newtrade_trade` | K 线数据 + 通知服务 |
| 网格交易系统 | `/Users/yl/vscode/Grid_Trading` | K 线数据 + 通知服务 |
| 服务器巡检系统 | `/Users/yl/vscode/inspection_automation` | 通知服务 |
| A 股筛选系统 | `/Users/yl/vscode/stockfilter` | 通知服务 |

## 2. 业务背景

### 2.1 当前痛点

#### 2.1.1 数据采集重复
- 3 个交易系统各自独立调用币安 API 获取 K 线数据
- 存在大量重复请求，浪费 API 配额
- 容易触发币安风控限流

#### 2.1.2 通知能力分散
- 5 个项目各自实现飞书推送逻辑
- 代码重复，维护成本高
- 巡检系统使用 Shell 脚本，无法复用 Python 库
- 无消息队列，同步发送可能阻塞主流程

#### 2.1.3 数据不一致风险
- 各系统调用 API 时间点不同
- 可能导致同一时刻数据存在差异
- 影响交易决策一致性

### 2.2 建设必要性

通过统一基础设施服务，解决上述痛点，实现：
- 数据采集集中化
- 通知能力服务化
- 技术栈标准化

## 3. 需求范围

### 3.1 服务组成

本项目包含两个独立但相关的子服务：

```
统一基础设施服务
├── K 线数据服务 (Kline Data Service)
│   ├── 数据采集模块
│   ├── 指标计算模块
│   └── 数据存储模块
│
└── 统一通知服务 (Unified Notification Service)
    ├── 消息发送 API
    ├── 消息队列模块
    └── 配置管理模块
```

### 3.2 功能边界

#### ✅ 包含的功能

**K 线数据服务：**
- 定时从币安 API 采集 K 线数据
- 支持多币种、多周期
- 预计算常用技术指标（MA/EMA/RSI/MACD/ATR/布林带等）
- 存储到 PostgreSQL 数据库
- 提供数据查询 API

**统一通知服务：**
- 提供 HTTP API 发送消息
- 支持文本、Markdown、卡片消息格式
- 支持多项目 webhook 配置
- 消息队列异步发送
- 错误重试机制
- 简单频率控制

#### ❌ 不包含的功能

**K 线数据服务：**
- 业务指标计算（各系统独立）
- 交易信号检测
- 评分引擎逻辑

**统一通知服务：**
- 消息模板管理（v1.0）
- 消息历史记录（v1.0）
- 告警升级机制
- 多渠道自动切换

### 3.3 用户特征

**主要用户**：5 个业务系统的开发者/运维人员

**使用场景**：
- 业务系统定时任务调用 K 线数据 API
- 业务系统触发通知时调用通知服务 API

## 4. 功能性需求

### 4.1 K 线数据服务

#### 4.1.1 数据采集

**FR-KD-001: 多币种支持**
- 支持配置监控币种列表
- 初始支持：BTCUSDT, ETHUSDT, BNBUSDT
- 支持动态添加/删除币种

**FR-KD-002: 多周期支持**
- 支持周期：15m, 1h, 4h, 1d
- 网格交易额外支持：15m, 1h, 4h
- 做空系统支持：15m, 1h, 4h, 1d

**FR-KD-003: 采集频率**
- 15m 周期：每 15 分钟采集一次
- 1h 周期：每 60 分钟采集一次
- 4h 周期：每 4 小时采集一次
- 1d 周期：每日采集一次

**FR-KD-004: 数据补全**
- 支持手动触发历史数据补全
- 支持指定时间范围补全

**FR-KD-005: 限流保护**
- 遵守币安 API 限流规则
- 失败自动重试（最多 3 次）
- 重试间隔递增（2s, 5s, 10s）

#### 4.1.2 指标计算

**FR-IC-001: 基础指标计算**
- MA (移动平均线): 5/10/20/60 周期
- EMA (指数移动平均线): 5/10/20 周期
- RSI (相对强弱指标): 14 周期
- MACD (移动平均聚散指标): 标准参数

**FR-IC-002: 高级指标计算**
- ATR (平均真实波幅): 14 周期
- 布林带 (Bollinger Bands): 20 周期，2 标准差
- 成交量均线：5/20 周期

**FR-IC-003: 指标存储**
- 指标与 K 线数据关联存储
- 支持按指标类型查询

#### 4.1.3 数据存储

**FR-DS-001: 数据库选型**
- 使用 PostgreSQL 14+
- 使用时序数据优化（分区表）

**FR-DS-002: 数据分区策略**
- 按币种 + 周期分区
- 每个分区独立索引
- 支持快速数据清理

**FR-DS-003: 数据保留策略**
- 做空系统数据：保留 30 天
- 其他系统数据：可配置（默认 180 天）
- 支持自动清理过期数据

**FR-DS-004: 数据查询 API**
- RESTful API 查询接口
- 支持时间范围查询
- 支持币种/周期过滤
- 支持指标数据查询

#### 4.1.4 数据服务 API

**FR-API-001: 查询 K 线数据**
```
GET /api/v1/klines
Params:
  - symbol: 币种 (必填)
  - interval: 周期 (必填)
  - start_time: 开始时间 (可选)
  - end_time: 结束时间 (可选)
  - limit: 数量限制 (可选，默认 1000)
```

**FR-API-002: 查询指标数据**
```
GET /api/v1/indicators
Params:
  - symbol: 币种 (必填)
  - interval: 周期 (必填)
  - indicator_type: 指标类型 (必填)
  - time: 时间点 (可选，默认最新)
```

**FR-API-003: 健康检查**
```
GET /api/v1/health
Response:
  - status: 服务状态
  - last_update: 最后更新时间
  - db_status: 数据库连接状态
```

### 4.2 统一通知服务

#### 4.2.1 消息发送

**FR-NS-001: 统一发送接口**
```
POST /api/v1/send
Body:
  {
    "project": "btc_eth|new_coin|grid|inspection|stock",
    "message": "消息内容",
    "type": "text|markdown|card",
    "level": "info|warning|error"
  }
```

**FR-NS-002: 消息格式支持**
- 文本消息 (text)
- Markdown 消息 (markdown)
- 卡片消息 (card) - JSON 格式

**FR-NS-003: 消息级别**
- info: 普通信息
- warning: 警告信息
- error: 错误告警

**FR-NS-004: 异步消息队列**
- 使用 Redis 作为消息队列
- 消息入队后立即返回
- 后台 worker 异步发送
- 队列容量限制：10000 条

**FR-NS-005: 错误重试**
- 发送失败自动重试
- 最多重试 3 次
- 重试间隔：1s, 3s, 5s
- 重试失败记录日志

**FR-NS-006: 频率控制**
- 每个项目独立频率限制
- 默认：60 条/分钟
- 可配置调整

#### 4.2.2 配置管理

**FR-CM-001: Webhook 配置**
- 通过环境变量配置
- 格式：`{PROJECT}_WEBHOOK`
- 示例：`BTC_ETH_WEBHOOK=https://...`

**FR-CM-002: 配置热更新**
- 支持不重启服务更新配置
- 通过 SIGHUP 信号触发

#### 4.2.3 管理 API

**FR-ADM-001: 服务健康检查**
```
GET /api/v1/health
Response:
  - status: ok|degraded|error
  - queue_size: 队列中消息数
  - workers: worker 数量
```

**FR-ADM-002: 队列状态查询**
```
GET /api/v1/queue/status
Response:
  - total_messages: 总消息数
  - pending: 待发送数
  - failed: 失败数
```

## 5. 非功能性需求

### 5.1 性能需求

**NFR-001: 响应时间**
- K 线数据查询 API: < 500ms (95% 请求)
- 通知发送 API: < 100ms (消息入队时间)
- 健康检查 API: < 50ms

**NFR-002: 吞吐量**
- K 线数据服务：支持 100 次/秒查询
- 通知服务：支持 1000 条消息/分钟

**NFR-003: 并发能力**
- 支持 50 个并发连接
- 数据库连接池：20 个连接

### 5.2 可靠性需求

**NFR-004: 可用性**
- 服务可用性：≥ 99.5%
- 计划外停机：< 4 小时/月

**NFR-005: 数据完整性**
- K 线数据不丢失
- 消息不丢失（队列持久化）

**NFR-006: 容错能力**
- 币安 API 失败不影响历史数据查询
- 通知服务支持重试

### 5.3 可维护性需求

**NFR-007: 日志记录**
- 结构化日志（JSON 格式）
- 日志级别可配置
- 关键操作审计日志

**NFR-008: 监控指标**
- API 请求量/响应时间
- 队列长度/处理速率
- 错误率/重试次数

**NFR-009: 配置管理**
- 配置与代码分离
- 支持环境变量
- 敏感信息加密

### 5.4 安全性需求

**NFR-10: API 安全**
- 支持 API Token 认证（可选）
- CORS 跨域控制
- 请求频率限制

**NFR-11: 数据安全**
- Webhook URL 不记录到日志
- 数据库连接使用连接池
- 敏感配置使用环境变量

## 6. 技术约束

### 6.1 技术栈要求

**后端框架**:
- Python 3.9+
- FastAPI 0.100+
- Uvicorn (ASGI 服务器)

**数据库**:
- PostgreSQL 14+
- Redis 7+ (消息队列)

- Docker 20+
- Docker Compose 2.0+

**API 兼容**:
- RESTful API 设计
- JSON 数据格式
- 向后兼容至少 2 个版本

**数据兼容**:
- 支持从现有系统迁移
- 数据格式保持一致

**代码规范**:
- 遵循 PEP 8
- 类型注解 (Type Hints)
- 单元测试覆盖率 ≥ 80%

**文档规范**:
- API 文档自动生成 (OpenAPI/Swagger)
- 部署文档完整
