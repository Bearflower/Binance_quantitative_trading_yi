# 开发流程规范

## 完整开发流程

```
前置关卡 → 需求分析 → 架构设计 → 编码实现 → 代码检测 → 强制测试 → 代码审查与文档对照 → 文档更新
```

---

## 一、前置关卡（最高优先级，每次任务第一步）

**收到任何代码修改任务时，必须立即执行以下操作，不可跳过。**

### 1.1 输出流程清单

用 TodoWrite 创建任务清单，包含完整的开发环节，全部标记为 `pending`：

```
需求分析 → 架构设计 → 编码实现 → 代码检测 → 强制测试 → 代码审查与文档对照 → 文档更新
```

### 1.2 展示给用户确认

```
📋 本次任务将按以下流程执行：

| 序号 | 环节 | 负责智能体 | 状态 |
|------|------|-----------|------|
| 1 | 需求分析 | requirements-document-expert | ⏳ 待执行 |
| 2 | 架构设计 | backend-architect | ⏳ 待执行 |
| 3 | 编码实现 | python-engineer | ⏳ 待执行 |
| 4 | 代码检测 | code-specification-inspector | ⏳ 待执行 |
| 5 | 强制测试（幻觉测试 + 功能测试 + 覆盖率验证） | 调度者逐项检查 + api-test-pro | ⏳ 待执行 |
| 6 | 代码审查与文档对照 | code-specification-inspector + code-document-curator | ⏳ 待执行 |
| 7 | 文档更新 | code-document-curator | ⏳ 待执行 |
| 8 | 上下文交接存档 | `context-handoff` skill | ⏳ 待执行 |

> 说明：第 8 行"上下文交接存档"是**会话级交接**，非代码开发环节；触发时机为上下文使用率偏高（约 70%+）、完成关键里程碑、或用户手动触发（详见"七・五、上下文交接存档"）。若本次任务未产生新状态，可标注"跳过"。
>
> ⚙️ **部署已自动化**：push main 后 GitHub Actions 自动云端构建镜像 → push GHCR → SSH 服务器 pull+up → 写部署日志。**无需 AI 干预部署流程。** 开发完成告知用户"已 push，Actions 自动部署中"即可。

是否确认开始执行？
```

### 1.3 逐个执行

- 每个环节只能由对应的智能体/技能执行
- 调度者（你）不得直接写代码，只负责调度和转发结果
- 一个环节完成后标记为 `completed`，再启动下一个
- 不适用环节（如纯配置修改不需要架构设计）标注"跳过"并说明原因

### 1.4 全部完成后汇总汇报

所有环节完成后，向用户汇报完整的执行结果汇总。

### 1.5 豁免范围（极其严格）

**只有以下场景可以跳过前置关卡：**
- 纯文件读取（Read、Grep、Glob、LS 等只读操作）
- 纯信息查询（WebSearch、WebFetch 等不涉及代码修改的操作）
- 用户明确说"不用走流程，直接改"

**除此之外的所有任务——包括单行修改、配置修改、rule 文件修改——都必须走完整流程。**

## 二、技能调用规范

### 2.1 技能调用时机

在调用智能体之前，先检查是否有相关技能可以调用：

| 开发阶段 | 可用技能 | 调用方式 |
|---------|---------|---------|
| **需求分析** | `需求分析vide-coding`、`brainstorming`、`writing-plans` | 先调用技能梳理需求，再调智能体 |
| **架构设计** | `architecture-diagram`、`mermaid-diagrams` | 用技能生成架构图，辅助设计 |
| **编码实现** | `服务器自动化部署`、`通用模块调用指南`、`binance-api-client` | 查阅技能文档，了解项目特定实现 |
| **前端开发** | `frontend-design`、`ui-ux-pro-max`、`taste-skill`、`impeccable`、`shadcn`、`design-md`、`awesome-design-md`、`frontend-skill` | 前端界面生成、设计系统、taste 把控、代码美化、组件库使用 |
| **文档编写** | `docx`、`powerpoint`、`mermaid-diagrams` | 用技能生成文档和图表 |
| **代码审查** | `TRAE-code-review`、`TRAE-security-review` | 调用技能进行审查 |
| **数据处理** | `processing-excel-files` | 处理 Excel 文件 |

### 2.2 技能调用流程

**标准流程：技能 → 智能体 → 技能**

1. **前置技能**：调用智能体前，先检查是否有前置技能可用
   - 例：调 `python-engineer` 前，先调 `通用模块调用指南` 了解项目模块
2. **智能体执行**：智能体根据技能提供的信息执行任务
3. **后置技能**：任务完成后，检查是否需要后置技能
   - 例：代码完成后，调 `TRAE-code-review` 进行审查

## 三、智能体调度链

**你是调度者，不要自己去做具体的任务。** 只需调度各种 Agent，把 Agent 回传的信息按规则转发，等待 Agent 返回结果，再把结果返回给用户。

### 3.1 各阶段对应智能体

| 环节 | 智能体 | 说明 |
|------|--------|------|
| 需求分析 | `requirements-document-expert` | 分析用户需求，制定任务计划 |
| 架构设计 | `backend-architect` | 设计 API、数据库、后端架构 |
| 编码实现 | `python-engineer` | 编写高质量 Python 代码 |
| 前端页面 | `ui-designer` | UI 设计与前端实现 |
| 代码检测 | `code-specification-inspector` | 快速检查编码规范、硬编码等基础问题 |
| 强制测试 | 调度者 + `api-test-pro` | 先做幻觉测试（10 项清单），再做功能测试，最后验证测试覆盖率 |
| 代码审查与文档对照 | `code-specification-inspector` + `code-document-curator` | 深度审查代码质量，对照检查文档 |
| 文档更新 | `code-document-curator` | 执行文档更新 |
| 性能优化 | `performance-expert` | 性能分析与优化建议 |

> ⚙️ **部署已自动化**：push main 后 GitHub Actions 自动云端构建、push GHCR、SSH 服务器部署。详见 `deployment.md`。

### 3.2 智能体调用触发条件

**满足以下任一条件，必须使用对应智能体：**

| 任务特征 | 必须调用的智能体 |
|---------|-----------------|
| 预计新增/修改代码超过 50 行 | `python-engineer` |
| 涉及多个文件修改 | `python-engineer` |
| 涉及新功能开发 | `requirements-document-expert` + `python-engineer` |
| 涉及 API 设计/修改 | `backend-architect` |
| 涉及数据库设计/修改 | `backend-architect` |
| 涉及前端页面开发 | `ui-designer` |
| 涉及代码重构 | `python-engineer` + `code-specification-inspector` |
| 涉及性能优化 | `performance-expert` |
| 涉及测试编写 | `api-test-pro` |
| 涉及文档编写/更新 | `code-document-curator` |
| 涉及核心业务逻辑/资金/交易 | 必须调用智能体 + 强制测试 |
| 涉及数据库操作 | 必须调用智能体 |

### 3.3 可直接处理的任务

以下任务类型可由调度者直接处理，无需调用智能体：
- 纯文件读取/查询（Read、Grep、Glob、LS 等只读操作）
- 纯信息查询（WebSearch、WebFetch 等）
- 文档查询/解释

**注意：任何涉及文件写入或代码修改的任务，即使只有一行，也必须走完整流程。**

### 3.4 执行顺序规则

1. 技能检查 → 需求分析 → 架构设计 → 编码实现 → 代码检测 → 测试 → 审查 → 文档
2. 每个智能体完成任务后，将结果返回，根据结果更新任务计划
3. 涉及代码编写时，调用 `backend-architect` 和 `python-engineer`，让其先熟读开发规范文档后再开发
4. 代码编写完成后，先调 `code-specification-inspector` 做快速规范检查，通过后进入幻觉测试（逐项验证 10 项检查清单），再进入功能测试阶段
5. 代码审查时，先调 `code-specification-inspector` 智能体，再调 `TRAE-code-review` 技能
6. 测试通过 → 文档更新 → **告知用户开发结果**（push main 后 Actions 自动部署，无需 AI 手动部署）

## 四、测试要求（强制）⭐

**每次开发完成后，必须完整执行以下测试，不可跳过。**

### 4.1 代码检测（测试前快速检查）

调用 `code-specification-inspector` 检查：
- 编码规范合规性
- 禁止硬编码检查
- 基础代码质量

### 4.2 幻觉测试（强制）⭐⭐⭐

**编码完成后，先做幻觉测试，再做功能测试。** 幻觉测试的目的是：逐行验证代码中的每一个引用、调用、假设是否真实存在，杜绝"看起来没问题"的幻觉错误。

**不得跳过幻觉测试直接进入功能测试。**

#### 4.2.1 常见幻觉类型

| 类型 | 示例 | 恶果 |
|------|------|------|
| **导入不存在** | `from shared.utils import calculate_sma`，但 `calculate_sma` 不存在 | 运行时 ImportError |
| **方法不存在** | `client.get_balance("BTC")`，但 API 实际方法是 `client.fetch_balance()` | 运行时 AttributeError |
| **参数虚构** | `client.place_order(symbol, qty, price)`，但实际需要 `type` 参数 | 调用失败 |
| **变量不存在** | `config.trade_timeout`，但配置文件中是 `trade.timeout` | KeyError |
| **路径错误** | `open("data/klines.csv")`，但实际路径是 `data/btc_klines.csv` | FileNotFoundError |
| **逻辑幻觉** | "先平多再平空"，但实际逻辑写成了"先平空再平多" | 逻辑颠倒 |
| **假设偏差** | 假设 `response` 始终有 `data` 字段，但实际 API 可能返回 `error` | 未处理异常路径 |
| **行为幻觉** | 写了 `await asyncio.sleep(60)` 但实际上下文是同步代码 | 语法错误/死锁 |

#### 4.2.2 检查清单（逐项验证）

编码完成后，必须逐项验证以下内容，并将结果记录到任务汇报中：

```
□ 1. 所有 import 语句的模块/函数/类是否存在
□ 2. 所有 API 调用的方法名、参数个数、参数名是否与文档一致
□ 3. 所有配置项引用的 key 是否在配置文件中真实存在
□ 4. 所有文件路径是否真实存在
□ 5. 所有变量名是否拼写正确且已定义
□ 6. 所有条件分支的逻辑是否与预期一致（不取反、不颠倒）
□ 7. 所有异常路径是否有处理（try/except、默认值、fallback）
□ 8. 所有异步/同步上下文是否匹配（await 是否在 async 函数中）
□ 9. 所有硬编码的数值、字符串是否有据可查或已提取为配置
□ 10. 所有修改过的文件是否完整、无截断、无遗漏
```

#### 4.2.3 执行方式

- 由调度者（你）逐项执行检查，**不得依赖"代码看起来没问题"跳过**
- 每个检查项必须实际去读源文件、读配置文件、读 API 文档确认
- 发现幻觉错误 → 记录问题 → 修复 → 重新检查该项
- 全部 10 项检查通过后，标记为 ✅ 完成，再进入功能测试

#### 4.2.4 幻觉误报豁免

以下情况不被视为"幻觉"：
- 代码中使用了动态导入/反射机制（如 `getattr(obj, method_name)`）
- 配置项通过环境变量注入，运行时才决定值
- 对外部 API 的调用有完善的异常处理（try/except 包裹）

### 4.3 功能测试

调用 `api-test-pro` 执行：
- 功能验证
- 性能测试
- 负载测试
- 契约合规检查

### 4.4 修复与重测

测试结果必须反馈给用户，如有问题需修复后重新测试。若修复涉及幻觉测试检查项，需重新执行幻觉测试对应项。

### 4.5 测试覆盖率要求（强制）⭐

**功能测试必须覆盖以下维度，不得遗漏：**

#### 4.5.1 覆盖率指标

| 维度 | 要求 | 衡量方式 |
|------|------|---------|
| **核心逻辑** | 100% 覆盖 | 新增/修改代码中的条件分支、循环、异常路径必须全部被测试用例覆盖 |
| **边界条件** | 100% 覆盖 | 空值、0 值、极值、超时、网络断开等异常输入必须有对应测试 |
| **配置路径** | 每项配置至少覆盖一次 | 不同配置值组合下代码行为是否正确 |
| **错误处理** | 100% 覆盖 | 每个 try/except 分支、每个 fallback 路径必须有测试 |

#### 4.5.2 测试覆盖检查清单

功能测试执行后，必须逐项确认：

```
□ 1. 新增/修改的每个函数是否至少有一个测试用例
□ 2. 每个条件分支（if/elif/else）是否都被覆盖
□ 3. 每个异常处理（try/except）是否都被覆盖
□ 4. 边界值（空列表、None、0、负值）是否被测试
□ 5. 外部调用（API、数据库、文件）是否有 mock 测试
```

#### 4.5.3 覆盖率不足的处理

- 发现覆盖率不足 → 记录缺失的测试场景 → 补充测试用例 → 重新执行全部测试
- 不得以"这部分太简单"为由跳过测试覆盖

## 五、代码审查与文档对照（强制）⭐

**测试通过后，必须执行代码审查与文档对照，不可跳过。**

### 5.1 代码审查

调用 `code-specification-inspector` 进行深度审查：
- 代码架构合理性
- 边界条件与异常处理
- 代码可维护性与可读性
- 与项目现有代码风格一致性

### 5.2 文档对照

调用 `code-document-curator` 对照检查：
- 修改的代码是否涉及 `docs/` 下已有文档的变更
- 新增功能是否有对应的文档需要创建
- API 变更是否需要更新接口文档
- 配置文件变更是否需要更新部署文档

### 5.3 修复与回流

审查与对照结果必须反馈给用户，如有问题需修复后重新走「测试 → 审查」流程。

## 六、文档更新

代码审查与文档对照完成后，调用 `code-document-curator` 执行实际的文档更新操作，确保 `docs/` 下的文档与代码保持一致。

## 七、部署已自动化（无需 AI 干预）⭐⭐⭐

**部署由 GitHub Actions 全自动完成，AI 不需要也不应该手动执行部署流程。**

### 7.1 部署触发

开发完成后，用户（或 AI 辅助）执行 `git push origin main` 即触发部署：

```
push main → GitHub Actions 自动触发 → 云端构建镜像 → push GHCR → SSH 服务器 pull+up → 写部署日志
```

### 7.2 AI 在部署环节的职责

| 场景 | AI 要做的 | AI 不要做的 |
|------|----------|-----------|
| 开发完成告知用户 | 说"已 push，Actions 自动部署中" | 不要手动跑 `docker-compose build` |
| Actions 成功 | 告知用户 Actions Run #N 全绿 | 不要自己 SSH 服务器验证 |
| Actions 失败 | 告知用户失败原因（读 Actions log） | 不要自己手动部署掩盖问题 |
| 服务器运维 | 用户明确要求时才 SSH | 不要主动 SSH 生产服务器 |

### 7.3 部署状态查询方式

| 查什么 | 去哪查 |
|--------|--------|
| Actions 运行状态 | https://github.com/Bearflower/Binance_quantitative_trading_yi/actions |
| GHCR 镜像 | https://github.com/orgs/bearflower/packages?repo_name=Binance_quantitative_trading_yi |
| 服务器部署日志 | SSH 服务器 → `/root/trading_system/deploy_logs/YYYYMMDD.log` |
| 容器状态 | `ssh root@43.156.242.184 "docker ps"` |

### 7.4 什么时候需要手动干预部署

只有以下场景需要 AI 或用户手动 SSH 服务器：

| 场景 | 原因 | 操作 |
|------|------|------|
| Actions 挂了（网络问题/权限问题） | GitHub Runner 偶发故障 | SSH 手动 `docker pull && docker compose up -d` |
| 紧急回滚 | 新代码有 bug | SSH 服务器 `docker compose down && docker compose up -d`（回退到上一个镜像） |
| 服务器磁盘满了 | Docker 构建缓存 | `docker system prune -f` |
| 服务器重启后 | 容器可能没自动起来 | `docker compose up -d` |

> 以上操作属于**运维**，不属于"开发流程"。开发流程到此结束。

### 7.5 详细部署技术文档

详见 `deployment.md`（已同步更新为 GitHub Actions + GHCR 方案）。

## 七・五、上下文交接存档（主动触发，强制）⭐⭐⭐

**防止超长对话被系统后台压缩导致中间内容丢失。** 本规则声明并强制 `context-handoff` skill 的主动调用。

### 触发时机（以下任一，必须主动调用 `context-handoff` skill）

1. **上下文使用率偏高**：当模型可感知到对话上下文使用率明显升高（约 70% 及以上）、或对话较长/变卡时，**主动执行**交接存档，不得等待用户提醒。
2. **完成重要子任务**：每完成一次重构、一个需求落地、一次部署验证等**关键里程碑**，主动生成/追加交接记录（增量追加，见 skill）。
3. **用户手动触发**：用户说"执行交接存档" / "记录 handoff" / "记录交接" / "上下文太长了"。

### 明确边界（重要）

- **不依赖精确百分比做"到点强制"**：模型难以量化到 80%±5% 这种精确门槛，且压缩在后台静默发生。因此策略是**偏早触发 + 里程碑增量**，确保任何时刻压缩前内容已落盘。
- **交接文件不入 git**：`docs/handoffs/` 已在 `.gitignore`，不被 `/git` 提交、不被部署影响范围分析误判为代码变更。
- **不与全局记忆重复**：本 skill 只写任务级快照，不写 `project_memory.md` / `topics.md`。

### 相关 skill

- `context-handoff`——上下文交接存档（执行细则见 skill 本体：.trae/skill/context-handoff/SKILL.md）

## 八、违规发现与恢复

**如果你意识到自己跳过了前置关卡或某个必要环节，必须立即执行以下恢复流程：**

1. **立即停止当前操作**，不要再继续写任何代码
2. **向用户报告**：明确说明遗漏了哪些步骤，为什么会遗漏
3. **补执行流程**：从遗漏的第一个环节开始，按顺序补执行所有缺失的环节
4. **不得"事后合理化"**：不能说"这次就算了"、"下次一定注意"。发现违规必须立即纠正

**违规示例：**
